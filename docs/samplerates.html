Sample rates, periods and resampling

A sample in a module has no pitch of its own. It is just a list of bytes.
The note you put in a pattern tells the player how fast to read those bytes, and how fast depends on the tracker mode you are in.
ProTracker (.mod) and FastTracker (.xm) do not agree on this, and inside .xm there are two frequency tables that also differ in how they get there.

This matters the moment you resample a sample to a target note, because the target byte rate is a different number in each mode.
If you resample in one mode and save in the other, everything will play slightly too fast or too slow.

ProTracker: Amiga periods

On the Amiga, the Paula chip is told a period: the number of clock ticks between two sample bytes.
A lower period means a higher pitch.

rate = 7093789.2 / (2 × period)   (PAL Amiga clock, BassoonTracker uses 7093790)

ProTracker knows 36 periods (3 octaves, 856 down to 113) plus a finetune table per sample in steps of 1/8 semitone.
That is all a .mod file can express: the note picks a period, the finetune picks one of 16 variants of that period.

An NTSC Amiga runs its clock at 7159090.5 Hz, so the same module plays 0.92% higher there. ProTracker itself doesn't care, it just writes periods.

FastTracker: "Amiga frequency table"

FastTracker 2 is a PC program, but its default frequency table imitates the Amiga: notes map to the same period numbers (428 for C-4, 214 for C-5 in FT2 naming).
The difference is the clock it divides by:

rate = 7158728 / (2 × period)

That constant comes from the NTSC Amiga clock, and it is why C-4 in FastTracker is the famous 8363 Hz.
The same period on a PAL Amiga (and in ProTracker mode) gives 8287 Hz.

The ratio between the two is 7158728 / 7093790 = 1.0092, or about 16 cents.
FastTracker also has 8 octaves instead of 3, and a per-sample relative note on top of finetune, so a sample can be shifted by whole semitones without touching its data.

FastTracker: "Linear frequency table"

With the linear table switched on, FastTracker stops using Amiga periods altogether.
A "period" is now just a number on a straight line where every semitone is 64 units and every octave is 768:

period = 7680 - 64 × (note - 1)   (note 1 = C-0, note 49 = C-4)
rate = 8363 × 2(4608 - period) / 768

C-4 gives period 4608 and, by construction, exactly 8363 Hz again. C-5 gives 3840 and 16726 Hz.
So the base rates of the notes are identical to the Amiga table. What changes is everything that moves a note:

Amiga tableSlides, portamento and vibrato add to the period. One unit of slide is a bigger pitch step on high notes than on low notes, exactly like real Amiga hardware.
Linear tableSlides add to the linear period. One unit is always 1/64 semitone, on any note. Slides sound the same in every octave.

What this means for resampling

The Resample function in the sample editor converts a sample so that it plays back at its original pitch and speed when triggered on the note you press.
To do that it needs the byte rate of that note, and it takes it from the current tracker mode. The panel shows you the number.

Consequences:

Resample in .xm mode, then save as .mod
Every sample now plays 0.92% too slow and 16 cents flat. All samples shift together, so the song is still in tune with itself, only a little low.
The real problem is timing: a drum loop that you cut to exactly 2 beats is now 0.92% longer than 2 beats.
At 141 BPM, speed 6, two beats is 8 rows = 0.851 s. That is 14106 bytes at 16574 Hz but 14235 bytes at 16726 Hz.
The player reaches the next row before the loop is finished and cuts it 129 bytes (8 ms) early. If the sample does not fade out by itself, that is a click on every retrigger.

Resample in .mod mode, then save as .xm
The other way round: 0.92% too fast, 16 cents sharp, and a short gap of silence before every retrigger.

Mixing samples that were resampled in different modes
They are now 16 cents apart from each other. Finetune (12.5 cents per step) gets you close but not exact.

Rule of thumb
Switch to the mode of the format you are going to save before you resample.
If you convert a finished song from one format to the other and want it to sound identical, resample every sample by the ratio 7093790 / 7158728 = 0.99093 (going to .mod) or its inverse 1.00915 (going to .xm).
BassoonTracker does not do this for you when you switch modes.

Which one is "right"?
Neither. A PAL Amiga plays .mod files the ProTracker way, FastTracker 2 plays .xm files the 8363 way, and every serious player (OpenMPT, ...) follows the same split.
As long as a sample is resampled for the format it ends up in, it plays correctly everywhere.
