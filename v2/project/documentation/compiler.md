# YAML compiler (spec 005 Phases 1-4, spec 008 skin, spec 009 registry)

Status: implemented for spec [005-interactive-workbench](../specs/005-interactive-workbench/requirements.md), all phases. The recipe vocabulary and diagnostic codes are tabulated in [interactive workbench](interactive-workbench.md) "Reference". See [interactive workbench](interactive-workbench.md) for the workbench UI and the `node v2/server.mjs` service that now drives conversion during editing.

## Pipeline

```
project/specs/application/current/app.yaml (+ referenced components/actions/rules)
  -> compiler/yaml.js      (source-range-preserving parse of each file)
  -> runtime/componentTypes.js (which types exist and what each accepts; spec 009)
  -> compiler/skin.js      (the skin document: styles, states, assets; spec 008)
  -> compiler/convert.js   (name resolution, labels, layout fields, prose recipes, styles, diagnostics)
  -> generic component tree + compiled skin + diagnostics list
  -> compiler/generate.js  (CLI; writes project/specs/application/app-outline.json)
  -> renderers/canvas/mountGeneric.js + runtime/genericLayout.js (v2/preview-app.html)
```

Run `node v2/compiler/generate.js` after editing any file under `project/specs/application/current/` (or let `node v2/server.mjs` run the same `compileApplication` on Save & Refresh; both write the identical `app-outline.json` shape), then open `v2/app.html` (plain application) or `v2/preview-app.html` (with Inspect/Interact tools) (served over plain HTTP, same as `preview.html`). This is a development-time step (specification-workflow.md: "Development-time outline/code generation is allowed; launching generated source remains static"); `preview-app.html` itself only fetches the already-generated `app-outline.json`, no compiler code ships to it.

This was for a while the second of two independent pipelines: spec 003's `preview.html` + `outline.json` + `runtime/{validate,normalize,layout}.js` + `renderers/canvas/mount.js` rendered a fixed transport/instrument-list example alongside it. Spec [011](../specs/011-retire-spec003-pipeline/requirements.md) retired that one on 2026-09-10, so `preview-app.html` + `app-outline.json` + `runtime/genericLayout.js` + `renderers/canvas/mountGeneric.js` is now the only pipeline.

## `compiler/yaml.js` — provenance

Project-owned (MIT), written from scratch rather than adding a third-party YAML dependency to the zero-dependency `v2` tree (spec 005 design.md: "kept out of the shipped app", and it never ships — only `generate.js`, a Node dev-time script, imports it). It intentionally supports only the block-YAML subset the project actually authors: block mappings, block sequences (including a sequence at the same indentation as its parent key, which real YAML also allows), scalar/mapping sequence items, single-key "named node" sequence items, folded multi-line plain scalars, and whole-line comments. It does not support flow collections, anchors/aliases/tags, multi-document streams, block scalars (`|`/`>`), or inline comments. See the file header for the full list; `v2/tests/yaml.test.js` runs it against every file currently under `application/current`.

A bare-prose rule file with no top-level key (`rules/noDependencies.yaml`) parses as a single scalar document rather than a mapping-parse failure.

## `compiler/convert.js` — identity, labels, layout, recipes

- **Identity** (`compiler/identity.js`): no authored IDs. A node's local identity is its `name:` field, else the mapping key it was nested under, else `type.firstLabel`, else its type. Instance ids are ancestry-qualified (`main.controlBar.button.Play`). Nodes that would otherwise collide (e.g. the two `notification light` entries in `app.yaml`, which share the same mapping key) get a deterministic `#1`/`#2` suffix and an `ambiguous-duplicate-name` warning, rather than being silently merged.
- **Labels** (`compiler/labels.js`): comma-separated label text splits into ordered variants (`"song, s"` -> `["song", "s"]`); not rewritten in YAML.
- **Layout fields** (`compiler/layoutFields.js`): `width`/`height` of `fill`/`fixed`/a number, `resizable` of `horizontal`/`vertical`. A `fixed` dimension with no explicit number takes the size the skin's style for that type declares (spec 008); a type the skin says nothing about uses this delivery's documented `COMPONENT_DEFAULTS` (a panel's fixed height defaults to 28px), and a type with neither falls back to a generic size and emits a `layout-default-fallback` warning rather than silently inventing a "real" requirement.
- **Component types** (`runtime/componentTypes.js`, spec 009): the compiler keeps no list of type names. A type's registry entry says whether it is implemented, how its children are authored (`content:`, `items:` of a declared child type, or named sibling keys), whether it carries artwork, and which properties it accepts. Every authored key is classified as a universal property, one of the type's own, its child slot, or a mistake; a mistake on a leaf is an `unknown-component-property` warning naming what the type accepts, rather than the bogus child node it used to become. A type that is declared but not yet rendered (`menu`, `spinBox`) says so in its `unsupported-component` message and has its item actions and properties checked all the same. See [components.md](components.md).
- **Styles** (`compiler/skin.js`, `runtime/skinModel.js`): `app.skin` names the skin document (default `skin/default.yaml`), which is compiled once before the tree and returned as `result.skin`; every styled node gets `style: { type, variant, requested, source, definition }`, where the source range is the `variant:`/`style:` line that asked for it. A radio group's variant cascades to its items through `itemStyle`. Unknown variants, states, properties and artwork are warnings, never failures. See [skin.md](skin.md).
- **Prose recipes** (`compiler/recipes.js`): a small, tested phrase vocabulary (`"toggle play state"`, `"toggle recording"`, `"toggle X on click"`, `"highlighted when X is active"`) maps recognized rule/action text to a generated binding with provenance. `noDependencies` and `horizontalResize` are recognized by name (informational / already covered by independent layout fields). Anything else — the two notification-light visibility/lighting sentences, the two radio-item playback-order sentences, `action1`/`action2`, the `volumemeter`/`menu` references — produces an `unresolved-*` warning and an inert/placeholder node. This is deliberately a small fixed vocabulary, not a general natural-language interpreter (design.md: "Do not claim arbitrary natural language can be understood by a small deterministic compiler").

Every diagnostic carries `{ severity, code, message, file, range, nodeId }`. Source ranges are exact offsets, indentation included (fixed in spec 008: they were short by each line's indentation, which only mattered once the Skin tab began splicing YAML at them); `COMPILER_VERSION` is 0.2.0 and `OUTLINE_SCHEMA_VERSION` is 3 as a result. A YAML syntax error or a missing `app.yaml`/`app.ui.main` is a hard failure (`generate.js` leaves the previous `app-outline.json` in place rather than overwriting it with a broken/partial result); an unresolved reference, unsupported component type or unresolved rule/action is a warning and the rest of the tree still compiles and renders (component/action reference cycles are also caught and reported as errors, without recursing forever, but do not by themselves abort the whole document the way a syntax error does).

Each generated binding carries `origin: "rule"|"action"` (which authoring field produced it) *and* its own `kind` from the recipe (e.g. `"visual-state"`, `"command"`, `"layout-policy"`) as separate keys - the binding literal is built as `{ origin: "...", ...result.binding }`, deliberately in that order, so the recipe's `kind` can never silently overwrite `origin` (an earlier version wrote `{ kind: "rule", ...result.binding }` and the spread clobbered it; caught via `v2/workbench.html`'s "contributing rules" panel and the Interact-mode mock-dispatch lookup both coming up empty - see the regression test in `compiler.test.js`).

## Phase 2: hit-testing, ancestry and the message bridge

`runtime/hitTest.js` is pure and DOM-free: `hitTestPoint(paintOrderNodes, point)` walks a flattened, paint-ordered node list backwards and returns the first (i.e. topmost/deepest) rect containing the point; `ancestryChain(root, id)` returns the root-to-target id path for breadcrumbs; `mapPointerToLogical(...)` corrects a pointer event's client coordinates for any mismatch between a canvas's intrinsic CSS box and its rendered bounding box (page zoom, a CSS transform) - devicePixelRatio itself is already absorbed by the canvas's internal resolution and `ctx.setTransform`.

`renderers/canvas/mountGeneric.js` uses these to implement Inspect/Interact modes and an on-canvas toolbar with clickable breadcrumbs. Hover only updates in Inspect mode; a persisted selection outline is drawn in either mode (spec 005 IWB-007: "selection survives mode switching where its node exists"). Inspecting a node never dispatches anything. Since Phase 4, Interact mode runs a `runtime/buttonController.js` per supported button/radio item and dispatches `origin: "action"` command bindings against an explicit mock state (`mockField`/`mockValues` from the recipes), tracing input/state/activation/command over the bridge as `v2:trace`; see [interactive workbench](interactive-workbench.md). It is still a visible mock, not real playback.

Recipes that observe state and recipes that change it must agree on the field: `RULE_RECIPES`' `highlighted-when-active` maps its condition subject through `CONDITION_FIELD_ALIASES` (play → `playback.status` active when `"playing"`, record → `record.active` active when `true`) so the binding carries `mockField` + `activeValue` that `ACTION_RECIPES`' toggles actually drive; unknown subjects still get a derived field (active when `true`) that nothing drives, which stays inspectable in the gallery rather than silently working.

When mounted inside an iframe (`window.parent !== window`), the renderer posts structured messages to the parent: `v2:ready` (on mount, with `sourceFiles`), `v2:hover`/`v2:select` (with `nodeId`, `ancestry`, `source`, `refSource`, `bindings`), each carrying the outline's `sourceHash` as `revision` so a parent can detect it's talking to a stale iframe. It also accepts `v2:setMode` and `v2:selectId` from the parent (e.g. clicking an ancestry breadcrumb in the workbench re-selects that node inside the iframe, which then posts `v2:select` back). Every message handler checks `event.origin`/`event.source` before touching payload data.

`v2/workbench.html` is the split-pane host: a file tree built from `app-outline.json`'s `sourceFiles` (or `/api/files` when served by `server.mjs`), a `<textarea>` buffer per file (read-only on a static host; editable and saveable under `node v2/server.mjs`, see [interactive workbench](interactive-workbench.md)), and a details panel driven entirely by the iframe's `v2:select` messages (ancestry breadcrumbs, definition/use-site links, contributing-rule links). Selecting a range uses the node's absolute character offsets (`compiler/yaml.js`'s `range.start/end.offset`) with `textarea.setSelectionRange` plus focus, which browsers auto-scroll into view. A per-file SHA-256, computed client-side with `crypto.subtle` (available on `http://localhost`, a secure-context exception) against `app-outline.json`'s `sourceFileHashes`, flags a buffer as stale if the on-disk file changed since the last `generate.js` run without requiring a server round-trip.

## `runtime/genericLayout.js` + `renderers/canvas/mountGeneric.js` — known limitation

The source language has no `layout.direction` field yet, so row-vs-column is a rendering default, not an authored fact: a `radioGroup` is always a row; any other container with a **fixed** height is treated as a single toolbar row (its children side by side); everything else stacks as a column. This matches `app.yaml`'s `top`/`controlBar` bars and its overall vertical panel stack, but it is a documented guess, not a spec requirement — a future authored direction field should override it. One consequence: `notifications`' two stacked `notification light` placeholders don't have enough height inside `top`'s fixed 28px toolbar row to avoid visually overlapping each other (the layout engine stretches a container to its row's cross-axis space so overflow can't cascade into sibling rows, but it doesn't shrink a container's own overflowing children). Acceptable for this delivery's "simplified but inspectable" scope; not a hidden/undisclosed limitation.

## Verification

`node --test "v2/tests/*.test.js"` (Node 26 needs the file glob) covers `compiler/{yaml,convert}.js`, `runtime/genericLayout.js`, `runtime/hitTest.js` and `server.mjs` (`tests/server.test.js` runs the real handler on an ephemeral port against a temporary copy of the source tree: containment, Host/token checks, atomic replace, 409/422, publish/hard-failure/race semantics) (parsing every real source file, name/label/layout/recipe resolution including the `origin`/`kind` regression, deterministic re-compilation, unresolved references, reference cycles, malformed-source hard failure, generic layout row/column/fill/auto distribution, and hit-testing/ancestry/pointer-mapping in isolation). Manual verification with chrome-devtools against a local static server: `v2/preview-app.html` standalone (diagnostics list/console, panels/buttons/radio items/placeholders, viewport resize) and `v2/workbench.html` end-to-end — hovering updates the status line, clicking Play in Inspect mode opens `components/controlBar.yaml` with the exact button block selected and shows its ancestry/definition/contributing-rule links, clicking the `main` breadcrumb re-selects the root and opens `app.yaml`, and switching to Interact mode and clicking Play logs a mock `transport.toggle` dispatch that never fires in Inspect mode (confirmed by console message counts before/after each click).
