## 2026-09-10 — Spec 009: the component registry

User direction after an assessment of what porting the v1 application to v2 would need: tackle the component registry first, because adding a component type meant editing six hardcoded lists that did not know about each other, and the port needs about thirty more types than the four v2 rendered.

`runtime/componentTypes.js` now declares every component type once: prose description, whether it is implemented, how its children are authored, whether it carries skin artwork, whether it is interactive, how selection affects its siblings, its layout direction, its draw kind and the properties it accepts. `UNIVERSAL_PROPERTIES` declares what every component accepts. The compiler, the layout engine, the canvas renderer, the emitter, the runtime factories and the workbench all read it, and `SUPPORTED_TYPES`, `RESERVED_KEYS`, `STYLED_TYPES` and both copies of `INTERACTIVE_TYPES` are gone. `renderers/canvas/drawKinds.js` is the new table where a kind owns both its drawing and its measurement, so those two cannot disagree; the emitter now calls one generic `component(type, props, children)` factory, which also puts the authored type name into the generated code as documentation.

Three things the registry made possible immediately. A key a component's type does not declare is reported as `unknown-component-property` at that key, listing what the type accepts, instead of silently becoming a child node with a misleading "unresolved component reference" (a mistyped `labell:` on a button was the motivating case). A type can be *declared without being implemented*, which is what `menu` and `spinBox` became: both are already authored in the current source, their properties and item actions are checked, the renderer draws its placeholder, and the diagnostic says "declared but not rendered yet" rather than treating them as typos. And the workbench gained a Components tab: every type with its status, contract, properties, a sample drawn by its own draw kind and the nodes using it, with links to the Skin tab and the State gallery, plus a `type:` row in the details panel. That closes the component-contract half of spec 002.

`checkbox` was added as the proof, through the registry alone: one entry, the shared `spriteLabel` draw kind (artwork at natural size with the label beside it), and two skin states over the `checkbox_on`/`checkbox_off` artwork already in the asset folder.

## 2026-09-10 — Spec 010: the port roadmap

User request after spec 009 closed: write down the further steps for moving the v1 application onto the v2 system, since the earlier assessment was only a chat answer.

Allocated spec 010 as an architecture/research spec: twelve work packages plus a cross-cutting parity harness, each to become its own numbered spec when it starts, with a dependency graph, five milestones, the risks, and six open decisions that are the author's to make. It rests on the 2026-09-10 inventory of `script/src`, `script/plugins` and `player/src`, which is summarised in its requirements: 25,300 lines of v1 own code against 6,728 in v2, 26 reusable component types against 6 implemented, 10 fonts against 1, 113 spritesheet assets against 14, 63 events and 37 commands against 4 prose recipes, about 54 tracker effect branches, and no automated tests on the v1 side at all. About 8,800 of v1's 14,453 UI lines sit in surfaces that are not component trees and become specialized components rather than YAML.

The order is dependency first, then risk, then visible value. Playback moves to the front, ahead of the UI machinery it does not need: it is the largest unknown, it is independent of layout and interaction, `player/src` is a 5,593-line UI-free reuse candidate, and a transport of plain buttons already exists to drive it. Then layout (clipping, scroll viewports, an overlay layer with z-order, declared breakpoints), then interaction (drag with capture, wheel, text entry with a caret, double-click, a declared shortcut table), then the remaining twenty component types and the screens they unlock, then the document model with undo and selection, then the pattern grid as the proof of the specialized-component contract, then renderer performance measured against that workload, then persistence and providers, features and the plugin path, and the remaining specialized surfaces.

This supersedes steps 5 to 9 of `IMPLEMENTATION-PLAN.md`, and says why: the DOM renderer buys accessibility rather than parity, since v1 is one canvas and a 21-element HTML shell, so it becomes conditional; playback was last and is now first; and step 4's promised clipping bounds, coalesced invalidation and semantic DOM mirror were never delivered and are now packages of their own. Steps 7 and 8 survive intact as the feature registry and the pattern grid.

Also recorded the definition of "ported" as six programme-level gates covering screen, musical, editing, file and delivery parity plus no regression in v2's existing guarantees, and the constraint that the song document never enters the state store: v1's patterns are six to twenty thousand note objects and modules on disk reach 15 MB.

No code changed. Documentation only: the spec, the specs and documentation indexes, product steering, and the supersession note on the roadmap. No Git commit was created.

## 2026-09-10 — Spec 012: playback, the first real capability (roadmap P2)

User direction: implement spec 010, the port roadmap, unattended. Started with its first package, playback, which the roadmap puts first because it is the largest unknown and the most independent piece of work.

The generated application now plays real modules. `player/src` from the parent repository (16 files, 5,593 lines, the playback-only subset with no UI imports) was adapted into `v2/domain/playback/engine/` and wired through `capabilities.js`, so the `transport.toggle` command the prose recipe already generated stops being a mock and delegates to the engine. Nothing in the authored YAML changed to make that happen, and the authored rule that lit the mock now lights the button from the real engine, because both name the same state field. Only the generated app and the bundle reach the capability: the authoring preview keeps its mock, so opening the workbench never starts an audio device and never loads a 68 KB sequencer.

Three divergences from the original, each recorded in `domain/playback/README.md` next to the code. The engine no longer creates an audio context at module import or patches the global constructor name, so the caller supplies one, created on the click. The browserified WAAClock bundle is gone, replaced by `domain/playback/scheduler.js`, a v2 implementation of the four things the sequencer actually uses; that is safe because the clock decides when the scheduling loop runs, not when notes sound, and every note, ramp and envelope point inside the loop is scheduled at an absolute audio-clock time. Nothing else changed: the circular imports between tracker, audio and instrument are preserved exactly, because reordering them is what would break them.

Those two divergences also bought the port its first real test story. The engine is now importable in plain Node, so `tests/playback.test.js` loads three fixtures and asserts their musical facts (title, channels, pattern shape, song length, instruments, envelopes, the vibrato effect, tempo, and that playing schedules a batch of sources spanning the lookahead window with absolute times), and `tests/scheduler.test.js` pins the clock's semantics against a fake context. These are the first automated tests this engine has ever had on either side of the project; v1 has none. `domain/playback/silentContext.js` is the stub context they run against, recording every start, stop and parameter automation so a test can assert on the schedule rather than on a waveform.

One small addition to the authored language, because playback had to be observable: a `label` may name a state `field` instead of static text, and that field becomes part of the application's state so a capability has somewhere to publish to. The status bar now shows the song title and the playback status. It needed no new draw kind and no branch on a component name, and the compiler carries every declared property of a type onto its node generically now, which removed the last hardcoded property pair.

Found while building: the position cursor did not advance. The sequencer schedules ahead and records timestamped states, and in v1 the frame loop decides which one is "now" and pushes it back into the engine; the capability had been publishing to the store without doing that, so anything reading the engine's own position, including the future pattern grid, would have sat at row 0. Also recorded as observed behaviour rather than corrected: v1 converts 8-bit sample data by dividing by 127 rather than 128, so values reach 1.008 and Web Audio clamps the difference, which is visible as a peak of 1.05 at the master output.

Verification: 127 tests, 125 passing, 2 pre-existing skips, up from 111. One new browser scenario, 17 checks, all passing: the engine and the module are absent at startup, the first click loads and plays, the engine reports four tracks and the title "wizball", the lazy chunk and the module data arrive on that click, the audio context runs and the master output carries signal at 0.52 rms, the pattern row advances, the Play button draws its active artwork, the status bar shows the title and status, a second click stops while keeping the module loaded, and the authoring preview never loads the engine and dispatches the mock instead. The other seven scenarios and the full build were re-run unchanged.

Not done: the offline render comparison against v1's own engine, which is roadmap package P13 and now says so. This package establishes that the engine runs, is bounded and is testable, not yet that it renders identically to v1. Recording, MIDI, the write path and remote sources are later packages; MP3 export is dropped because it needs a CDN-fetched encoder. No Git commit was created.

## 2026-09-10 — Spec 013: layout foundations (roadmap P3)

The third package of the port roadmap, and the debt spec 003's step 4 left: nothing in v2 was clipped, there was no scroller, and there was no way to draw above the tree.

`runtime/genericLayout.js` now returns a clip for every node, a content extent and applied offset for every viewport, and the ids of out-of-flow nodes in paint order. A node's clip is its parent's clip intersected with its own rect if its type clips, and its parent's otherwise; only the new `viewport` type clips, which is deliberate and is what kept the application's rendering identical. A panel does not clip, because clipping the flow would hide the overflow an author needs to see. Hit-testing now requires a point to be inside both the rect and the clip, so a control scrolled out of sight cannot be clicked where it is not visible; the click falls through to whatever really is visible there.

The `viewport` type lays its children out at natural height, translates them by the offset its bound state field holds, clips them, and reports the content extent so the offset can be clamped inside the layout pass. That means a bad field value cannot lose the content, and one viewport replaces the three separate scrollers v1 hand-rolled in its list box, its pattern view and its arrangement view. Interactive scrolling is explicitly not here: wheel, drag and a scrollbar thumb need the input work in package P4, and the roadmap now says P4 owns them.

Two registry fields carry the overlay layer: `layer: "overlay"` takes a node out of flow, laid out against the viewport, painted after the tree in declared order and clipped only by the viewport; `modal: true` additionally makes it swallow input, so a hit outside its subtree is not a hit at all. That is v1's zIndex sort plus its single global modal slot, expressed as declared data rather than a sort key an author maintains, and it goes through one gate in front of every pointer path so Inspect and Interact route identically. No component type declares either field yet, because dropdown, menu, modalDialog and tooltip are package P5; the mechanism is verified by mounting a hand-built tree through the public renderer API, with a throwaway type declared the way P5 will declare one and removed again afterwards.

`layout.direction` is now authorable, ahead of the component type's declared direction and ahead of the pre-013 rule that a fixed-height container reads as a row. That last step stays, because the application relies on it for its top bar and control bar.

Verification: 135 tests, 133 passing, 2 pre-existing skips, up from 127. One new browser scenario, 9 checks: a 60-pixel viewport holding twelve rows draws 2,621 lit pixels inside itself and exactly zero below it where the clipped rows were laid out, the sibling after it still draws, changing the bound field changes the top row's pixels, an absurd offset is clamped rather than emptying the box, a visible row activates on click, a modal overlay draws centred over the tree, and a control behind it cannot be activated. The other eight scenarios re-run at 111 checks, all passing.

Found while doing it: three of the four problems this package surfaced were in my own test fixtures rather than the code, and each is now documented in the test. A viewport's content extent is its own inner width, not its parent's. A row that starts inside a 20-pixel box can still extend past it. And a panel's own 9-slice border reads as content to a pixel counter, one bright pixel down each edge for the full height, which is the difference between a real clipping check and one that always passes.

Also corrected while here: the Components tab scenario had pinned the registry's contents as a literal, so adding the viewport type broke it. It now derives the expectation from the registry itself. Not done in this package and recorded as such: align, minimum and maximum sizes, and the declared breakpoints that replace v1's hand-written cascade, all of which belong with the screens in P5. No Git commit was created.

## 2026-09-10 — Spec 014: pointer interaction (roadmap P4, pointer half)

Package P4 was split in two when it was started. The pointer work and the keyboard work share nothing but the renderer they land in, so each became its own spec and each could be verified alone; this is the pointer half, and spec 015 owes the rest.

Before this, v2's whole input model was hover, press, focus, Enter and Space. There was no pointer capture, so there could be no drag, and without a drag there is no slider, no scrollbar and no block selection. `runtime/pointerRouter.js` is now a pure state machine that takes positions and the id of whatever the renderer found under them and returns semantic inputs, each addressed to a node: capture, a three-pixel drag threshold, leave and re-enter while held, a 400-millisecond double-click window with five pixels of slop, and secondary clicks that take no capture at all. Three details are deliberate and are documented where they live. The first drag event reports its delta from the press point rather than from where the threshold was crossed, so a fast flick does not lose its first three pixels. Coming back onto a node while still holding re-presses it, which is what a native button does. And a double-click is emitted *after* the second release rather than instead of it, so promoting a type to double-click-aware cannot regress anything.

Which controller a node gets is now declared by its type. `runtime/behaviors.js` is the one table from a behavior name to a factory, exactly as the draw-kind table is the one table from a draw kind to pixels; `button`, `value` and `scroll` are the three. Every controller has the same three members, so the renderer still has one `feed()`, and controllers now report `handled`, which is how a wheel can be offered to each ancestor in turn until one takes it and how the renderer decides whether to suppress the browser default.

A value control does not hold its value: the bound state field does, and every input carries the current value while the controller returns a new one. Which field that is resolves in three steps — the authored `field:`, then the mock field of a `change` action bound to the control, then a field derived from the node id — and the renderer and the emitter call the same function, so the field a generated application declares is the field the renderer writes. Bounds come from the authored `min`, `max` and `step` and every result is clamped and snapped on every path, so no gesture can produce an out-of-range or fractional number. `slider` and `spinBox` differ by two options: absolute along x against relative along y, with a stepper column on the spin box.

Spec 013's viewport can now be scrolled three ways — the wheel, a drag on its background, a drag on its scrollbar — and all three compute a *requested* offset that the layout pass clamps, so the clamp stayed in one place and no path can lose the content. `runtime/scrollbar.js` holds the thumb arithmetic that the draw kind, the controller and the cursor logic all read, and it returns nothing when the content fits, which is how each of those three decides to do nothing. A viewport at either end, or with no bound field, does not consume the wheel, so an outer scroller can take over.

`activate(id)` became `dispatch(id, event, detail)`. `actions:` has always carried an arbitrary event key and only `click` had a consumer; `change`, `doubleClick` and `secondaryClick` now do too, a binding with no event is still a click, and a `change` carries its new value into the generated action module as `detail`. A radio group's choices are authored as items, so the group is where its `change` action lives and the chosen item's name is the value.

Also delivered: one declared cursor per type, with the dragged node keeping the cursor wherever the pointer goes; and file drag-and-drop, where a drop calls `appContext.openFiles(files)`. The generated application gets that hook through a **reserved host command** — a `capabilities.js` key beginning `host.` is not authored in YAML and is not compiled from a binding, it is a hook the renderer offers and the manifest says who takes it — so dropping a module file on the generated application loads and plays it, while the authoring preview passes no app context at all and a drop there is a trace and nothing else.

Verification: 161 tests, 159 passing, 2 pre-existing skips, up from 135. One new browser scenario driving real Chrome input, 23 checks: pressing a slider at a quarter of its track gives 25; dragging it and ending 260 pixels below the control gives 90, so capture held; the thumb moved from the left of the track to the right; the wheel steps a spin box up and down; pressing the stepper's top half moves one step; the wheel over a *row inside* a viewport scrolls the viewport; dragging its background 40 pixels moves the offset 40; dragging its thumb 10 pixels moves it 48, so proportionally further; dragging across a button activates nothing; a double-click reports click, click, doubleClick in that order; a right-click reports only secondaryClick; the four cursor cases are right including during a drag; a dropped file is acknowledged, kept from the browser and handed to the application; and every gesture appears in the Interaction log with the drag coalesced to 8 entries out of 134. A third part drives the real workbench, because a renderer emitting a trace is not the same as the log showing it: the log's filter set starts as exactly the kinds it knows, so all three new kinds would have been hidden rather than shown uncoloured, and a wheel over the *authored* spin box now reads there as a wheel, as `tracks.value: 0 to 1`, and as the `tracks.set` command it is bound to. All ten scenarios together: 148 checks, none failing. `node build.mjs` produces all three targets; the entry chunk grew from 46,248 to 63,553 bytes and the playback engine stays in a lazy chunk.

The authored application's compile went from 13 warnings to 9, and three of its controls started working. Two of those had never worked and the reason was not in the renderer: `- click: toggleRecording` named an action document that does not exist, so the record button had been inert since spec 005, and `action:` is documented as an alias of `actions:` but only `actions:` was ever parsed, so a third radio group's binding was dropped with no warning at all. A bare action reference is now read as prose with camelCase split into words, which reaches the `toggle recording` recipe that already existed, and the alias is honoured. The record button consequently reaches the red active artwork its skin has always described, which until now was only checkable in the workbench's variant library.

Found while doing it, and worth recording: **a state change did not re-lay out, only redraw.** Spec 013's viewport therefore did not move when its bound field was written from outside the renderer — the rows kept the rectangles the previous pass had given them — and spec 013's browser scenario had passed anyway, because its check rested on a pixel fingerprint of the top row that changed for an unrelated reason. The renderer now separates the canvas resize from the layout pass and re-lays out on any state change, since a state change can move things and not only recolour them; the scenario asserts the applied offset as well as the pixels; and spec 013's tasks document carries a dated amendment saying so. The general lesson is recorded there too: a pixel check needs a structural assertion beside it or it can pass over the absence of the thing it is checking.

Three smaller findings. Making `viewport` interactive made `interactive` read oddly, since a viewport needs a controller but is not a control; rather than add a second flag, `interactive` keeps its documented meaning of "the renderer gives it a behavior controller" and `behavior` says which, and the two tests that pinned the list of interactive types were rewritten to derive it from the registry and assert the rule instead. Two tests and one browser scenario used `spinBox` as their example of a declared-but-unimplemented type, so promoting it broke all three; they now use `menu` and additionally check an implemented type's declared property, covering both sides of the distinction rather than resting on which types happen to be finished. And a slider's `min: 1` arrived at the node as the string `"1"`, so the compiler now converts a property the registry declares as a number and warns when the value is not one.

Not done and recorded as such: keyboard input is still the pre-014 minimum, and the focus model, text entry, the shortcut table, tooltips, dialog keys and command enablement are spec 015, which completes P4. Redraw coalescing stays package P8, which wants measurement before it changes how every input redraws. Horizontal scrolling and cell-level hit-testing belong to the pattern grid in P7. `scrollbar`, `knob` and `rangeSlider` are not component types: a viewport draws its own thumb, and a standalone scrollbar needs the binding vocabulary P5 brings. Touch and pen are not handled, which matches v1. No Git commit was created.
