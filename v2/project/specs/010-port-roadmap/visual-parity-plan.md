# Visual parity plan — v1 vs v2

Date: 2026-09-16. Audit only — no code/YAML changes were made while producing this document (one prior, already-applied fix is noted in Screen 1 below for context). Produced by live, side-by-side screenshots of both apps in real headless Chromium (Playwright, confirmed available in this environment via `npx` despite every prior spec assuming otherwise — see how-to at the bottom of this file), not static reference images, so what's described here is the actual current rendered state of both.

**Correction, recorded by the user 2026-09-16, after this audit's first pass**: the finding below originally concluded v1 uses floating overlay panels over an always-visible main screen, and recommended building an overlay/z-order mechanism to match (the original Task 5). That conclusion was wrong - see [ui-layout-model.md](../ui-layout-model.md), now steering documentation, for the corrected model and why the mistake happened. The section below is rewritten to match; Task 5 further down is re-scoped accordingly. Read `ui-layout-model.md` first - it explains the *goal* this whole plan should restructure v2 toward.

## The one finding that explains almost everything else

**v1 is divided into five fixed horizontal sections - menu bar, song properties, control bar, pattern (itself split into a sidebar and a main area), and piano - and each section can swap in one of several "full section" panels, in place, never as a floating layer.** Options, File Operations and Nibbles each swap into the **song properties section**; Sample Edit swaps into the **pattern section**. Their own "X" close button does not close an overlay - it returns *that section* to its own default content. The reason other regions kept rendering in this audit's own screenshots is that they are genuinely separate, unaffected sections - not because anything was layered on top of anything.

**v2 does not yet give these panels their own, independent section-scoped swap zones.** `normalMainView` currently conflates several of v1's own distinct sections into one combined vertical stack: `fileOperationsPanel`/`optionsPanel`/`sampleEditPanel` (each gated by `top-view.value`) sit as plain siblings alongside `editPad`/`patternViewPanel`/`songPatternList`/`songProperties` (which have no such gating and always show), all inside the one `main-view.value`-gated group. Because a swapped-in panel isn't scoped to its own bounded section, a tall one pushes every *later* sibling in that same combined stack down or off-screen instead of affecting only its own section's own space - confirmed for Options (already fixed this session) and structurally true for File Operations/Nibbles the same way.

Every other screen-specific finding below is a *symptom* of this one structural gap, except for two independent ones (the editPad button-clipping bug, and the sample editor's own control-orientation mismatch), called out separately.

**This is the highest-leverage fix in this whole plan** — see Task 5 below — but it's also the biggest one, since it changes *where these panels are scoped* (a real, independent "song properties section" and "pattern section" region each with their own swap zone), not just proportions, for four screens at once. It needs its own dedicated spec, not a quick YAML edit - and it must not be an overlay/z-order mechanism (see `ui-layout-model.md`).

## 1. Main tracker view

**v1** (live, `tinytune` loaded): a "BASSOON" wordmark banner (animated waveform art) top-left, a small position/jump list under it; a "TRACKER" wordmark, BPM/song-length/pattern-length/repeat spinboxes; a song/instrument list top-right; a transport row (Song/Pattern radio dot, Play, Record, File/Options/Sample Edit buttons, Mode MOD/XM, Track-count 4/8/12/16); a "Ready: …" status line with share/favorite icons; 4 track oscilloscopes (real waveform, not flat); **a per-track S/M/FX button row**; a left-docked, always-visible song browser with **Songs/Samples/Playlists tabs**, a curated demo list with per-entry format icon + author/year, transport (prev/play/next/loop/shuffle) and "Play random Mod/XM/Playlist" buttons; **a docked piano keyboard** bottom-left; the 4-column pattern grid on the right.

**v2**: menu bar; a VU-bar-style strip + an empty text field (title?); a control row (File Operations/Options/Sample Edit, Song/Pattern, Play/Record, a BPM spinbox, Mode MOD/XM); a Stopped/More-info row; editPad's Track/Pattern headers (buttons not rendering, see Screen 7); 4 track oscilloscopes (flat — no song loaded, expected); a large blank area where the pattern grid should be; a plain-text song/pattern list at the bottom with no icons or styling.

**Gaps, most to least structural:**
- No logo/wordmark art anywhere (`BASSOON`/`TRACKER` banners). Likely permanently out of scope already (no v2 skin asset — matches the same reasoning `infoBar`'s own missing favorite/share icons already recorded) — confirm, don't rebuild speculatively.
- **No per-track S/M/FX header on the classic grid** — already a known, recorded gap (`trackControl.js`, flagged since spec 059/062's own closing notes as a real, freely-buildable follow-up, never picked up).
- **The song browser is not docked in the main view at all** — in v2 it only exists behind "File Operations" (Screen 3), and even there it's a plain vertical list with no format icon, no author/year subtext, no Songs/Samples/Playlists tabs, no transport/shuffle/random buttons. This is the single largest *content-density* gap on the main screen (v1 treats browsing as an always-present dock; v2 treats it as a separate, occasional modal-like screen).
- **Piano not visible by default** — confirm real default state (see Task 6) before deciding whether to change it; v1's docked piano may just be this particular demo's own saved UI state, not a hardcoded default.
- Pattern grid area, song/pattern list: **no visible waveform/data because no demo module auto-loads** in this port yet — a data/behavior gap, not a layout one; out of scope for this plan (belongs with whatever spec decides v2's own startup behavior).

## 2. Options panel

Already covered in detail in this session before this audit started — restated for completeness. v1: swapped into the song properties section, 6 columns (VU Bars / Stereo / Screen Refresh / Frequency Table / Dropbox Existing File / MIDI-In), each a header + a compact radio-button stack + (for 3 of them) a checkbox row below; that section is ~965×175px and does not touch the pattern grid, which lives in its own, separate section. v2: `optionsPanel.yaml` authors the same content as one long vertical stack of full-width sections (~600px+ tall at 1000px width), which is why it used to show by default and push the tracker off-screen (default-show bug already fixed this session).

**Gap:** wrong layout shape (stack vs. grid) *and* wrong scoping (swapped into a shared stack instead of its own section) compound each other — fixing only the grid-vs-stack shape (Task 3) helps regardless of whether/when the section-scoping fix (Task 5) also lands.

## 3. File Operations (disk operations)

**v1**: swapped into the song properties section, 4 columns — **Action** (Load/Save, each a radio dot), **Type** (Module/Sample/Playlist, radio dot — note: v1 lets you *load* a sample or a playlist directly, not just a module), **From** (Bassoon/ModArchive/Modules.pl/Dropbox/Local, radio dot), and a **file list** on the right (scrollable, per-row format icon + size, e.g. "AMBROZIA 878K"). All 4 columns visible at once; picking a combination immediately refreshes the list.

**v2**: `fileOperationsPanel.yaml` — a Load/Save toggle row, then (Load side) a "From" row of 5 buttons (Bassoon/ModArchive/Modules.pl/Playlists/Hippo — this maps roughly to v1's own From + Type=Playlist combined into one flatter list, a deliberate v2 simplification already recorded, spec 069), then a file-list area below. In this test, the list area rendered **empty even after selecting "Bassoon"** and waiting — worth a quick, separate check (possibly just this static-serving setup's own fetch-path issue, not necessarily a real app bug; re-verify against `node v2/server.mjs` before concluding anything).

**Gaps:** column-vs-stack shape (same class as Options); v1's "Type" concept (Module/Sample/Playlist as *load* targets, not just save targets) has no v2 equivalent — this is a **functional** gap already known from the P9 history (loading a sample directly was explicitly scoped out), not new; flag but don't fold into a visual-only fix.

## 4. Sample Edit

**v1** (swapped into the pattern section): instrument name field; a **large waveform view** with LOAD/PLAY/RANGE/LOOP/STOP/MORE buttons directly under it; **4 vertical fader-style sliders side by side** (Volume/Finetune/Fadeout/Panning) to the left of a Loop/Vibrato tab strip; **two envelope editors side by side** (Volume Envelope | Panning Envelope), each with its own graph, Sustain/Loop checkboxes, Start/Length fields.

**v2**: instrument spinbox + name field; a waveform slot (empty here, no sample loaded); Volume as a **horizontal slider**; Loop-enabled checkbox; Start/Length; one row of operation buttons (Normalize/Fade In/Fade Out/Trim/Reverse/Invert, plus Create Loop/Resample); then Finetune/Panning/Fadeout/RelativeNote continuing as more horizontal sliders down the page (envelope editors presumably further below, not reached in this viewport).

**Gap:** this is the most content-dense screen in the whole app and the biggest restructuring job — v1 packs 4 vertical faders + a big waveform + 2 side-by-side envelope graphs into roughly one screen height; v2's single-column stack of horizontal sliders is several times taller. Recommend tackling this **last**, as its own dedicated spec (it isn't a quick regroup like Options).

## 5. Nibbles

**v1**: swapped into the song properties section (~790×220px at this viewport), "NIBBLES — A Tribute to FastTracker and Triton" title art on the left, a small "Ready Player 1? / START" prompt box center, an **Options/Difficulty column** on the right (Wrap/Grid checkboxes, Novice/Average/Pro/Triton radio), High/Exit buttons at the bottom of that column. The actual play grid is small and only becomes visually busy once a game is in progress.

**v2**: a full sibling of `normalMainView` (not scoped to a song-properties-sized section), the game grid spans the whole width at a fixed large size, Score/Lives/Level/Difficulty as plain stacked text labels (no box/border styling), Wrap/Grid checkboxes, Novice/Average/Pro/Triton buttons, Highscore/Exit buttons, then a full-width "Ready Player 1"/START bar at the very bottom.

**Gap:** same section-scoping root cause as Options/File Operations - Nibbles needs to be the song properties section's own alternative content, sized to that section, not a full-viewport sibling; independent of that, v2's own game grid is sized to fill the whole viewport rather than v1's fixed, compact size — worth checking whether `nibblesGrid`'s own authored size should be a fixed value instead of `width/height: fill` once it is properly scoped to its own section.

## 6. Menu bar

File/Edit/View/Help and every submenu item (including dynamic Undo/Redo labels, the nested Clear submenu, View's own six items) match v1's `menu.js` exactly, item for item, in order. **No work needed here.**

## 7. editPad (Track/Pattern clear/copy/paste)

**v1**: two compact columns, each a small header ("↓Track"/"↓Pattern") followed immediately by 3 stacked buttons (Clear/Copy/Paste), maybe 90px tall total.

**v2**: `editPad.yaml`'s own root `layout: { width: fill, height: fixed }` has **no `size:` value at all**. Only the two text headers ("Track"/"Pattern") are visible in every screenshot taken this session; none of the 6 Clear/Copy/Paste buttons ever appeared, at any screen, in any state. This looks like a straightforward, high-confidence authoring bug (a `height: fixed` with nothing to be fixed *to* should almost certainly be a declared `size:` in the 80-100px range, or `height: auto`), not a proportions question. **Verify against the compiled outline / a taller viewport before fixing**, in case it's actually rendering just below what these particular screenshots happened to catch — but given it never appeared once across ~6 different states, this is the most likely real, isolated bug in the whole audit.

## 8. Piano

Not conclusively compared this pass — clicking View → Piano produced no visible change in a 700px-tall viewport, but the panel is a **fixed 200px-tall dock** (per its own `pianoPanel.yaml`) that may simply have been pushed below the fold by everything above it, the same class of issue as Options. Re-check with a taller viewport (or after Tasks 1/3 land, since those directly affect how much vertical space is left for it) before concluding anything is actually broken here.

## 9. Row/column (multitrack) view toggle

Not compared this pass (needs a loaded demo module to show meaningful pattern content in either view, and no demo auto-loads in this environment). Revisit once main-view content is easier to populate for testing.

## Ordered small steps

Each step below is independently buildable and testable (a `computeGenericLayout` test against the real compiled `app.yaml`, the same convention every prior spec in this port used, plus a real screenshot to confirm) before moving to the next. Steps 1-8 are pure **restructuring** - they use only content v2 already has, just scoped and shaped correctly. Steps 9+ are **new content** v1 has that v2 has never built at all; each is its own, larger, separate initiative and is *not* required to unblock the steps before it.

1. **✅ Done, 2026-09-16 - Fix `editPad.yaml`'s missing button size.** Turned out to need `direction: row` (added) plus dropping the bare `height: fixed` (removed, so it auto-sizes to its own real content) - and, while verifying against a real screenshot rather than trusting the compiled-outline check alone, surfaced two more real, confirmed, system-wide bugs neither test convention this project already uses would have caught on its own:
   - **`compiler/emit.js#layoutLiteral()` never emitted `layout.direction` for any node, ever** - only `width`/`height`/`resizable` were ever written into a generated `app/ui/*.js` file's own `layout: {...}` literal. Confirmed system-wide, not editPad-specific, by grepping every emitted file: exactly one `direction` appeared anywhere in `app/ui/`, and only inside a `breakpoints` override (serialized as a raw JSON blob through a different path). Every authored `direction:` in every component YAML in the whole application had been silently dropped from the real generated app since whenever each was authored - the compiled dev-time outline (`app-outline.json`) had it correctly the whole time, which is exactly why every `computeGenericLayout`-against-the-compiled-outline test in this whole test suite (dozens of them) never caught it: that check never goes through `emit.js` at all.
   - **`runtime/components.js#component()` independently dropped `layout.direction` too**, in the plain-object reconstruction every generated file's own `component("panel", {...})` call runs through at load time - the same one-line omission, in a second place, affecting hand-written glue and generated code alike. Fixing `emit.js` alone would not have been enough; both needed the identical one-line addition.
   - **`normalMainView` itself was missing `height: fill`** (`app.yaml`, no height at all authored - defaulting to auto). This meant none of its own `height: fill` descendants (`patternViewPanel`, and everything nested under it) ever received real, viewport-relative space - confirmed directly: varying the test viewport's own height from 300 to 2000px changed nothing at all about `normalMainView`'s own computed height, proving it was never actually anchored to the real available space. Adding the missing `height: fill` fixed this at the root, and, as a direct, confirmed side effect, also resolved the two `patternViewScreen.test.js` failures editPad's own fix had exposed (`patternGridPanel`/`multitrackViewPanel` computing to zero height) - no test assertion needed to be weakened; the real fix made them correctly pass again.

   One clearly deliberate, out-of-scope-for-this-step discovery, confirmed but not chased: v1's Options panel now renders noticeably more compactly than before this step (each settings category as one row, not stacked full-width sections) purely as a side effect of the `direction` fix above - `optionsPanel.yaml`'s own per-category rows had *already* authored `direction: row`, silently broken the same way editPad's was. This is a real, welcome improvement, but the panel still isn't v1's real 6-column grid - that stays Step 7's own job.

   `tests/nibblesMainView.test.js`'s own "editPad's authored height: fixed is unaffected by nesting depth" assertion no longer had a valid example (editPad is no longer `height: fixed`) - substituted `main.top.volumemeter` (a genuinely fixed, real-numbered height, spec 054), which proves the same underlying property. Full suite: 958/958 passing. `node compiler/generate.js` (12 warnings, unchanged) and `node build.mjs app`/`dist` (103 loose ends, unchanged) both confirmed - none of these three fixes touch any authored command or add any new one.
2. **✅ Done, 2026-09-16 - Re-verify the File Operations empty-list finding.** It was not a static-serving artifact - it was a real, confirmed bug, live in the browser, with a console error the original audit pass never captured (it only screenshotted): `store: unknown field "rows.main.fileOperationsPanel.browser"`, thrown from `domain/diskOperations/index.js#publish()`'s own `app.state.set(...)` call. Two real, separate defects, both found by tracing the actual thrown error rather than guessing:
   - **`domain/diskOperations/index.js`'s own `BROWSER_ROWS_FIELD` constant hardcoded a stale id**, `"main.fileOperationsPanel.browser"` - one level shallower than the real, current node id, `"main.normalMainView.fileOperationsPanel.browser"` (confirmed directly against the compiled outline, not assumed). Fixed the constant; `tests/diskOperations.test.js`'s own 10 hardcoded occurrences of the same stale string needed the identical update (its own fake `app.state` never validates field names, so it had never caught this either).
   - **Fixing the id alone did not fix the crash** - the corrected field name was *still* "unknown" to the real store. Root cause, one level deeper: `compiler/emit.js`'s own state-field derivation switch (the one that seeds `state.js` with every field a capability might ever write to) has a case for every other specialized behavior - `list`, `disclose`, `tabs`, `collapsible`, `digitEntry` - **but never had one for `fileBrowser`'s own `"rowList"` behavior**. Neither its `rows.<id>` field (this type's own equivalent of a list's selection field) nor its `scroll.<id>` field (which it reuses from `listController.js` unchanged) was ever registered in any generated `state.js`, for any fileBrowser node, since the type was first built (spec 035/036). `runtime/store.js#set()`/`#subscribe()` both strictly reject any field not pre-seeded this way - confirmed by reading the store itself, not assumed - so *every* `domain/diskOperations#publish()` call, for *every* one of its five targets (Bassoon/ModArchive/Modules.pl/Playlists/Hippo), had been throwing in the real generated application the whole time. Invisible until this session's live-browser verification because every existing test's own fake `app.state` stand-in (a plain, non-validating `Map`) never rejects an unknown field the way the real store does - a real, confirmed gap in this whole port's own test convention, not just this one screen.
   - Fixed by adding a `behavior === "rowList"` case to `emit.js`, registering both fields (`[]` and `0` respectively), matching the shape `list`'s own two-field case already has.

   Verified live: Bassoon's own curated module list, and spec 069's own Playlists list (DemoScene 2023-2026, DSR 2024, Chippies, RAW diskmag, each with a real track count), both now populate correctly with no console errors. Full suite: 958/958 passing. `node compiler/generate.js` (12 warnings, unchanged) and `node build.mjs app`/`dist` (103 loose ends, unchanged; `state.js` now lists two more real fields) both confirmed.
3. **✅ Done, 2026-09-16 - Give the pattern section a real, bounded top-level wrapper.** A new `patternSection` panel (`width: fill, height: fill, direction: column`), nested inside `normalMainView`'s own existing content list, in place of `editPad`/`patternViewPanel`'s own former flat positions there; `infoBar` moved into it too, out of being a top-level sibling of `controlBar` - matching v1's own real child order exactly (`editPanel`, then `infoPanel`, then `visualiser`/`patternView`, all owned directly by `_patternPanel`). `fileOperationsPanel`/`optionsPanel`/`sampleEditPanel`/`songPatternList`/`songProperties` are untouched, still flat siblings of `patternSection` inside `normalMainView` - deliberately deferred to steps 4-6, exactly as planned.

The one test that had asserted the old ("always present") behavior (`tests/nibblesMainView.test.js`) was split in two: the menu-bar/control-bar half kept its own "present either way" claim (still true), and a new, separate test now asserts infoBar's own correct presence/absence on each side of the Nibbles toggle.

   Verified directly against the compiled outline (`patternSection`, `editPad`, `infoBar`, `patternViewPanel` all present with real, non-zero rects, in the right order) and live in the browser: the "STOPPED / MORE INFO" status row now renders between the edit pad and the scopes/pattern grid, exactly where v1 puts it, instead of its old position directly under the control bar.
