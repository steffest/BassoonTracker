# 023 — menu bar prerequisites

Date: 2026-09-11. Kind: feature. Status: specified. Implements the prerequisite spec 022 named for the last of P5's six screens: "the **menu bar** needs `menu` itself promoted from a placeholder first (its `subItems` nesting is exactly `submenu`'s own shape from spec 020, and promoting `menu`/`submenu` together was already flagged in spec 020 as a later spec's call)." This spec is that later spec - it promotes `menu`, not the menu bar screen itself, which becomes possible once this lands.

## Purpose

`script/src/ui/components/menu.js` (v1's `Menu`) is a row of top-level items, each showing a label; clicking one opens its own `Submenu` (already ported, spec 020) positioned below it, and clicking a different item while one is open switches which submenu shows. `script/src/ui/app/menu.js` (the real app's menu bar) nests this two and three levels deep - File/Edit/View/Help across the top, and inside Edit, a "Clear" item that is itself a nested flyout (Clear Track/Pattern/Song/Instruments).

The key finding, from reading both files rather than assuming: v1 keeps a menu item's clickable button and its opened `Submenu` as two separate objects (`item.subMenu`, added as a sibling in the DOM tree, not a child of the button). Authoring a menu item directly as a `submenu`-typed node - the obvious first idea - does not work for that reason: a `submenu` is `layer: "overlay"`, which spec 013 already excludes from in-flow layout, so it would never get a row position to show "File" at, closed or open. The fix mirrors `dropdown`'s own synthesis (spec 020) exactly, in the opposite direction: wrap the authored `submenu` node in a new, plain, in-flow trigger, and give that trigger the original node as its synthesized child.

## User stories and acceptance

- **MENU-001 — A menu's top-level items each open their own submenu:** As an author, `type: menu, items: [{label: File, type: submenu, items: [...]}, ...]` compiles and mounts; clicking "File" opens its submenu anchored below it; clicking one of its own items runs that item's command and closes the submenu. Acceptance: the compiled tree has real, recursively-nested nodes (verified by a compiler test); at mount time each `submenu`-typed item is wrapped into a `menuTrigger` (verified directly against `runtime/overlaySynthesis.js`).
- **MENU-002 — Nesting works to arbitrary depth:** As an author, an item inside an open submenu that is itself `type: submenu` (v1's "Clear" under "Edit") is wrapped exactly the same way, anchored to the *right* of its own row rather than below, since it is inside a column, not a row. Acceptance: a doubly-nested authoring case compiles and synthesizes correctly (both verified directly).
- **MENU-003 — Only one flyout is open at a time within a menu or a submenu:** As a user, opening a different top-level item's submenu closes whichever one was already open; the same is true one level down, for a submenu's own nested items. Acceptance: gated on a new, generic `exclusiveOverlayChildren` registry fact set on `menu` and `submenu`; a plain `dropdown` (whose parent never sets this fact) is unaffected.
- **MENU-004 — No regressions:** Acceptance: the unit suite passes; `dropdown`'s own "disclose" behavior, unaffected by menuTrigger sharing it, keeps anchoring "below" (its own hardcoded default, never overridden by the new per-instance `popupEdge` property menuTrigger alone sets); submenu's pre-023 behavior (plain command items, disabled items, hover preselection) is unchanged for any item that is not itself `type: submenu`.

## Non-functional requirements

Every new mechanism is gated on a registry fact (`wrapsFlyoutItems`, `isMenuFlyout`, `exclusiveOverlayChildren`) or an instance property (`popupEdge`, following `node.vertical`/`node.dialogResult`'s own precedent), never a type name, matching spec 009's rule and its enforced scanning test. `compiler/convert.js` needed no change at all: `menu`'s and `submenu`'s contracts are both the same bare `{ childrenIn: "items" }` shape `listbox`/`dropdown` already use, so nested authoring (an item whose own type is `submenu`, with its own `items:`) already compiles correctly through the existing, generic per-node conversion path.

## Scope boundaries

In scope: promoting `menu` to `implemented: true`; a new synthesized-only `menuTrigger` type; the wrapping mechanism in `runtime/overlaySynthesis.js`; the small, generic extensions to `renderers/canvas/mountGeneric.js`'s existing "disclose" activation (per-instance anchor edge, exclusive sibling-closing); a `menuTrigger` draw kind; `app.yaml`'s own placeholder menu items reshaped into a real (if still small) nested example, so the existing action1/action2 compiler-testing fixture keeps demonstrating what it always has (an unresolved action reference), now from inside a real menu structure instead of the old itemActions-only shape.

Out of scope, each recorded rather than folded in:

- **The menu bar screen itself** (`app/menu.js`'s real File/Edit/View/Help/Help content, the vumeter, the key/midi indicators) - this spec is the prerequisite spec 022 named, not the screen; authoring it is later work now that this unblocks it.
- **Hover-switches-open-submenu-while-one-is-already-open.** v1's real UX: moving the pointer across the top bar while a submenu is open switches which one shows, with no extra click. This spec's mechanism only switches on click; continuous hover-driven switching would need the pointer router to feed a live per-item hover position to a container the way spec 021's tab strip does, which is a real piece of additional mechanism, not a byproduct of promoting `menu`.
- **Two-click switching between top-level items while one is open.** A consequence of spec 013's own pointer-down modal gate (clicking outside the open modal dismisses it and swallows that same click, requiring a second click to open the next one) that already existed for `dropdown` before this spec and is not new to menus; recorded rather than silently accepted.
- **Arrow-key navigation, Enter-to-execute the highlighted item.** Matches `listbox`/`submenu`'s own already-recorded gap (spec 019/020): Tab and Escape work through the existing focus/modal machinery; arrow keys do not.
- Browser verification: not performed, for the same reason specs 019-022 recorded none - this environment still has no Playwright/Chromium install (checked again for this spec). Verified instead by the unit suite (`runtime/overlaySynthesis.js`'s wrapping is pure and directly testable) and a compiler-level test of real nested YAML authoring; the renderer-level activation logic (`mountGeneric.js`'s "disclose" branch) is reasoned through by hand in design.md rather than exercised, since it needs a live DOM mount this environment cannot give it.
