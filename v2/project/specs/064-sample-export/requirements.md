# 064 — Sample export (WAV/RAW/XI)

Date: 2026-09-15. Kind: feature. Status: specified. Continues package **P9** (persistence, providers, file operations) of the [port roadmap](../010-port-roadmap/requirements.md), following spec 063 (random song). Picks up the gap spec 037/038 each deliberately left open: "sample export (WAV/RAW), ... a save/export screen ... remain unallocated."

## Purpose

Module export (specs 037/038) covers the two module formats v2 loads. v1 also exports the *current instrument's sample* on its own, in three shapes reachable from the same save panel: an XI (Extended Instrument) file, a WAV (8- or 16-bit RIFF PCM), or a headerless RAW 8-bit file. Spec 038 deliberately factored `fasttracker.js`'s instrument/sample-writing block into a shared, unexported `writeInstrumentSamples()` helper "ready for a later sample-export spec's own `writeXI` port to reuse" - this is that spec.

## What v1 actually does (read from source, not assumed)

- **`script/src/ui/diskOp_Save.js`** (the disk-operations save panel) offers four sample formats when `mainFileType === FILETYPE.sample`: "wav 16 bit", "wav 8 bit" (the default), "RAW 8 bit" and "xi" (72-137). The XI branch (84-95) calls `FastTracker().writeXI(instrumentIndex, next)` directly; the other three (97-130) read `Tracker.getCurrentInstrument().sample` and either build a RAW buffer inline or call `encodeRIFFsample(sample.data, bits)`.
- **`FastTracker().writeXI`** (`script/src/fileformats/fasttracker.js:680-809`, already read in full for spec 038's own research) writes a fixed 298-byte header (signature, 22-byte name, tracker-name block, format version `0x0102`, a 96-entry sample-number-for-notes table, both envelopes' 12 points each, envelope counts/sustain/loop bytes, envelope types, vibrato, fadeout, 22 reserved bytes, sample count) for **one instrument**, then the exact same per-sample header/delta-encoded-data block `write()`'s own `writeInstrumentSamples()` (spec 038, `domain/moduleExport/fasttracker.js`) already ports - confirmed field-for-field by diffing both blocks side by side, not assumed from the shared name alone.
- **`encodeRIFFsample`** (`script/src/audio/riffWave.js:44-126`) writes a 44-byte RIFF/WAVE/fmt/data header (mono, a hardcoded 8000Hz sample rate - the file's own comment reads `"how can we know this from raw samples?"`, since a v1 in-memory sample carries no rate of its own) followed by 8-bit unsigned (`round(x*127.5+127.5)`) or 16-bit signed (`round(x*32767)`) PCM, with a trailing zero pad byte if the sample count is odd.
- **The inline RAW 8-bit branch** (`diskOp_Save.js:101-113`) has a real, confirmed defect, not a stylistic quirk: it allocates `sample.length` bytes, writes two zero bytes first (`file.clear(2)`), then writes only `sample.length - 2` data bytes (`for (i = 0; i < sample.length-2; i++)`). The result is a file of the promised length that starts with two spurious zero bytes and silently drops the sample's own last two data points - not a header any RAW/`.sample` reader expects, and not something intentionally trimmed either (the comment above it, `"sample length is in word"`, describes a rationale for a 2-byte adjustment that the code does not actually implement correctly: it neither doubles the length for a word-sized format nor accounts for the dropped samples anywhere else). Confirmed by tracing the loop bounds and the preceding `clear(2)` together, not from the comment alone.

## Decisions and assumptions

- **The RAW 8-bit defect is fixed, not ported.** Every other byte-for-byte port in this roadmap preserves v1's real behavior even when odd (e.g. spec 043's asymmetric snap-to-zero); this one is different in kind, matching the bar spec 034/037/040/043 already used for "fix, don't preserve" (hippo.js's unguarded crash, a division-by-zero in `adjustVolume`, a dead undo field, a hardcoded wrong extension): a RAW export that silently loses data and prepends garbage bytes has no plausible reader relying on that shape, and no test or fixture in this repository exercises it either. `domain/moduleExport/sample.js#writeRaw` writes exactly `sampleData.length` bytes, one per sample point, no header.
- **`writeXI` lives in `domain/moduleExport/fasttracker.js`**, alongside `write()` and the `writeInstrumentSamples()` helper it already reuses - not a new file, since it is one function sharing that file's existing helper and imports, exactly as spec 038's own note anticipated.
- **WAV and RAW get a new sibling module, `domain/moduleExport/sample.js`**, since neither format has anything to do with a whole module (song/pattern/instrument-table) the way `protracker.js`/`fasttracker.js` do - a sample encoder operates on a plain `{data, bits}` pair, not `Tracker` directly, so (unlike every other writer in this folder) it takes its input as parameters rather than reading the engine singleton itself. `writeXI`, `writeMod` and `writeXm` all still read `Tracker` directly per this folder's own documented exception, since an XI file is instrument-shaped and genuinely needs `Tracker.getInstrument(index)`.
- **A capability is added (`exportSample`), but not wired to any YAML/`capabilities.js` entry.** `node compiler/generate.js` was run before writing this spec and confirmed no authored action anywhere references sample export (12 warnings, none naming it) - unlike module export, which reused an already-authored, previously-unresolved "Save" menu item, there is no existing save/export screen or menu entry for a sample at all yet in v2. Building one is design.md's own separately-recorded, still-unallocated "a save/export screen" item; this spec follows the same "mechanism first" split every specialized surface and every prior P9 slice already used (specs 033→034→035→036, 040→041→042, 043→044→045, 051→052→053), leaving the capability real, tested and ready to wire the moment that screen exists.
- **The current instrument's sample rate is not tracked anywhere in this port** (confirmed by grep - `domain/playback/engine/models/sample.js` has no rate field, matching v1's own `Sample` model), so `writeWav` hardcodes 8000Hz exactly as v1 does, not a v2 regression.

## User stories and acceptance

- **SEXP-001 — XI export re-serializes one instrument exactly.** `domain/moduleExport/fasttracker.js#writeXI(instrumentIndex)` produces bytes that a test-local parser (mirroring `script/src/fileformats/fasttracker.js#loadXI`'s own field layout - v2's ported engine never gained an XI reader, since loading one was never in this port's scope) decodes back to the same name, sample count, envelope points/counts/sustain/loop settings, vibrato and per-sample volume/finetune/panning/relative-note/loop metadata and sample data as the source instrument, for a real fixture instrument with a real envelope (`sin.xm`'s own instrument 1). Acceptance: a round-trip unit test.
- **SEXP-002 — WAV export produces a valid, readable RIFF file at both bit depths.** `domain/moduleExport/sample.js#writeWav(data, bits)` produces a byte-exact RIFF/WAVE/fmt/data header (format 1/PCM, 1 channel, 8000Hz, the correct byte rate/block align/bits-per-sample for each depth) and correctly quantized, decodable sample data for both `bits: 8` and `bits: 16`, including the odd-length trailing pad byte. Acceptance: a unit test parsing the header fields directly and decoding the data back within the depth's own known rounding tolerance.
- **SEXP-003 — RAW export writes every sample, none dropped, no leading pad.** `domain/moduleExport/sample.js#writeRaw(data)` produces a buffer of exactly `data.length` bytes, decodable back to the original data (within 8-bit rounding tolerance) with no offset. Acceptance: a unit test exercising the exact defect found above and confirming it does not reproduce.
- **SEXP-004 — The capability is real and ready to wire.** `domain/moduleExport/index.js#exportSample(app, format)` (`format` one of `"xi"`, `"wav8"`, `"wav16"`, `"raw8"`) reads the live current instrument/sample from `Tracker`, dispatches to the right writer, and triggers a browser download exactly like `exportModule` already does - refactored to share one small `downloadBuffer()` helper rather than duplicating the Blob/anchor-click dance a second time. Acceptance: a unit test with a stubbed `document`/`Blob`/`URL` (matching however `exportModule`'s own existing test, if any, already stubs the DOM - confirmed by reading `tests/moduleExport.test.js` before writing a new one) confirming the right writer is called for each format and a download is triggered.
- **SEXP-005 — No regressions.** Full unit suite passes; `node compiler/generate.js` and `node build.mjs app`/`dist` succeed with no new warnings or loose ends (no YAML/`capabilities.js` change); MOD/XM export (specs 037/038) are unaffected by the `downloadBuffer()` refactor.

## Non-functional requirements

- Headless verification only (no browser-automation dependency in this environment, the same recorded reason every spec since 019 has given).
- No YAML/compiler/`capabilities.js` change - see the decision above.

## Scope boundaries

In scope: `domain/moduleExport/fasttracker.js#writeXI`, new `domain/moduleExport/sample.js` (`writeWav`, `writeRaw`), `domain/moduleExport/index.js#exportSample` and its `downloadBuffer()` refactor, and tests for all of the above.

Out of scope, recorded rather than silently dropped:

- **Playlist export (PLS/M3U/JSON) and MP3 export** - unchanged from spec 037/038's own scope boundaries; MP3 in particular needs its own research pass, since spec 033 already found v1's own "export" round-trips through a server-side `lame.exe` rather than the vendored-encoder shape open decision 5 assumed - a real, recorded discrepancy the roadmap has not yet reconciled.
- **A save/export screen** - `exportSample` has nowhere to be triggered from yet; a picker between targets/formats (module, sample, playlist) is design.md's own separately-recorded later item, the same split every other specialized surface in this roadmap already used.
- **Dropbox as a save target** - the browser's own download (`Blob`/`URL.createObjectURL`/a synthetic `<a>` click) is the only target here, matching spec 037/038's own scope boundary exactly; v1's own `saveTarget === "dropbox"` branches are not ported.
- **Reading a `.xi` file back into v2** - not in this port's scope (v2 loads `.mod`/`.xm` only); SEXP-001's test-local parser exists only to verify this spec's own writer, not as new production code.
