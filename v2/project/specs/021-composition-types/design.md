# 021 — Design

## The one new mechanism: a container whose children are conditionally absent from layout

Spec 020's real contribution was making an *overlay's* presence a runtime fact instead of a static one. This spec needs the same idea for two *in-flow* containers: a tabPanel shows exactly one child's subtree, and a collapsePanel shows all of its children or none of them. Neither is an overlay - both stay exactly where they are laid out, unlike a popup or a dialog - so spec 020's `overlayOpen` mechanism does not apply directly, but the underlying idea generalizes: `runtime/genericLayout.js`'s `layoutNode()` already treats "not laid out at all" (no rect, no clip, and therefore no draw and no hit) as the correct effect for something that is not currently shown; this spec reuses exactly that effect for two more, non-overlay cases.

Two new `computeGenericLayout` options, both following `scrollOffset`/`overlayOpen`'s own shape (a pure callback the caller supplies):

- `activeTab(node) => number` - which child index of a `tabHeader`-declaring node is showing. Only that child is laid out; every other child gets no rect at all, via a new `layoutTabs()` alongside `layoutRow`/`layoutColumn`/`layoutViewport`.
- `collapsed(node) => boolean` - whether a `collapsible`-declaring node's children are laid out at all. When true, `layoutNode()` treats the node as if it had none, exactly the one-line change `isOverlay`'s own gate already makes for a closed overlay.

Both default to `() => 0` / `() => false` respectively, so a caller that does not pass them (every test written before this spec) is unaffected.

## tabPanel

`tabHeader: { height: 24 }` is a new per-type registry fact (parallel to `clips`, `modal`, `layer`): a container declaring it gets the tab-switching layout above, and the number is how tall the reserved header strip is - read by both `genericLayout.js` (to size the content area under it) and the `tabPanel` draw kind (to draw the row of tab buttons in it), so the two can never disagree about where the header ends. `items` (the existing bare `{ childrenIn: "items" }` shape, unchanged from spec 016) are ordinary child nodes, exactly as `listbox`'s are: each one's own `label` is what the tab button shows, and its own children are what appears when it is the active tab.

Tab-switching reuses `runtime/listController.js`'s existing `createListController` unchanged, registered under a new behavior name `"tabs"` (spec 020 already established this pattern for `disclose`/`flyout`: a second name for an existing factory when the *meaning* of activating it differs, not the *shape* of the gesture). A press-and-release on a resolved tab index is exactly `listController`'s own "a plain click on an item selects it" case; nothing about scrolling or dragging is exercised because `renderers/canvas/mountGeneric.js`'s new `tabIndexAt(node, point)` (parallel to the existing `itemIndexAt`) supplies `scrollable: false`, so the wheel/drag paths never fire. `tabIndexAt` does not reuse `itemIndexAt`, because a tab button is not a real per-child rect the way a listbox row is - only the *active* item ever has one, and every other item's "button" is a synthetic strip position the draw kind paints, not a laid-out node. `tabIndexAt` instead divides the tabPanel's own rect's header strip into `items.length` equal-width slots (see "what this deliberately does not do" below for why not variable widths) and reports which one a point falls in, `null` outside the header row entirely.

Because the controller's result is a plain `{ changed: true, value: index }` - identical in shape to a slider's or a listbox's - `renderers/canvas/mountGeneric.js`'s existing `feed()` branch (`if (result.changed && typeof result.value === "number") applyValue(node, result.value)`) handles a tab switch with no new code there at all. `applyValue` writes the field, dispatches `"change"`, and re-lays out - the last of which is what actually swaps which child is visible, through the new `activeTab` layout option above.

## collapsePanel

`collapsible: true` is the new per-type registry fact. Its own click is a plain button activation (`behavior: "collapsible"`, a third alias of `createButtonController` alongside spec 020's `disclose`), and `feed()` gains one small, behavior-name-gated branch: activating a `"collapsible"`-behavior control writes the *negation* of its own bound field through the same `applyValue()` every value-like control already uses, rather than dispatching a command - the same shape spec 020's dropdown-toggle branch already has, reusing `valueFieldOf()`'s existing resolution order (authored `field:`, then a bound `change` action's mock field, then a name derived from the node's id) so a collapsePanel's state lives in exactly the place every other control's does: inspectable in the State gallery, and persisted in a generated application's real store the same way a checkbox's or a slider's is.

The field is boolean and named for what it means (`collapsed`, true hides the content), not for whether the container is "on": a fresh mount with an unwritten field reads as `false` (falsy), which is "not collapsed" - content shows by default, matching v1's own always-showing collapsePanel and meaning no existing tree changes behaviour by this type merely existing in the registry.

## buttonGroup

No new mechanism at all. Promoted to `implemented: true` with its container corrected from spec 016's guessed `{ childrenIn: "items", childType: "button" }` to the bare `{ childrenIn: "items" }` `listbox`/`dropdown`/`submenu` already use (see requirements.md for why `childType` was the wrong shape - it is `radioGroup`'s own "the group dispatches, not the item" contract, and a button group's whole point is the opposite of that). Each item goes through the same full per-node conversion (`compiler/convert.js`'s `convertContentItem`) any panel's `content:` item already does, so a `- type: button, label: Play, actions: transport.toggle` item is neither more nor less capable inside a `buttonGroup` than inside a `panel`. The only two things `buttonGroup` actually contributes over authoring a `panel` are its declared `direction: "row"` default and drawing nothing of its own (`draw: "none"`, the same kind `radioGroup` already uses for the same reason: its children draw themselves) - a way to say "these buttons belong together" without asking for panel chrome around them.

## Draw kinds

- **`tabPanel`**: divides its own rect's top `tabHeader.height` pixels into `items.length` equal slots and, for each, fills a plain rect (a different fill for the active index, from `state.activeIndex`, which `visualStateOf()`'s new `"tabs"` branch resolves from the bound field the same way listbox's `selectedItemRect` is resolved) and writes that item's own label centred in it. The content area below draws nothing itself - the active item's own children paint through the ordinary per-node pass, exactly as `modalDialog`'s synthesized children already do (spec 020).
- **`collapsePanel`**: a plain background fill over its own full rect (`styled: false`, the same "no artwork exists for this yet" choice `knob`/`listbox`/`submenu`/`dropdownPopup` already made) and its own `label`, left-aligned in the header strip, plus a small `▾`/`▸` glyph reflecting `state.collapsed` (resolved by `visualStateOf()`'s new `"collapsible"` branch) so the affordance is visible even before a real skin ever draws one.

`buttonGroup` needs no new draw kind: it keeps the existing `"none"` kind (draws nothing; its children draw themselves), already used by `radioGroup` for the identical reason.

## What this deliberately does not do

- **No variable-width tab buttons sized to each label's own text.** v1 measures each tab button from its own configured width; this spec divides the header strip evenly instead. A tab button is a synthetic strip position, not a real laid-out child node (only the active item ever gets one), so giving it a "natural" width would mean measuring an item's label from inside `tabIndexAt`'s pure-geometry function, which has no font access - the renderer's other per-pixel text measurements (`charIndexAt`) already live where the font does, in `mountGeneric.js`'s own drawing closures, not in a pure geometry helper. Equal-width tabs are simpler, honest about the roadmap's own "reduced visual fidelity" decision (spec 010's open decision 1), and correct for every acceptance criterion this spec states.
- **No per-tab or per-row hover highlighting** for either type, matching `listbox`'s own already-recorded scope cut for the identical reason (a second piece of geometry tracking beyond what is already resolved).
- **No fix for `measureIntrinsic()`'s "auto" imprecision** (see requirements.md's scope boundaries) - `runtime/genericLayout.js`'s intrinsic-sizing pass has no access to `activeTab`/`collapsed`, so an author who gives either type `layout: { height: auto }` gets a box sized to the sum of *all* its children, not just the ones actually shown. Consequence-free today (nothing authors either type at all yet); recorded rather than silently accepted.
- **No authored use in `app.yaml`.** Verified against hand-built trees and the unit suite, exactly as spec 020 was.
