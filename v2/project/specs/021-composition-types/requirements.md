# 021 — tabPanel, collapsePanel, buttonGroup

Date: 2026-09-11. Kind: feature. Status: specified. Implements the fifth implementing cluster of package **P5** of spec [010](../010-port-roadmap/requirements.md), the port roadmap, following spec [020](../020-overlay-controls/requirements.md) (the overlay-dependent trio). Spec 016's design.md calls this last implementing cluster "composition": three ways of arranging a fixed set of children, none of them needing the overlay/modal mechanism the previous cluster built on.

## Purpose

`tabPanel`, `collapsePanel` and `buttonGroup` are the last three catalogue entries package P5 declared without drawing (spec 016). Once these are implemented, P5's own remaining work is "the screens, authored last" - the menu bar, the control panel, the options panel, the info bar, the edit pad, the song and pattern lists - which needs every type in the catalogue to exist first.

Two of the three needed a real decision spec 016 deliberately left open, having read the v1 source rather than guessed:

- **`tabPanel`** (`script/src/ui/components/tabPanel.js`, 137 lines): v1 shows one child panel at a time behind a row of tab buttons, but hard-codes a footer strip and `Layout.trackControlHeight`, a tracker-specific constant. Neither belongs in a generic catalogue type; this spec's job is separating "which child is showing" (generic) from "the tracker's own tab bar" (an authored screen's job, later).
- **`collapsePanel`** (`script/src/ui/components/collapsePanel.js`, 33 lines): a labelled header over a background - nothing in v1's version actually collapses anything. Read again for this spec: still true. This spec decides it should, since a header a user cannot click is a worse-than-decorative label, and the mechanism spec 020 built for showing/hiding an overlay generalizes cheaply to showing/hiding an in-flow container's content too.
- **`buttonGroup`** (no v1 source): spec 016 guessed `childType: "button"`, mirroring `radioGroup`/`radioItem`. Read again against what `radioGroup`'s own `childType` shape actually does (`compiler/convert.js`'s `convertItems()`): it forces every item to one type and gives the *group*, not the item, its own `actions:` binding - exactly `radioGroup`'s own exclusive-choice shape, and exactly wrong for "independent buttons that each dispatch their own command." This spec drops `childType` in favour of the same bare `{ childrenIn: "items" }` shape `listbox`/`dropdown`/`submenu` already use, so each button in the group is a real, independent node with its own `actions:`.

## User stories and acceptance

- **CMP-001 — A tabPanel shows one child at a time, switched by a row of tab buttons:** As an author, `type: tabPanel, items: [...]` draws a strip of tab buttons, one per item, using each item's own `label`; clicking one shows that item's own children and hides every other item's, writing the selected index to the bound `field` (falling back to a derived name, exactly as `listbox`'s does). Acceptance: exactly one item's subtree has a rect/is drawn/is hit-testable at a time; clicking a tab switches which one; an out-of-range or absent field value falls back to index 0.
- **CMP-002 — A collapsePanel's header toggles whether its content is shown:** As an author, `type: collapsePanel, label: "Options"` draws a header with its label and a plain background; clicking the header toggles a bound boolean field (falling back to a derived name); while collapsed, its children have no rect and are neither drawn nor hit-testable. Acceptance: click toggles the state; the field is inspectable (State gallery, a generated app's real store) exactly like any other control's; collapsed is the *not*-default (a fresh mount shows content, matching v1's own always-showing behaviour when the field has never been written).
- **CMP-003 — A buttonGroup lays out independent buttons with no exclusivity:** As an author, `type: buttonGroup, items: [...]` is a row of ordinary child nodes (typically `button`), each keeping its own `actions:`/`rule:`/every other property exactly as it would inside a plain panel's `content:` - buttonGroup adds no selection state and no artwork of its own. Acceptance: two buttons in the same group dispatch their own, independent commands; nothing about clicking one affects the other; an author who reaches for `buttonGroup` instead of `panel` gets a row of authored buttons with no border/background rather than a mistake.
- **CMP-004 — No regressions:** Acceptance: the unit suite passes; every earlier interactive type's layout, click/drag/wheel/keyboard routing, and spec 020's overlay mechanism are unchanged for a tree that uses none of the three new types.

## Non-functional requirements

No component type is checked by name outside `runtime/componentTypes.js`, `runtime/skinModel.js` and `renderers/canvas/drawKinds.js` (spec 009's rule, enforced by `componentTypes.test.js`'s scanning test). tabPanel's tab-switch and collapsePanel's toggle are gated on registry facts (`entry.tabHeader`, `entry.collapsible`) and behavior names (`"tabs"`, `"collapsible"`), never on `node.type === "..."`, the same discipline spec 020 held to.

## Scope boundaries

In scope: `runtime/genericLayout.js`'s two small, targeted additions (only the active tab's subtree is laid out; a collapsed container's children are not laid out at all - both "absent from layout" in exactly the sense a closed overlay already is, spec 020); promoting all three to `implemented: true` with final contracts; draw kinds for `tabPanel` and `collapsePanel` (`buttonGroup` reuses the existing `"none"` kind unchanged); `compiler/emit.js` state-field seeding for `tabs`/`collapsible` behaviors.

Out of scope: the footer strip and tracker-specific layout constant v1's `tabPanel` hard-codes (an authored screen's concern, not this generic type's); per-tab hover highlighting (matching `listbox`'s own already-recorded "the selected row's tint is implemented, hover's is not"); variable tab-button widths sized to each label's own text (equal-width tabs only - visual fidelity was already deprioritized by spec 010's decision 1, and computing per-label pixel widths for a *header row that is not a real laid-out child* is exactly the kind of coordinate-inventing this roadmap's screens are meant to avoid); nested collapse/tab state persisted anywhere but the bound field; an `"auto"`-sized tabPanel or collapsePanel measuring only its *active*/*expanded* content rather than the sum of all its children (a known, explicitly recorded imprecision - nothing authors either type with `layout: auto` yet, so it is consequence-free today; fixing it needs `runtime/genericLayout.js`'s `measureIntrinsic()` to know which child is active/whether a node is collapsed, which today it cannot without also being handed the layout options object every one of its many call sites would need threaded through); any authored use in `app.yaml` (nothing currently authors any of the three). Browser verification: not performed, for the same reason specs 019/020 recorded none - this environment still has no Playwright/Chromium install (checked again for this spec).
