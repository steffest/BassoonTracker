# 040 — Sample processing operations

Date: 2026-09-13. Kind: feature. Status: specified. Continues package **P10** (features and the plugin path) of the [port roadmap](../010-port-roadmap/requirements.md), following spec 039 (the feature registry). P10's own first named tenant, "the sample editor," starts here - the smallest, most self-contained real slice of it, not the whole plugin at once.

## Purpose

A dedicated research pass read `script/plugins/sampleeditor/{sampleEditor,sampleView,waveform,sampleProcessing,loopCreator,resamplePanel,hissReductionPanel}.js` in full (~4,300 lines total) before scoping anything. That reading, plus independent tracing of `domain/song/editHistory.js` and `script/src/ui/stateManager.js#createSampleUndo`/its own undo/redo dispatch, found the plugin splits cleanly into pieces of very different size and portability - and found that a seam for exactly this spec was already planted, on purpose, two specs ago.

## What v1 actually does (read from source, not assumed)

- **`script/plugins/sampleeditor/sampleProcessing.js` (182 lines) is the single most directly portable file in the whole plugin**: four operations (`adjustVolume`, `trim`, `reverse`, `invert`), each pure array math over an injected `context` with no DOM, no globals beyond undo bookkeeping. `adjustVolume(amount)` takes `"max"` (normalize to unity peak, only scaling up, never down), `"fadein"`/`"fadeout"` (a linear ramp across the whole selection), or a signed percentage (positive boosts through a soft-knee compressor above 0.9 peak, `getSoftClippedVolume`/`boostVolumeSoftClip`, `:8-38`, to avoid harsh clipping; negative is a plain scale-and-clamp). `trim()` strips leading/trailing near-silence (below one 8-bit quantization step, `1/128`), stops at the loop's own end point so a looped tail is never truncated, and enforces an even final length (MOD/XM word alignment) - genuinely careful, not naive. `reverse()`/`invert()` share one `applyRangeTransform` helper that already does undo bookkeeping generically.
- **The `context` interface these four operations receive** (`waveform.js:1233-1253`, read to understand what they actually depend on): `splitRange(useEmptyRange)`/`joinRange(parts)` slice a plain JS array (`instrument.sample.data` - the exact shape `domain/playback/engine/models/sample.js` already exposes) into `{head, range, tail}`, mutate `range`, and reassemble by concatenation; `getRange()` returns the current `{rangeStart, rangeLength}` selection (`rangeLength` falsy = "no selection" = operate on the whole sample); `getLoop()`/`setLoop()` read/write `instrument.sample.loop.{start,length}` for `trim()`'s own loop-respecting logic. Nothing here needs a DOM, a canvas, or v1's own `Y`/`EventBus` globals.
- **v1's own sample-edit undo is a second, separate system from the pattern-edit one** (`StateManager.createSampleUndo(action, rangeStart, rangeLength)` / `.registerEdit(...)`, `stateManager.js:197-207`), driven back into the plugin by an `EVENT.commandProcessSample` listener in `waveform.js` (`:1469-1500`) that **only runs `if (me.isVisible())`** - a real v1 limitation (undo/redo for a sample edit silently does nothing while the sample editor isn't the currently-shown view), not a design worth preserving.
- **`domain/song/editHistory.js` (spec 028) already has a `EDITACTION.SAMPLE` constant and an explicit comment marking the seam**: `// DATA/SAMPLE: declared, not implemented here - P10's own territory.` This was planted on purpose, two specs before P10 was ever allocated, for this exact moment - confirmed by reading `domain/song/index.js`'s own `history = createEditHistory({ applyPatternDiff })` construction (no `applySampleDiff` wired in yet) and its exported surface (`getCurrentInstrumentIndex` exists; no sample-data read/write or edit-registration entry point exists yet).
- **v1 keeps two separate undo domains** (pattern edits and sample edits); this port has always kept exactly one shared stack (`domain/song`'s own `history`), and the seam above was clearly planted to keep it that way rather than reproduce v1's own split - a real, deliberate improvement, not a port of v1's behavior.
- **The rest of the plugin is not part of this spec**: `sampleView.js` (the menu, sliders, spinboxes, instrument-name field, envelope panels, transport buttons - all ordinary, already-implemented v2 component-tree territory once a screen is authored) and `waveform.js`'s own rendering/interaction (a real, third specialized-component candidate after `patternGrid`/`fileBrowser` - drawing, zoom/scroll, per-pixel marker hit-testing, playback preview) are both later specs. So are `loopCreator.js`, `resamplePanel.js` and `hissReductionPanel.js` (848, 116 and 443 lines respectively) - each already a separable, real feature reachable from the same menu, none of which the four core operations depend on.
- **One real v1 inconsistency worth recording, not fixing here**: `sampleView.js`'s own 16-bit→8-bit conversion button (`changeSampleBit`, `:869-887`) re-quantizes sample data immediately and destructively, with no `StateManager.registerEdit` call at all - the one edit in this whole plugin that is not undoable. Not this spec's concern (no bit-depth conversion is in scope here), recorded for whichever spec eventually ports it.

## Decisions and assumptions

- **A new domain module, `domain/sampleEditor/`**, not an extension of `domain/song/`: sample selection and sample-data operations are a genuinely different concern from pattern/row selection, even though both eventually share one undo stack. `domain/sampleEditor/processing.js` holds the four pure DSP transforms (array in, array out - directly unit-testable with plain arrays, no Tracker, no domain/song import at all); `domain/sampleEditor/index.js` is the capability (selection state, the four operations, undo registration), reaching into `domain/song/index.js`'s own (extended) public surface for the current instrument and edit registration - an ordinary inter-module dependency, not a new documented exception to any "reach into the engine directly" rule, since `domain/sampleEditor/` never imports `domain/playback/engine/` itself.
- **`domain/song/index.js` gains three things**: `getCurrentInstrument()` (mirroring its own existing `getCurrentInstrumentIndex()`), `registerSampleEdit(action)` (a thin pass-through to the same shared `history.registerEdit`, the one door for anything outside `domain/song/` to add an undo entry), and `applySampleDiff(action, direction)` wired into `createEditHistory`'s own `applySampleDiff` option (mirroring `applyPatternDiff`'s existing shape) - it needs `Tracker` (already imported there) to find the target instrument and switch to it if the edit being undone/redone belongs to a different one, matching v1's own `redo()`/`undo()` (`stateManager.js:49,100`).
- **v1's two-field `{type: DATA, target: SAMPLE}` action shape collapses to one**: nothing else in v1 ever used `type: EDITACTION.DATA` with a different `target`, so this port's own sample-edit actions carry `type: EDITACTION.SAMPLE` directly - a small, deliberate simplification, not a port of an indirection nothing else needs.
- **A sample-edit undo works regardless of whether any sample-editor screen is open** - v1's own `if (me.isVisible())` guard is an accident of its event-driven UI wiring, not a behavior worth reproducing; this port's own single shared undo stack has no "is a screen showing" concept for pattern edits either, so there is nothing to make sample edits consistent with by adding one.
- **Selection defaults to "the whole sample"** when nothing is selected (`{start: 0, length: 0}`, `length === 0` meaning "operate on everything"), matching `splitRange()`'s own `rangeLength` falsy branch exactly.

## User stories and acceptance

- **SAMPLE-001 — Selection.** `domain/sampleEditor/index.js` exposes get/set for a `{start, length}` sample selection, defaulting to "the whole sample." Acceptance: unit tests for the default and for setting/reading an explicit range.
- **SAMPLE-002 — `adjustVolume`.** All four `amount` forms (`"max"`, `"fadein"`, `"fadeout"`, a signed percentage) produce the same sample data v1's own algorithm would, verified against hand-built arrays with known expected output (not a round trip - there is no file format involved here). Acceptance: one test per form, plus the soft-clip boost's own peak-tracking behavior.
- **SAMPLE-003 — `trim`.** Strips near-silent head/tail, respects a loop's own end point, enforces an even final length, and is a no-op when there is nothing to trim. Acceptance: unit tests for each of these four behaviors independently.
- **SAMPLE-004 — `reverse`/`invert`.** Exactly what they say. Acceptance: unit tests.
- **SAMPLE-005 — Undo/redo, unified with `domain/song`'s own stack.** Every operation registers one undo entry; `domain/song#undo()`/`redo()` correctly restores/reapplies the exact sample-data range that changed, including switching to the edited instrument first if a different one is currently selected, and correctly handles a length-changing edit (`trim`) as well as same-length ones. Acceptance: a unit test per operation confirming `undo()` restores the original data and instrument selection exactly, and `redo()` reapplies it.
- **SAMPLE-006 — No regressions.** Full unit suite passes; `domain/song`'s own existing pattern-edit undo tests are unaffected; no YAML/compiler/capabilities.js change (headless capability only, no screen yet).

## Non-functional requirements

- Headless verification only (no browser-automation dependency in this environment, the same recorded reason every spec since 019 has given) - nothing here has a screen yet.
- No new component type, no YAML, no capability mapping - matching spec 039's own shape (a mechanism/capability spec, not a screen).

## Scope boundaries

In scope: `domain/sampleEditor/{processing,index}.js`, a `README.md`, `domain/song/index.js`'s three additions, `domain/song/editHistory.js`'s new `applySampleDiff` hook, and tests for all of the above.

Out of scope, recorded rather than silently dropped:

- **The waveform view** (`waveform.js`'s own drawing/zoom/scroll/marker-hit-testing/preview-playback) - a real, third specialized-component candidate after `patternGrid`/`fileBrowser`; a later spec.
- **The rest of `sampleView.js`'s own screen** (menu, sliders, spinboxes, instrument-name field, envelope panels, transport buttons, draw-mode freehand editing) - ordinary, already-implemented v2 component-tree territory once authored; a later spec, needing the waveform view to exist first (or at minimum a placeholder) to be useful.
- **`loopCreator.js`, `resamplePanel.js`, `hissReductionPanel.js`** - each a separate, real feature, each its own later spec. `loopCreator.js` shipped as specs 043-045; `resamplePanel.js` as spec 046. **Amendment, 2026-09-14**: `hissReductionPanel.js` will not - the port roadmap's own [requirements.md](../010-port-roadmap/requirements.md) records a resolved open decision (7) permanently excluding it, superseding "a later spec" above without rewriting it.
- **`resample`/`resampleToRate`** (`waveform.js`'s own, not `sampleProcessing.js`'s) - a naive nearest-neighbor 2x resize or an interpolated arbitrary-rate resize; belongs with whichever spec ports the resample panel, not this one.
- **8-bit/16-bit conversion** (`changeSampleBit`) - `sampleView.js`'s own, non-undoable in v1; a later spec's decision whether to fix that inconsistency or preserve it.
- **Where the "sample" screen mounts** - v1's own `customPanel` (host-owned region shared with the pattern/multitrack views) has no v2 equivalent decision made yet; intersects with `top-view.value`'s existing screen-switching (already used by `fileOperationsPanel`/`sampleEditPanel`'s own placeholder since spec 026) - a later spec's to make, once there is a real screen to mount.
