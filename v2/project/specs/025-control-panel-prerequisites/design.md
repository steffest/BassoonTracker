# 025 — Design

## Breakpoints: a partial layout override, resolved where layout already is

`node.breakpoints` (compiled from the authored `breakpoints:` sequence) is a list of `{ maxWidth, layout }`, where `layout` carries *only* the fields the author actually wrote under it - never a full, defaulted layout the way a node's own `layout:` is. This matters: `compiler/layoutFields.js`'s `resolveLayoutFields()` always returns a complete `{ width, height, direction, resizable }`, defaulting anything absent (to `auto`, mostly), which is exactly right for a node's *own* layout but would be wrong for a breakpoint, since an author who only wrote `direction: column` under a threshold must not have `width`/`height` silently reset to `auto` at that width. `compiler/convert.js` calls the same `resolveLayoutFields()` (so a breakpoint's own values are validated and defaulted-per-field identically to the top-level case) and then keeps only the keys the raw YAML actually named.

`runtime/genericLayout.js` gained one new pure function, `effectiveLayout(node, viewportWidth)`: given the current viewport width (already threaded through the whole layout pass as `context.viewportWidth`, since `computeGenericLayout` always received the viewport), find every breakpoint whose `maxWidth` is at or above the current width, and return the node's own layout with the *narrowest* matching one's fields merged on top. "Narrowest wins" is the one real design decision here, and it mirrors v1's own cascade directly: `Layout.setLayout` always narrows *further* as the viewport shrinks (16 tracks → 12 → 8 → 4; `full` → `condensed` → `2row`), so a smaller `maxWidth` is always the more specific, more-overridden state, not a competing alternative to a larger one.

Every place `runtime/genericLayout.js` previously read `node.layout` directly now reads `effectiveLayout(node, context.viewportWidth)` instead: `isRow()`, `resolvedCrossAxis()`, `distributeMainAxis()`, `measureIntrinsic()` (which gained a `context` parameter in place of its old separate `measureLeaf`/`cache` pair, since it now needs `viewportWidth` too), `layoutViewport()`, `layoutTabs()`, `layoutOverlay()`. None of this is a new mechanism at each of those call sites - `effectiveLayout()` returns `node.layout` completely unchanged whenever a node has no `breakpoints` (or `computeGenericLayout` was not given a finite viewport width), which is every node and every caller before this spec, so the existing test suite - the actual regression backstop - kept passing with zero changes to its own assertions.

## `visibleWhen`: the same "absent from layout" trick, generalized past a fixed set of container types

Spec 020 (a closed overlay), spec 021 (a tab's inactive items, a collapsed panel's content) each independently taught `runtime/genericLayout.js` that "not currently shown" means *absent from layout entirely* - no rect, no clip, and therefore (since drawing and hit-testing both key off `layoutResult.rects` having an entry at all) no draw and no hit, with nothing further to teach the renderer. `visibleWhen` is that same idea offered to *any* node, gated on a plain state field instead of a specific parent container's own type: `flowChildren()` (already the one place both the overlay filter and the tab-header/collapse-content logic run through) now also drops a child whose `visibleWhen.field` does not currently hold one of its declared `oneOf` values, via a new `isVisible(node, context)` and a new `context.stateValueOf(field)` callback `mountGeneric.js` supplies from the same `mockState`/host-store object every other bound field already reads through.

This is deliberately *not* modeled as "named regions" the way v1's four independent `EVENT.showView` listeners are - there is no `region` concept anywhere in this mechanism, only a field name and a set of matching values, both entirely up to the author. v1's own two independent regions (the top area, the bottom area) fall out for free as two nodes that each happen to name a *different* field (`view.top`, `view.bottom`) - verified directly in `tests/viewVisibility.test.js` and `tests/controlPanelPrerequisites.test.js` - not because the mechanism knows about regions, but because nothing stops two unrelated nodes from being gated on two unrelated fields. Composing v1's exact vocabulary (the fact that `"main"` should reset *both* regions at once) is an authoring choice - two nodes each listing `"main"` in their own `oneOf` - not something this mechanism enforces or needs to know about.

## What this deliberately does not do

- **No vocabulary for writing a `visibleWhen` field.** An author wires a button to change one exactly the way any other bound field already gets written - an `actions:` binding whose recipe names a `mockField` matching the `visibleWhen.field` (the existing `set-value` recipe, spec 014, already does this: `actions: set the view` names a command whose `mockField` is `the-view.value`, if that's what an author names their field). Nothing new was needed and nothing screen-specific was built, since no screen authors one yet.
- **No replication of v1's specific breakpoint values** (`maxVisibleTracks`, `prefered`, the sidebar threshold, `controlPanelButtonLayout`'s three states) - those are facts about the control panel and pattern-grid screens' own content, decided when those screens are actually authored, not facts this mechanism spec should invent ahead of a real consumer.
- **No `maxHeight` breakpoints.** v1 has two (piano height at two thresholds); nothing the control panel needs is height-gated, and adding the symmetric case costs nothing later, when something does need it.
- **No authored use anywhere yet.** Verified against the unit suite and direct compiler/layout-pass tests, exactly as spec 020's own new mechanism was before anything used it.
