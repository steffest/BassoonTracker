# 047 — Nibbles: the game engine and grid

Date: 2026-09-14. Kind: feature. Status: specified. Continues package **P10** (features and the plugin path) of the [port roadmap](../010-port-roadmap/requirements.md), following spec 039 (the feature registry). Nibbles is P10's own second named tenant (open decision 3: "sample editor and Nibbles port; the generator waits"); the sample editor's own five sub-specs (040-046) are done. This spec is the mechanism - the headless game engine and its own specialized-component leaf - matching the "mechanism before screen" split every prior specialized surface in this port has used (`patternGrid`/`fileBrowser` before their screens, `waveformView` before spec 042, the loop creator's state/DSP (043) before its overlay (044) before its screen wiring (045)). The screen (config panel, score/lives display, buttons, the high-score table's own visual list, the menu action and feature-registry wiring) is a later spec's own.

## Purpose

`script/plugins/games/nibbles/nibbles.js` (1315 lines, read in full for this spec) is v1's third and last plugin - a complete, self-contained snake-style arcade game built directly against v1's raw UI element factories (`host.UI.button`/`image`/`panel`/etc.), with its own hand-rolled per-breakpoint layout math (`col1`-`col5`, and a distinct `col3` narrow-width variant) entirely outside v1's generic component system. Nothing in it touches the tracker's own song/pattern data at all - it is the first genuinely independent domain this port has ever added.

This spec ports the part of it that is real game logic and real drawing: the grid, the snake, collision, scoring, level progression, lives, and the 30 level layouts (decoded once, offline, from the real level-sprite PNG - not re-derived at runtime the way v1 does). It does not author any screen, since nothing about a game's own controls needs a raw canvas leaf - they are ordinary buttons/checkboxes/labels once one exists to bind them to, exactly as every other specialized leaf's own screen has been each time.

## What v1 actually does, and what this narrows out (read from source, not assumed)

- **The playing field's own size is derived from the browser window** (`game.resize()`, 359-382: `mapHeight`/`mapWidth` from `renderTarget`'s own pixel dimensions divided by a fixed 10px `gridsize`), and a fixed 40x15 level layout is centered inside whatever that turns out to be, with the fixed-size layout's own coordinates offset by a computed margin. **This spec fixes the grid at the level layout's own native size, 40x15 cells, always** - not derived from any window or leaf pixel size. This removes an entire axis of complexity (margin math, a `resize()`-triggered map rebuild, a level that "doesn't fit" warning already dead-code in v1 for the levels this spec ports) for a real but secondary piece of v1's own fidelity - the play area's own difficulty-relevant size no longer grows on a wider window. Recorded as a deliberate simplification, reversible if it turns out to matter, the same class of call open decision 1 already made for skin fidelity. The specialized leaf's own draw kind still picks whatever pixel-per-cell scale fits its own measured rect, exactly as `patternGrid`'s row height and `waveformView`'s one-sample-per-pixel already do - only the cell *count* is fixed, not the leaf's own drawn size.
- **v1 decodes the 206x97 indexed level-sprite PNG (`Nibbles.levels`) with a real canvas 2D context at runtime**, every time a level's own sprite is first needed (`getLevelSprite`, 557-575). This port decodes it once, offline, with the same dependency-free PNG reader spec 008's own skin-atlas tool already has (`tools/skinAtlas.mjs#decodePng`, which already handles this exact PNG's own indexed color type), and checks in the result as a plain ES data module (`domain/nibbles/levels.js`) - synchronously importable, headless-testable, no canvas needed at all. See design.md's own new `tools/nibblesLevels.mjs`.
- **v1 conflates walls, food and the snake's own body into one array of numbers** (`map`/`changeMap`, `cell()`/`setCell()`): 0 empty, 1-9 the current food digit, 10+ a wall (indexed into a *session-wide, ever-accumulating* `colors`/`colorMap` table that is never reset between levels), 1000+ snake body (the offset itself doubling as the body's own "age" for the fade-out tail effect). This port keeps the food/snake split (dynamic, mutable, reset per level) but keeps each level's own wall layout and its own small, self-contained color palette as static data read directly from `domain/nibbles/levels.js` - never copied into a mutable per-cell array at all, since walls never move once a level starts. This is a real, deliberate simplification of v1's own representation, not a change in observable behavior: a wall's own drawn color is identical, addressed through the level's own palette index instead of a global running offset.
- **The difficulty radio group's own four speeds** (180/100/75/40 ms per tick, `radioGroup.onChange`, 766-772) and **wrap-around** (`doWrap`, toggled by its own checkbox) are ordinary settings this spec's engine exposes as setters - the checkboxes/radio items themselves are screen territory (a later spec).
- **The high-score table** (`highScoreTable`, a fixed ten-entry array seeded with the parent project's own hall-of-fame names, persisted to `localStorage` under the literal key `"nibblesHighscore"`) is ported as its own small module (`domain/nibbles/highscores.js`), mirroring `domain/settings/favorites.js`'s exact shape (spec 033) and **keeping v1's own storage key**, so an existing user's saved scores carry over. The **prompting dialog** for a new high-score name (`host.UI.showDialog`, a raw v1-only modal API with no v2 equivalent) and the table's own **visual rendering** (name/score/level-sprite columns, a `modalDialog`-or-plain-panel layout) are both screen territory - a later spec's own; this spec's own module only answers "does this score qualify, and where," and inserts a supplied name.
- **The "SKIP"/"TRITON" meta-key cheat codes** (`me.onKeyDown`'s own `keyWord` buffer, 1247-1259) are trivial but screen-adjacent easter eggs, not core mechanics - deferred, recorded rather than silently dropped.
- **The player-1/logo decorative sprites, the score/lives LED-style number panel, and the whole hand-rolled `col1`-`col5`/`col3` breakpoint layout** are screen territory - a later spec's own, likely using the declared-breakpoint mechanism spec 025 already built rather than v1's own bespoke column math.

## Decisions and assumptions

- **The grid is a fixed 40x15 cells** (see above) - the single largest deliberate departure from v1 in this spec, made once, up front, rather than discovered mid-implementation.
- **Level data is baked at development time, not decoded at runtime.** `tools/nibblesLevels.mjs` (new, mirroring `tools/skinAtlas.mjs`'s own precedent of a small, dependency-free, Node-only dev tool) reads `assets/games/nibbles/src/levels.png` (copied from the parent repository, provenance recorded) and writes `domain/nibbles/levels.js`, a plain `export const LEVELS = [...]` array of 30 `{ start: {x,y}, colors: [...], cells: [[x,y,colorIndex], ...] }` entries - regenerated only if the source PNG ever changes, the same footing as `domain/playback/engine/enum.js`'s own big `NOTEPERIOD`/`FTNOTEPERIOD` literal tables. Verified against three independently hand-checked levels (1: empty; 3: two vertical bars; 30: a dense multi-color maze) before being trusted for anything else.
- **The engine never imports `domain/playback/`, `domain/song/`, or any tracker-specific module at all.** Nibbles shares nothing with the tracker's own document model - a first, genuinely independent domain folder in this port.
- **`domain/nibbles/index.js`'s `update()` takes no time parameter and is called once per game tick**, matching v1's own `game.update()` shape exactly; a controller-owned accumulator (see design.md) decides *when* a tick has elapsed, the same "elapsed carries forward, never drifts" idea `runtime/animationClock.js` already uses for sprite frames, restated for a game tick instead of a frame count - not extracted into a shared utility, since the two computations differ in what they wrap around (a frame count vs. nothing).
- **A new, small, generic renderer mechanism is needed: a "ticking" leaf.** `animSprite`'s own `animated: true` flag (spec 017) keeps the renderer's `requestAnimationFrame` loop alive for as long as a sprite is mounted, advancing a bound field's own frame count - the wrong shape for "call a whole simulation step," which has no frame count to wrap and needs to run even for a leaf with no bound `field` at all. `renderers/canvas/mountGeneric.js` gains a second, independent clock (`ticks: true` on a component type, `controller.onFrame(deltaMs)` called each tick) rather than overloading the sprite clock - the same choice spec 032's own coalesced-draw loop already made against the sprite clock ("the same start/stop shape ... applied here to everything else instead of unifying the two").
- **The engine's own state machine, including which message and button label the (not-yet-authored) info overlay should show, lives in the domain, not the future screen.** `getStatusText()`/`getButtonLabel()` are pure, derived accessors next to the rest of the state - matching `domain/song`'s own `getUndoLabel()`, so the eventual screen only ever binds to them rather than re-deriving the state-to-text mapping itself.

## User stories and acceptance

- **NIB-001 — The level data is real, not synthetic.** `domain/nibbles/levels.js` has exactly 30 entries; level 1 has no walls; level 3's own wall shape and every level's own start point match a hand-verified extraction from the real source PNG. Acceptance: a unit test asserting exact counts/positions for several levels, cross-checked against an independent read of the source pixels.
- **NIB-002 — Starting, moving, colliding and scoring behave as v1's own formulas do.** A fresh game starts at level 1 with 5 lives and 0 score; moving into a wall, the grid edge (without wrap), or the snake's own body ends the run (loses a life, or ends the game at 0 lives); moving onto the current food digit increments score by v1's own formula (`1000 + (200-frameTime)*currentNumber*2`), advances `currentNumber`, and wins the level at 10; every other tick without eating decrements score by 1 (never below 0). Acceptance: unit tests against real level data, including a wrap-enabled case and a snake-length/self-collision case (`snakeLength()`'s own formula, ported unchanged).
- **NIB-003 — Level progression and lives match v1.** Winning a level increments both level and lives (level capped at 30); losing a life without reaching zero moves to the `LOST` state, and only the following `primaryAction()` ("Try Again") restarts the same level's own snake position - `lost()` itself never resets anything, matching nibbles.js's own `game.lost()`/`game.onClick()` split exactly; reaching zero lives ends the game. Acceptance: unit tests driving a full win/lose sequence.
- **NIB-004 — The high-score table qualifies and inserts correctly, and reads v1's own storage key.** A score above the tenth entry's own score qualifies at the correct rank; inserting shifts lower entries down and drops the last; the table is capped at ten; the storage key is `"nibblesHighscore"`. Acceptance: unit tests mirroring `tests/favorites.test.js`'s own convention, including a fresh (no stored value) case.
- **NIB-005 — The specialized leaf draws the grid, snake, walls and food, and accepts arrow-key movement and Enter.** `nibblesGrid` is the port's fifth specialized-component leaf (after `patternGrid`, `fileBrowser`, `waveformView`, `loopCreatorView`): no children, its own controller (behavior `"nibbles"`) and draw kind read `domain/nibbles/index.js` directly. Arrow keys call `move()`; Enter calls the state-machine's own primary action. Acceptance: a fake-canvas draw-kind test (mirroring `waveformView.test.js`'s own convention) plus a controller test against synthetic key events.
- **NIB-006 — The leaf keeps advancing the game on its own while playing, and stops driving the renderer's clock once nothing needs it.** The new ticking mechanism calls `onFrame(deltaMs)` every animation frame while `nibblesGrid` is mounted, which accumulates elapsed time and calls `update()` once per whole difficulty-tick interval (carrying the remainder forward, never drifting) - `update()` itself no-ops while the game is not in its "playing" state, matching v1's own internal guard, so the clock does not need to know or care. Acceptance: a controller test feeding synthetic deltas and asserting the exact number of `update()` calls for a given elapsed time and difficulty.
- **NIB-007 — No regressions.** Full unit suite passes; nothing under `script/src` or `script/plugins` is imported; `node build.mjs app`/`node compiler/generate.js` are unaffected (this spec touches no YAML, no compiler, no `capabilities.js` mapping - the same headless-only footing specs 039/040/043 already established for a mechanism with no tenant screen yet).

## Non-functional requirements

- Headless verification only (no browser-automation dependency in this environment, the same recorded reason every spec since 019 has given); the fake-canvas draw-kind test convention (`waveformView.test.js`/`loopCreatorView.test.js`) covers the drawing surface instead.
- No new runtime dependency - `tools/nibblesLevels.mjs` is a development-time script only, reusing the existing dependency-free PNG decoder.

## Scope boundaries

In scope: `tools/nibblesLevels.mjs` (new), `domain/nibbles/levels.js` (generated), `domain/nibbles/index.js` (new), `domain/nibbles/highscores.js` (new), `runtime/nibblesController.js` (new, behavior `"nibbles"`), `renderers/canvas/drawKinds.js`'s new `"nibblesGrid"` entry, `runtime/componentTypes.js`'s new `nibblesGrid` type (including the new `ticks` registry flag), `renderers/canvas/mountGeneric.js`'s new, independent tick clock, and tests for all of the above.

Out of scope, recorded rather than silently dropped:

- **The screen** (config panel, score/lives display, Start/Exit/HighScore buttons, the info overlay's own visible text, the high-score table's own visual list, the "Nibbles" menu action and feature-registry wiring, and `top-view.value`'s own new sibling value) - a later spec's own, the same "mechanism, then screen" split every prior specialized surface used.
- **Dynamic, window-size-derived grid dimensions** - see Decisions and assumptions; a fixed 40x15 grid is used instead.
- **The high-score name-entry dialog and the table's own visual rendering** - screen territory; this spec's own module only answers "does this score qualify" and "insert this entry."
- **The "SKIP"/"TRITON" cheat codes** - trivial, screen-adjacent, deferred.
- **The decorative player-1/logo sprites** - not copied into `v2/assets` by this spec; a later spec's own, when the screen needs them.
