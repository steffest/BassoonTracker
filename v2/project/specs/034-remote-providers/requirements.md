# 034 — Remote providers: catalog browsing and the proxy fallback

Date: 2026-09-13. Kind: feature. Status: specified. Continues package **P9** (persistence, providers, file operations) of the [port roadmap](../010-port-roadmap/requirements.md), following spec 033 (settings and favorites).

## Purpose

P9's design sketch names "the five providers (own API, ModArchive, modules.pl, HippoPlayer, Dropbox) behind one interface" as its next piece after settings. Reading all five `script/src/provider/*.js` modules in full (not assumed from the design sketch) found that **there is no one interface** - v1 never built one. Three providers (ModArchive, modules.pl, HippoPlayer) share a genuinely common shape (`get(path, callback)` → a browsable tree). Dropbox is a materially different, larger thing: stateful OAuth, a vendored 162-line SDK (`script/src/lib/dropbox.js`), and a browser popup/redirect auth flow whose redirect URI (`https://www.stef.be/bassoontracker/auth/dropbox.html`) is hardcoded to the original author's own domain - a v2 instance running anywhere else cannot complete that flow without a new redirect URI, which is a real product/hosting decision, not a code-porting one. Bassoon (`script/src/provider/bassoon.js`, v2's own API) is a third shape again: a CORS proxy passthrough plus a server-side render/export pipeline (`storage/render` → `storage/convert` → `storage/wavtomp3`, ending in a `document.location` download) - the render/export half belongs with the format write path (a later P9 slice), not "browsing."

This spec takes the slice that is genuinely one shape and needs nothing else first: **the three catalog browsers, plus the one proxy function `loadModule` already needs**. Dropbox, Bassoon's render/export path, the disk-operation screens and the format write path remain unallocated - see Scope boundaries.

## What v1 actually does (read from source, not assumed)

- **`script/src/provider/modarchive.js`, `modulespl.js`, `script/src/provider/hippo.js`** each export one object with a `get(url, next)` method. `url` is a slash-delimited pseudo-path (`"genre/12"`, `"artist/7/2"`, `"toprating/1"`, `"playlist/foo"`), split into `[verb, param, page]` and switched on. Each returns, via callback, an array of `{title, url, children?, info?, icon?}` tree nodes - the shape `script/src/ui/diskOperations.js`'s listbox renders directly (`addListatLevel`, `diskOperations.js:278-295`). ModArchive/modules.pl memoize `genres`/`artists` in a module-level array (fetched once, reused); a genre/artist/toprating/topreview page appends a synthetic `{title: "... load more ...", children: [], url: <next page>}` node when the server reports more pages (`modarchive.js:153-171`, `modulespl.js` has no pagination sentinel for genre but does for toprating/topscore/artist - confirmed by re-reading both in full: `modulespl.js`'s `loadGenre`/`loadArtists` never appends one, only `parseModList`'s callers for `toprating`/`topscore`/`artist` do, via the same `formatFileSize` helper).
- **Two API bases per provider**, both already-hardcoded absolute URLs on the original author's own hosting (`https://www.stef.be/bassoontracker/api/...`) - not a relative path, and not this repository's own `api/` folder at build time (though that folder's own server code is what backs those URLs when deployed there; "api/ stays as is", open decision 4, already resolved this). ModArchive additionally has an "API v1" base (`toprating`/`topreview`) whose JSON is wrapped in a `{modarchive: ...}` envelope (`parseModListV1`, `modarchive.js:114-120,136-175`) - a different response shape from its own v2 API base (`genres`/`artists`/`genre`/`artist`, unwrapped, `parseModList`, `modarchive.js:122-134`). This asymmetry is v1's own, not introduced here.
- **Hippo (`hippo.js`) is the simplest**: `get("playlists")` lists cached `.prg` playlist names (title = filename with `.prg` stripped and underscores turned into spaces), `get("playlist/<name>")` fetches one playlist's contents. No pagination, no genre/artist tree, no v1-API-envelope quirk.
- **`filesystem.js#loadFile`'s own proxy retry** (`filesystem.js:26-36`): on `XMLHttpRequest.onerror` (CORS or mixed-content), if the URL is not already a proxied one, it retries through `BassoonProvider.proxyUrl(url)`; otherwise it gives up. `BassoonProvider.proxyUrl`/`isProxyUrl` (`bassoon.js:84-90`) are pure string functions - `baseUrl + "proxy?" + encodeURIComponent(url)` and a prefix check.
- **`domain/playback/index.js#loadModule`** (v2, existing) already does the equivalent job with `fetch()`, but has no retry at all: a failed `fetch()` (network error, thrown before a response even arrives - which is exactly what a CORS failure looks like to `fetch`) propagates as a rejected promise with no fallback, unlike v1's own behavior.
- **Dropbox (`dropbox.js`, all 143 lines read)**: `checkConnected()` (promise, lazy-imports `lib/dropbox.js`, checks a stored access token by calling `users/get_current_account`), `showConnectDialog()`/`authenticate()` (a `ModalDialog` plus a redirect to the hardcoded `authRedirect` URL above), `list(path, next)`/`get` (alias of `list`), `getFile(file, next)` (downloads a blob), `putFile(path, content, next)` (uploads, honoring `SETTINGS.dropboxMode` - `"overwrite"` vs `"add"+autorename`, a setting v2 already persists via `domain/settings/index.js`'s `dropbox-mode.value`/`dropboxMode` key). None of this is attempted here.
- **Bassoon's render/export path** (`bassoon.js:28-82,92-106`): `renderFile(fileName, toMp3)` chains three sequential POSTs to `storage/render/<mod|xm>` → `storage/convert/<tempFile>` → (`toMp3` ? `storage/wavtomp3/<tempFile>` : skip), each round-tripping the *original module bytes* again (confirmed by re-reading: every `FetchService.sendBinary` call sends `file.buffer`, not the previous step's result - the "conversion" is entirely server-side, keyed by the returned `tempFile` token), ending in a same-tab navigation (`document.location.href = ...?dl=1&name=...`) that triggers a browser download. This is the "vendored, no-CDN MP3 encoder" open decision 5 already flagged as a *divergence* to build, not a port - v1 never runs an encoder client-side at all. None of this is attempted here.
- **The disk-operation screen's own root listing is a separate static snapshot**, not `ModArchive.get()`/`ModulesPl.get()` called with an empty path: `diskOperations.js:393-405,449-461` fetch `data/modarchive.json`/`data/modulespl.json` (static files at the parent repository's root, not under `api/`) once and cache them as the tree's root; `ModArchive.get()`/`ModulesPl.get()` are only ever called to expand a node the static snapshot already contains (`toggleDirectory`, `diskOperations.js:680-710`). This spec does not need those static snapshots at all - see Scope boundaries.

## Decisions and assumptions

- **No provider interface is invented where v1 has none.** Three separate modules (`domain/providers/modArchive.js`, `modulesPl.js`, `hippo.js`), each with one `browse(path)` function - not a shared factory or base class - because forcing a common interface across v1's own genuinely different response shapes (the API-v1 envelope, the pagination sentinel, Hippo's total absence of both) would be exactly the kind of ahead-of-need abstraction this project's own conventions avoid. Where the three really are identical in *shape* (a tree node, a path-splitting dispatch), the three modules read alike by construction, not by inheritance.
- **`fetch()`, not a ported `FetchService`.** v2 has never ported `script/src/fetchService.js`'s jQuery-shaped `XMLHttpRequest` wrapper, and nothing here needs it: `domain/playback/index.js#loadModule` already uses plain `fetch()`, and every provider call in this spec is a `GET` returning JSON - the exact shape `fetch(url).then(r => r.json())` already covers.
- **`domain/providers/bassoon.js` is proxy-only.** `proxyUrl`/`isProxyUrl` port verbatim (pure string functions, no divergence possible). `renderFile` and `putFile`-adjacent upload behavior are not here - see Scope boundaries.
- **The proxy retry lands in `domain/playback/index.js#loadModule`**, not as a new capability nothing calls. `loadModule` already does the fetch this needs to wrap; duplicating a second "load a URL, retry through the proxy" function elsewhere would fragment the one place a module URL is actually fetched. `domain/providers/index.js` exports the retry wrapper; `loadModule` imports and uses it, a small, explicit cross-domain import recorded in both READMEs, the same shape spec 033 already used twice (`domain/playback` ↔ `domain/settings`).
- **Dropbox is its own later spec**, not a smaller slice folded in here. Reasons, in order of how load-bearing they are: (1) its OAuth redirect URI is hardcoded to a domain this port does not own, which is a hosting/product decision (what redirect URI does *this* deployment use?) that blocks writing correct code, not just more of it; (2) `checkConnected`/`authenticate` are stateful across page loads in a way `browse()` is not, needing a real design for where that state lives (the settings capability's `dropboxMode` is a mode flag, not a session); (3) `lib/dropbox.js` (162 lines, not yet read in full for this spec) needs its own provenance/vendoring pass, matching how spec 006 vendored CodeMirror deliberately and documented it, not silently bundled.
- **The disk-operation screens, the static root-snapshot JSON files, and `random.*`/`generatePlayList` command wiring are not here either.** All three need YAML authoring (new `actions/*.yaml` files or recipe matches for `random.*`; a screen with a hierarchical, expand/collapse-capable listbox v2's own `listbox` type does not have - spec 019 shipped a flat list only) - UI-authoring work this capability-only spec does not touch, matching every prior P9/P6/P7 split (a capability lands before the screen that displays it).

## User stories and acceptance

- **PROV-001 — ModArchive browsing.** `domain/providers/modArchive.js#browse(path)` reproduces `ModArchive.get()`'s dispatch for `genres`, `artists`, `genre/<id>[/<page>]`, `artist/<id>[/<page>]`, `toprating[/<page>]`, `topreview[/<page>]`, including the API-v1 envelope unwrap and the "... load more ..." pagination sentinel. Acceptance: unit tests against a fake `fetch` covering each verb, the envelope unwrap, single-vs-array module results (`modarchive.js:141-151`'s own non-array special case), and the pagination sentinel appearing only when the server reports more pages than the current one.
- **PROV-002 — modules.pl browsing.** `domain/providers/modulesPl.js#browse(path)` reproduces `ModulesPl.get()`'s dispatch for `genres`, `genre/<id>[/<page>]`, `toprating[/<page>]`, `topscore[/<page>]`, `artists`, `artist/<id>[/<page>]`, including the `rate`/`score` extra-info label prefix (`modulespl.js:104-117`) and its own proxy-prefixed module URLs (`proxyUrl + mod.id`, distinct from ModArchive's direct `api.modarchive.org` URLs). Acceptance: unit tests mirroring PROV-001's coverage.
- **PROV-003 — HippoPlayer browsing.** `domain/providers/hippo.js#browse(path)` reproduces `Hippo.get()`'s `playlists`/`playlist/<name>` dispatch, including the cached-playlists-array memoization and the filename-to-title cleanup (`.prg` stripped, `_` → space). Acceptance: unit tests covering both verbs and an unrecognized verb resolving to `[]` (matching the `default: next([])` case all three providers share).
- **PROV-004 — The proxy fallback.** `domain/providers/bassoon.js#proxyUrl`/`isProxyUrl` port verbatim. `domain/playback/index.js#loadModule`'s fetch retries once through `proxyUrl()` when the first attempt fails (network error or non-OK response - see design.md for exactly which v1 case this covers, since `fetch()`'s own failure signal differs from `XMLHttpRequest.onerror`), and does not retry a second time if the proxied attempt also fails (matching v1's own "already proxied, no more retries" cutoff, `filesystem.js:28-35`). Acceptance: `tests/playback.test.js` extended - a fake global `fetch` that fails once then succeeds through the proxy path proves the retry; a fake `fetch` that fails both times surfaces the original error, not a silent hang.
- **PROV-005 — No regressions.** Full unit suite passes; `node build.mjs app`/`dist` unaffected (no YAML, compiler, or component-type change); a grep-based boundary test confirms nothing outside `domain/providers/` calls the three catalog hosts' URLs directly, matching the `domain/settings/`/`domain/song/` convention.

## Non-functional requirements

- Follows the existing `domain/*/README.md` convention: one boundary module per provider (three, since there is no shared interface to put behind one `index.js`), provenance recorded, pure where possible, headless-testable via a fake `fetch`.
- No new component type, no renderer change, no YAML/compiler change - a capability only, exactly as spec 033 was.
- Headless verification only, for the same recorded reason every prior spec since 019 has given (no browser-automation dependency in this environment).

## Scope boundaries

In scope: `domain/providers/{modArchive,modulesPl,hippo,bassoon,index}.js`, a `README.md`, `domain/playback/index.js#loadModule`'s proxy-retry extension, tests for all of the above, and the boundary test.

Out of scope, recorded rather than silently dropped:

- **Dropbox** (`checkConnected`/`showConnectDialog`/`authenticate`/`list`/`getFile`/`putFile`, `lib/dropbox.js`) - a later spec; the hardcoded auth-redirect domain is a real open question for whoever takes it, not a porting detail.
- **Bassoon's `renderFile`/`putFile`-adjacent render-export pipeline** - belongs with the format write path (WAV/MP3/XI writers), a later P9 slice; MP3 stays a *divergence* (a vendored, no-CDN encoder) per open decision 5, not this spec's concern.
- **The disk-operation screens** (YAML authoring, the load/save/type/target radio panels - each individually simple, already just `radioGroup`s per `diskOp_Actions.js`/`diskOp_Type.js`/`diskOp_Targets.js` - and the hierarchical, expand/collapse listbox `diskOperations.js`'s own tree view needs, which v2's `listbox` type does not have) - later spec(s), needing UI-authoring and possibly a component-type extension.
- **The static root-listing snapshots** (`data/modarchive.json`, `data/modulespl.json`, `data/modules.json`, `data/samples.json`, `playlists/main.json`) - belong with the disk-operation screen that actually fetches them for a tree's root; this spec's `browse()` functions are only ever called to expand a node, exactly as v1's own `ModArchive.get()`/`ModulesPl.get()` are.
- **`random.*`/`generatePlayList` command wiring** - `app.yaml` already references `newFile`/`randomSong`/`randomSongXM`/`randomPlayList`/etc. as unresolved action references (`app/LOOSE-ENDS.md`); giving them a real capability needs a new `actions/*.yaml` file or a recipe match, YAML-authoring work distinct from this capability-only spec. Recorded as a natural, small follow-on once this capability exists.
