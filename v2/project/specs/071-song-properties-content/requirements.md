# 071 — Song-properties section content

Date: 2026-09-16. Kind: feature. Status: specified. Continues [spec 070](../070-ui-section-alignment/requirements.md)'s own step 9 (`010-port-roadmap/visual-parity-plan.md`'s ordered list) - the first genuinely new-content step in that list, not a restructuring of content v2 already had.

## Purpose

Spec 070 gave the song-properties section a real, bounded wrapper and correctly scoped everything v2 already had into it (`songPatternList`, `fileOperationsPanel`, `optionsPanel`, `nibblesPanel`). What that section still lacks - because v2 has never built any of it before - is `appMainPanel.js`'s own **always-present** content: the mod-name inputbox, six spinboxes (Pattern/Instrument/Song Length/Song Repeat/Pattern Length/BPM), the instrument listbox, and three purely decorative banner elements (logo, corner deco, tracker wordmark). This spec builds all of it, in one pass, deliberately excluding one real, separable piece of v1 behavior: dragging an instrument row to reorder it (`runtime/componentTypes.js`'s own `listbox.reorderable` property is already declared, explicitly documented as "a later spec's work" since spec 019 - this spec does not change that).

## What v1 actually does (read from source, not assumed)

`script/src/ui/app/appMainPanel.js`, read in full (again, specifically for this spec - spec 070's own section-map research had already read it once for structure, not for these details):

- **Mod-name inputbox** (75-82): a plain text input, `onChange` sets `Tracker.getSong().title` directly and calls `UI.setInfo(value)` (a status-bar echo, no v2 equivalent needed - nothing else does this either). `EVENT.songLoading` sets it to `"Loading ..."`; `EVENT.songPropertyChange` restores the real title once loaded.
- **Six spinboxes** (120-194): Pattern (`Tracker.setCurrentPattern`), Instrument (`Tracker.setCurrentInstrumentIndex` - **the exact same call** `sampleEditPanel.yaml`'s own instrument spinbox already makes), Song Length (`Editor.addToPatternTable`/`removeFromPatternTable`, one step per change - see below), Song Repeat (`song.restartPosition`), Pattern Length (`Tracker.setPatternLength`), BPM (`Tracker.setBPM`). All six are resynced from `EVENT.songPropertyChange`/`EVENT.songBPMChange`/`EVENT.instrumentChange` whenever the song document itself changes (load, undo, playback advancing the pattern, etc.) - not just when the user drags the spinbox.
- **Instrument listbox** (84-110): one row per instrument slot (`Tracker.getMaxInstruments()`, not just the ones with names - matching `formatInstrumentIndex(index) + " " + instrument.name`, `lib/util.js:16-21`), reorderable (**excluded**, see Purpose), a click selects (`Tracker.setCurrentInstrumentIndex`), and a same-row click within 400ms of the previous one (`lastInstrumentClickTime`/`lastInstrumentClickData`, 93-100) is treated as a double-click and additionally opens the sample editor (`EVENT.command, COMMAND.showSampleEditor`).
- **Logo/corner/tracker** (56-73): `_logo` is a plain toggle button (own `onDown` flips its own `isActive`, nothing else reads it) swapping between a grey and a colour version of the same wordmark image - no functional effect anywhere else in the codebase. `_corner` is a static, non-interactive decorative image, no button at all. `_tracker` is the same shape as `_logo` - a toggle button, but its "active" image is a small ASCII-art version banner (`_buildSteffestVersion()`, not read in detail - a decorative easter egg, not user-facing product text). None of the three have any state anything else in the application reads.
- **Song Length's own real mechanics** (script/src/editor.js:372-416, read for this spec): `addToPatternTable(index, patternIndex)` inserts one entry (default: at the end, `patternIndex` default 0) and increments `song.length`; `removeFromPatternTable(index)` removes one entry (default: the last) and decrements `song.length`, clamping the current song position if it now points past the end. `appMainPanel.js`'s own spinbox `onChange` (152-156) calls exactly one of these per change (`if (currentLength > value) removeFromPatternTable(); else if (currentLength < value) addToPatternTable();`), relying on the spinbox's own one-step-per-drag/click gesture - never a multi-step jump in one call.
- **A closely related, already-authored, already-mocked precedent found while scoping this**: `components/songPatternList.yaml`'s own listbox (`field: song.position`) and its four buttons (`incrementPattern`/`decrementPattern`/`insertPattern`/`deletePattern`) are **100% static placeholder content** - the four commands are unmapped `GENERATED MOCK`s, and the listbox's own four items are hardcoded YAML strings, never actually reflecting the real song's pattern table. `script/src/ui/app/components/songPatternList.js` (read in full) shows this same listbox is, in v1, **fully dynamic** - one row per song-position entry (`"<step>:<pattern>"`, `song.patternTable`), and its four buttons are real, using the identical `addToPatternTable`/`removeFromPatternTable` primitives Song Length's own spinbox needs, plus a `Tracker.updatePatternTable(index, value±1)` for +/-. Building Song Length's own real add/remove logic without also making this listbox real would leave its four buttons doing real work with no visible effect (the list would still show four fake rows) - so this spec closes that gap too, not as scope creep but because leaving it open would make Song Length's own new behavior impossible to verify or use correctly.

## Decisions and assumptions

- **The instrument listbox (and `songPatternList`'s own real rows) reuse `fileBrowser`'s existing `rowList` mechanism**, not `listbox`'s. Confirmed by reading `runtime/listController.js` (fixed, YAML-authored child items only - no dynamic population path exists) against `runtime/fileBrowserController.js`/`renderers/canvas/drawKinds.js` (a `state.rows` array a capability publishes, generically documented as fitting "a local file list, a remote catalog page, or anything else shaped like a row" - confirmed the row shape used by the draw kind is `{title, level?, icon?, info?}`, read directly off `drawKinds.js`, not assumed from the doc comment alone). This needs new **domain/capability** code (publishing rows, handling selection and double-click) but zero new runtime/engine code - `doubleClick` is already dispatched generically for any node type (`mountGeneric.js`'s own `deliver()`). Reusing a type named "fileBrowser" for a non-file row list is a real naming mismatch, worth a one-line note wherever it's authored, not a blocker.
- **`domain/song/index.js` gains the pattern-table mutation primitives** (`addToPatternTable`/`removeFromPatternTable`/`incrementPatternTableEntry`/`decrementPatternTableEntry`) its own header comment currently calls out of scope ("pattern-table sequence... out of scope - see design.md," spec 028's own decision) - a normal evolution, the same way `domain/sampleEditor` grew across five later specs. This directly closes `songPatternList.yaml`'s own four pre-existing mocked commands as a side effect, not a separate initiative.
- **BPM lives in `domain/playback/index.js`, not `domain/song`** - tempo/scheduling is that module's own documented territory (it already owns `screenRefresh`/`ftMode`, neither song-document nor sample-edit state, for the identical reason).
- **The mod-name inputbox reuses the existing `song.title` field** (`domain/playback/index.js`'s own `STATE_FIELDS.title`, already published on load, already read-only-displayed by `infoBar.yaml`) - a new capability adds the write direction; no new field.
- **The Instrument spinbox reuses the existing `instrument-index.value` field and `instrument-index.set` capability** (`domain/sampleEditor/index.js#setInstrumentIndex`) verbatim - v1 itself makes the identical `Tracker.setCurrentInstrumentIndex` call from two different UI locations; v2 does the same from two different YAML nodes bound to the same field/action, no new capability.
- **The logo is a real, deliberately-mocked toggle** (`logo.active`, `toggle-generic`) swapping `logo_grey_70`/`logo_colour_70` - confirmed reading v1's own source that nothing else in the codebase ever reads this state; matching this whole port's own established precedent for real-but-functionally-inert UI state (e.g. `pattern-view.value`'s own sibling fields). **The tracker banner is ported as a plain, non-interactive image instead of a second toggle** - its own real "active" image is not a second static sprite but a canvas composition of an image plus dynamically-drawn version text (`_buildSteffestVersion()`, read in full), an easter egg disproportionate to its value to reproduce pixel-for-pixel; the always-visible `tracker` sprite alone is what's ported.
- **Asset availability confirmed, not assumed**: `skin/src/logo_grey_70.png`, `logo_colour_70.png`, `togglecorner.png`, `tracker.png` all exist as real source PNGs (checked directly on disk) - this whole banner piece is *not* permanently out of scope the way the plan's own step-9 bullet worried it might be (unlike `infoBar`'s own already-recorded missing icons). The corner deco (`_corner`) is non-interactive in v1 (a plain `UIImage`, no button) - ported the same way, a plain `image` node, not a control.
- **All six spinboxes, the mod-name box, and the instrument listbox republish on song load**, matching v1's own `EVENT.songPropertyChange`/`songBPMChange`/`instrumentChange` resync - not just reflecting the last local edit. `domain/playback/index.js`'s own existing module-load success path (where `STATE_FIELDS.title` is already republished) is extended to call into `domain/song`'s own new `publishSongProperties(app)` at the same point - an ordinary inter-module call through the public door, the same shape `domain/sampleEditor` already uses to reach `domain/song`.

## User stories and acceptance

- **SONGPROP-001 — The mod-name inputbox edits the real song title.** Typing a new value updates `Tracker.getSong().title`; `song.title` (already displayed by `infoBar.yaml`) reflects it immediately.
- **SONGPROP-002 — All six spinboxes read and write the real song document.** Each one's own real `Tracker`-level effect (verified against `domain/song`'s own existing thin forwards where they already exist, and the new ones this spec adds) matches v1's exactly; loading a different song resyncs all six, not just the ones the user hasn't touched yet.
- **SONGPROP-003 — The instrument listbox lists every instrument slot, selectably.** One row per `1..getMaxInstruments()`, `"<hex index> <name>"` (blank name where none exists yet); clicking a row makes it the current instrument, matching the Instrument spinbox's own value.
- **SONGPROP-004 — Double-clicking an instrument row opens the sample editor for it**, unconditionally (not a toggle) - selecting a different instrument while the sample editor is already open keeps it open, showing the newly-selected instrument.
- **SONGPROP-005 — `songPatternList`'s own listbox is real**, not four static rows - one row per song-position entry, reflecting the real `song.patternTable`; its four buttons (previously mocked) genuinely insert/delete/increment/decrement pattern-table entries.
- **SONGPROP-006 — The logo/corner/tracker banners render** with v1's own real artwork, in the right positions; clicking the logo toggles its own local, cosmetic grey/colour state, with no other effect anywhere. The tracker banner and corner deco are both plain, non-interactive images.
- **SONGPROP-007 — No regressions.** Full unit suite passes; `node compiler/generate.js` reports only the deliberate new loose ends this spec's own mocked logo/tracker toggles add; `node build.mjs app`/`dist` both succeed.

## Non-functional requirements

- Every new capability verified against `computeGenericLayout` (the compiled outline) **and** live in a real Chromium browser via Playwright - this whole port's now-established two-part verification convention since spec 070's own audit.
- No drag-to-reorder for the instrument listbox - explicitly, permanently out of *this* spec (a real, separate, later piece of runtime work: a drag-handle hit-test region, drag state, and a reorder-commit capability, none of which exist yet for any list in this codebase).
- No git commit created (this whole effort's own standing instruction).

## Scope boundaries

In scope: `components/songProperties.yaml` (or a new sibling component file for the instrument listbox/banners, decided in design.md), `components/songPatternList.yaml` (made real), `domain/song/index.js` (pattern-table mutations, instrument-row publishing, several new thin spinbox capabilities), `domain/playback/index.js` (BPM, mod-name write direction, the load-time publish extension), `domain/sampleEditor/index.js` (republishing instrument rows on a name edit), `capabilities.js`, and tests for all of the above.

Out of scope, recorded rather than silently dropped:

- **Instrument-row drag-to-reorder** - see Non-functional requirements above; `runtime/componentTypes.js`'s own `reorderable` property stays declared-but-unwired.
- **The pattern-sidebar song browser** (`patternSidebar.js`) - a separate, later, larger initiative (spec 070's own step 10), sharing no code with this spec's own instrument listbox despite both being "a real row list."
- **`UI.setInfo()`'s own status-bar echo** on a mod-name edit - no v2 status-bar mechanism exists to echo into; the real state field (`song.title`) updating is the acceptance criterion, not a secondary UI echo.
- **The tracker banner's own ASCII-art version-text content** (`_buildSteffestVersion()`) - ported as "whatever image asset it resolves to," not hand-transcribed; if no such asset exists as a plain sprite (unlike the four confirmed-present PNGs), the toggle still works, simply with no distinct "active" image, and this is recorded rather than blocking the whole banner piece.
