# 032 — Renderer performance

Date: 2026-09-11. Kind: feature. Status: specified. Package **P8** of spec [010](../010-port-roadmap/requirements.md), the port roadmap, following P7 (specs [030](../030-pattern-grid/requirements.md)/[031](../031-keyboard-note-entry/requirements.md), now closed) - "the first workload worth measuring," per the roadmap's own design.md.

## Purpose

`renderers/canvas/mountGeneric.js` currently draws synchronously, every time: a pointer drag, a state-store write, a keystroke, a resize - each calls `draw()` or `relayout()` (a full layout recompute plus draw) directly, on the spot, with no coalescing. During playback, `domain/playback/index.js`'s own per-frame position sampler can write two state fields in the same animation frame, each independently triggering a full redraw - twice the work for one frame's worth of change. The canvas also always renders at `window.devicePixelRatio`, unconditionally, where v1 defaults that off and makes it an explicit opt-in. Nothing here fails today because nothing in the generated application yet does enough at once to make it visible - which is exactly why the roadmap places this package after P7, the first workload (a 20-plus-row, several-track grid, redrawn on every scroll and keystroke) large enough to be worth measuring.

## Alignment with product vision

[product.md](../product.md) lists "canvas rendering, tracker performance" among the things that are "essential, not optional demonstrations" of this project's value proposition, and names "automatic layout... traceability" as core direction - a renderer that redraws twice for one change, or spends cycles on pixel density nobody asked for, undermines the first without anyone noticing until a real screen exercises it.

## Research basis

Read for this spec: `script/src/ui/ui.js`'s main render loop (`render()`, its `skipRenderSteps`/`maxRenderFps` frame-rate governance, `me.scaleToDevicePixelRatio()`, and the `EVENT.clockEventExpired` auto-throttle listener at the bottom of the file) and `script/src/ui/optionsPanel.js:97-99` (the "Screen refresh" radio group, `UI.skipFrame(index)` - the item's own list index *is* the skip count). `renderers/canvas/mountGeneric.js`'s current `draw()`/`relayout()` call sites (about 20, each synchronous) and `recomputeLayout()` (unconditional `window.devicePixelRatio`). `domain/playback/scheduler.js`'s `onMissedDeadline` option and `domain/playback/README.md`'s own divergence #2 ("reports a missed deadline through a callback rather than a global event") - built by spec 012, never wired to anything since nothing needed it yet. `app.yaml`'s already-authored, currently-mocked "Screen refresh" `radioGroup` (`optionsPanel.yaml:57-66`, values Smooth/Normal/Economical/Low CPU) and "Optimize High DPI" `checkbox` (`optionsPanel.yaml:68-71`).

Two things the design sketch names that research shows are already partly true or need correcting:

- **v1's `useDevicePixelRatio` defaults to `false`.** v2's store already seeds `high-dpi.active: false` to match - but the renderer ignores the field entirely and always scales to the device's real pixel ratio. The fix is not "add an option"; it is "start reading the option that already exists and already defaults correctly."
- **The "Screen refresh" mock is a no-op.** `screenRefreshSet.js`'s generated mock cycles through a `values` array the compiler could not populate (a `radioGroup`'s command payload is the clicked item's label string, not an enumerable boolean/index the mock generator knows how to guess), so clicking any of the four options today writes nothing useful. A real capability is needed, not because the field is unwired, but because the *existing* mock is silently broken for this one shape of control.

## Requirements

- **PERF-001 — Every draw-triggering event is coalesced into at most one draw per animation frame:** As a user, dragging a slider, scrolling the grid, or a keystroke each still updates the screen, but N triggers within one frame produce one `draw()` call, not N. Acceptance: replacing every direct `draw()`/`relayout()` call site with a `markDirty()`/`markNeedsRelayout()` request, firing a pointer-move/drag burst of 10 synthetic inputs within one frame produces exactly one draw (a controller-level or `computeGenericLayout()`-level test, not a browser frame-timing measurement, since the environment cannot make one).
- **PERF-002 — The canvas goes idle after settling, and there is no perpetual redraw loop:** As stated in the roadmap's own acceptance. Once nothing is dirty, the coalescing mechanism stops requesting further animation frames rather than polling "am I dirty?" forever at 60Hz. Acceptance: after the last of a burst of inputs, exactly one more animation-frame callback fires (the one that draws and finds nothing new dirty); none after that until something changes again - mirrored on the existing `startAnimationClock`/`stopAnimationClock` pattern spec 017 already uses for sprite animation, not a second, always-running loop.
- **PERF-003 — A frame-rate cap keeps a high-refresh-rate display from rendering faster than intended:** As ported from v1's own `maxRenderFps` (default 60): a draw that would fire sooner than `1000/maxRenderFps` ms after the previous one is deferred to the next opportunity, not dropped. Acceptance: on a simulated 120Hz callback cadence, actual draws happen at no more than 60 per second.
- **PERF-004 — "Screen refresh" (frame skipping) is real, not a broken mock:** As a user, choosing Smooth/Normal/Economical/Low CPU in the options panel sets how many animation frames are skipped between actual draws (0/1/2/3, the item's own position in the list, exactly as v1's `UI.skipFrame(index)` already does) - a real capability replacing the currently-no-op mock. Acceptance: selecting "Low CPU" and then dirtying the canvas causes a draw only on every 4th eligible frame, not every one.
- **PERF-005 — A missed audio-scheduler deadline automatically throttles the frame rate:** As ported from v1's `EVENT.clockEventExpired` listener (`ui.js:607-618`): `domain/playback/scheduler.js`'s existing (currently unwired) `onMissedDeadline` callback is connected, through a v2-native registration point rather than a `tracker.js` edit (see design.md's "one door" note), to the same skip-count "Screen refresh" already governs. Every missed deadline escalates the skip count by one, capped at 4 (one step past the UI's own highest manual option, matching v1 exactly) - *unless* it arrives less than two seconds after the last escalation, in which case it is ignored outright (v1's own `prevEventExpired` gate: the cooldown is measured between escalations, not between raw events, so the very first missed deadline always escalates immediately). Acceptance: one `onMissedDeadline` call raises the skip count by one immediately; a second call less than two seconds later does not raise it again; a third, more than two seconds after the second, does; the count never exceeds 4.
- **PERF-006 — devicePixelRatio scaling is an explicit, off-by-default option:** As a user, canvas rendering is at 1 logical pixel per CSS pixel unless "Optimize High DPI" is checked, matching v1's own `useDevicePixelRatio = false` default (v2's store already seeds `high-dpi.active: false`; only the renderer's own read of it is missing). Acceptance: with the option off (the default), `canvas.width`/`height` equal the element's CSS size with no DPR multiplication; turning it on multiplies both by `window.devicePixelRatio`, exactly as today's unconditional behavior already does.
- **PERF-007 — No regressions:** Acceptance: the unit suite passes; every existing interaction (drag, wheel, click, keydown) still visibly updates the screen - coalescing changes *when* a draw happens, never *whether* one does; the workbench's Inspect/Interact preview is not treated differently from a generated application (both share `mountGeneric.js`).

## Non-functional requirements

- **Architecture.** No new capability boundary: the frame-skip count is a plain state-store field (`screen-refresh.value`, already authored, already declared) written by a new, small capability (`setScreenRefresh`) and, separately, by the playback capability's own missed-deadline handler - the same "one shared number, two writers" shape v1's own single `skipRenderSteps` variable already has. `domain/playback/scheduler.js` gains one small extension point (a default-handler registration), not a change to `engine/tracker.js`, which stays under its own "byte-identical, three divergences" invariant.
- **Performance.** This spec is itself about performance, but its own acceptance is behavioral (coalescing happens, the cap holds, the loop stops), not a measured frame time - this environment has no real canvas/browser to measure paint cost in, the same gap every prior spec since 019 has recorded. Per-node dirty regions or per-element buffers (the design sketch's *second*, measurement-guided step) are explicitly not attempted here for exactly that reason - see Scope boundaries.
- **Reliability.** Coalescing must never drop a draw that was actually requested; a dirty flag set while a frame is in flight is picked up by the frame that follows, not lost.
- **Usability.** The two options-panel controls this spec finishes wiring (Screen refresh, Optimize High DPI) already exist and are already labeled; nothing new is authored.
- **Security.** Not applicable; no new input surface.

## Scope boundaries

In scope: coalescing every `draw()`/`relayout()` trigger into one per animation frame with an idle-when-settled stop condition; the frame-rate cap; wiring `screen-refresh.value` to a real, working skip-count capability; wiring the scheduler's `onMissedDeadline` to the same skip-count automatically; making `high-dpi.active` control the renderer's own DPR scaling, defaulting off.

Out of scope, recorded rather than dropped: per-node dirty regions or per-element offscreen buffers (v1's own answer, "one known-good answer but not the only one" per the roadmap's own words) - deferred until a real measurement (a browser-capable environment, still absent here) shows the single-coalesced-full-redraw approach is not enough; unifying the sprite-animation clock (spec 017) and this spec's own coalescing loop into one shared `requestAnimationFrame` driver - both already have independent, working start/stop lifecycles, and merging them is a refactor with no acceptance criterion requiring it; any change to `domain/playback/engine/tracker.js` itself, which is v1-ported code under its own "nothing else" divergence rule.
