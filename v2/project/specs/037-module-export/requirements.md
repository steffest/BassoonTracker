# 037 — Module export: saving a MOD, readable by v1

Date: 2026-09-13. Kind: feature. Status: specified. Continues package **P9** (persistence, providers, file operations) of the [port roadmap](../010-port-roadmap/requirements.md), following spec 036 (the disk-operation screen: loading a module). Delivers the one clause of P9's own stated acceptance nothing has touched yet: "exports are readable by v1."

## Purpose

Reading `script/src/editor.js`'s `buildBinary`/`save`, `script/src/fileformats/protracker.js`'s `write`, `script/src/fileformats/fasttracker.js`'s `write`/`writeXI`, `script/src/audio/riffWave.js`, `script/src/models/playlist.js`, and `script/src/filesystem.js`'s full `BinaryStream` in full (research pass, not assumed from the roadmap's own design sketch - see "What v1 actually does" for two real corrections that reading produced) found that "the format write path" is five genuinely separable pieces of different sizes and different dependencies: MOD export, XM export, sample export (WAV/RAW/XI), playlist export (PLS/M3U/JSON), and MP3 export. This spec takes the first: **MOD export**, because it is the smallest correct, complete, already-fully-unblocked slice (`domain/song`/`domain/playback` already expose everything `ProTracker().write()` reads), and it is the one export format that directly and simply proves P9's own acceptance clause - a file this port writes, that v1 can load back unchanged.

## What v1 actually does (read from source, not assumed)

- **`Editor.buildBinary(type, next)`** (`editor.js:625-641`) is a real, full re-serialization of the in-memory song - not a shortcut, and not dependent on the song never having been edited. It dispatches to `ProTracker().write(next)` for a `.mod` or `FastTracker().write(next)` for a `.xm`, based on `Tracker.inFTMode()`. `Editor.save(filename, target)` (`editor.js:489-516`) wraps the result in a `Blob` and either hands it to a caller-supplied function, `Dropbox.putFile`, or `script/src/filesystem.js#saveFile` (a plain `<a download>` click - the browser's own save-as).
- **`ProTracker().write()`** (`protracker.js:204-328`) computes the exact output size up front, then writes: a 20-byte title, 31 fixed 30-byte instrument headers (name/sample-length-in-words/finetune/volume/loop-start/loop-length - a missing instrument slot writes 30 zero bytes, not nothing), the song length and a fixed restart byte (127, unused by any player), a 128-byte pattern-order table, the format magic (`"M.K."` or `"8CHN"` for an eight-track module), every pattern's rows packed into 4-byte MOD note words (`(upperInstrumentNibble<<24)+(period<<16)+(lowerInstrumentNibble<<12)+(effect<<8)+param` - the same `>15`-instrument nibble-split the loader already reverses), then every instrument's raw 8-bit sample data (`Math.round(d*127)`, matching the engine's own load-side `/127` convention `domain/playback/README.md` already documents as a divergence-preserving quirk, not `/128`). More than 31 instruments truncates with a UI warning; this spec has no UI warning surface yet, so it logs instead - see Decisions.
- **v1's `BinaryStream` (`script/src/filesystem.js:57-218`) is one object with both read and write halves.** `domain/playback/engine/filesystem.js` (spec 012) kept only the read half, deliberately, since `player/src` never writes. Every write method (`writeByte`, `writeUByte`, `writeUint`/`writeLong`/`writeDWord`, `writeWord`, `writeString`, `writeStringSection`, `clear`, `fill`) is entirely absent from v2 today - a real prerequisite, the same shape spec 035's `fileBrowser` was a prerequisite for spec 036's screen.
- **`Tracker.getFileName()`** (`script/src/tracker.js:2468-2471`, UI-only code, not part of `player/src`/`domain/playback/engine/`) falls back to a slugified title with a `.mod` extension when the loaded song carries no `filename` of its own. `song.filename` itself *is* set by the ported, playback-only `Tracker.processFile` (`player/src/tracker.js:1884`, confirmed present in `domain/playback/engine/tracker.js` too), so this spec only needs the small fallback function, not a new data field.
- **Two corrections to the roadmap's own framing, found only by reading the code:**
  1. P9's design sketch lists "XI, WAV, the playlist formats, and the container formats" as the write path, implying MOD/XM are somehow already out of scope or already done - they are not; `Editor.save` (module export) is a real, working, currently-unaddressed v1 feature, and the most direct thing to check "exports are readable by v1" against.
  2. "The container formats" (the sketch's own phrase) has no write-side referent at all: `zip`/`gzip` in v1 (`fileformats/detect.js`, `tracker.js:2091-2215`) are exclusively used to *open* an archive someone loads, never to produce one. Nothing in the save/export path touches them. This clause of the roadmap's own design sketch is corrected here rather than carried forward unexamined.
- **A second, unreachable MP3 path exists in `editor.js` itself** (`window.renderToMp3`, `editor.js:957-1056`), dynamically importing `lamejs` from a CDN at call time - dead code, never called from any authored screen (the real MP3 path is `BassoonProvider.renderFile`, already documented in specs 033/034 as going through a server-side `lame.exe`). Recorded so a later spec does not mistake it for a second thing to port.

## Decisions and assumptions

- **A new, write-only `BinaryStream`, not an extension of the read-only ported one.** `domain/playback/engine/filesystem.js` is under `domain/playback/README.md`'s own "byte-identical to `player/src`, three divergences, nothing else" rule; adding write methods there would be a fourth, unrecorded divergence for a concern that engine never had. `domain/moduleExport/binaryWriter.js` is new v2 code (this functionality was never part of `player/src`, so there is nothing to diverge *from*), porting only the write-side methods `ProTracker().write()` actually calls (`writeByte`, `writeUByte`, `writeUint`, `writeWord`, `writeString`, `writeStringSection`, `clear`, `fill`) - no read methods, since export never reads.
- **A second documented exception, alongside `domain/song`'s own.** `domain/moduleExport/index.js` imports `Tracker` directly from `domain/playback/engine/tracker.js`, the same live singleton `domain/song/index.js` already reaches for the identical reason: the exported bytes have to come from the exact song/instrument objects the engine holds, not a copy. Recorded in both READMEs, matching the precedent's own wording.
- **`.mod` only; `.xm` is a real, explicit no-op for this spec, not a silent wrong export.** Porting `FastTracker().write()` (roughly twice `ProTracker().write()`'s own size, plus delta-encoded sample data and full envelope/vibrato instrument blocks) is a separate spec's work. When `Tracker.inFTMode()` is true, this spec's capability logs that XM export is not yet supported and does not produce a file - silently exporting a `.mod` from XM-mode song data would lose every instrument's envelope/panning/multi-sample information and is not "readable by v1" in any meaningful sense.
- **No format/target picker UI.** `script/src/ui/diskOp_Save.js`'s own type/format/target radio panels are real UI work this spec does not attempt (P9's own disk-operation-screen slice already exists for *loading*; a save screen is a separate future spec). Instead, this spec wires the File menu's own `saveFile` item - authored since the application's first cumulative spec, currently an `unresolved-action-reference` no-op - to a real command, the smallest reachable surface that already exists.
- **`saveFile` needs one word added to `compiler/recipes.js`'s existing `verb-action` recipe** (`clear|copy|paste|insert|delete|increment|decrement` → `+ save`), not a new recipe shape. This is the one exception to every prior spec since 033's own "no compiler change" - unlike those, which reused an already-authored, already-working vocabulary, nothing in the current recipe set can express "save file" as a one-shot, no-value command, and the `verb-action` recipe already exists for exactly this shape. Recorded explicitly as this spec's one compiler-adjacent change, not silently folded in.
- **The browser's own download, not `saveFile()` ported as a second function.** `Blob` + `URL.createObjectURL` + a synthetic `<a download>` click is plain browser API, not v1-specific code to port; `domain/moduleExport/index.js` does this directly, the same shape v1's own `script/src/filesystem.js#saveFile` already is.

## User stories and acceptance

- **EXPORT-001 — MOD export re-serializes the loaded song exactly.** `domain/moduleExport/protracker.js#write(Tracker)` (pure function, testable without a DOM) produces bytes that a second pass of `domain/playback/engine/fileformats/protracker.js`'s own **read** function can load back, reporting the same title, instrument count/names/volumes/finetunes/loop points, pattern table, pattern data (notes/instruments/effects/params) and sample data (within the 8-bit round-trip's own precision) as the original. Acceptance: a round-trip unit test - load a real fixture, write it, re-load the written bytes, compare the two in-memory songs field for field.
- **EXPORT-002 — More than 31 instruments truncates, not crashes.** A song with instrument slots beyond 31 exports only the first 31, matching v1's own truncation (minus the UI dialog, which becomes a logged message - no dialog surface exists to reuse here). Acceptance: a unit test with a song fixture (or a hand-built one) carrying more than 31 instrument slots.
- **EXPORT-003 — The File menu's Save item is real.** `compiler/recipes.js`'s `verb-action` recipe recognizes `save` alongside its existing verbs; `app.yaml`'s already-authored `saveFile` click resolves to command `file.save`, mapped in `capabilities.js` to `domain/moduleExport/index.js#exportModule`. Acceptance: `node compiler/generate.js` reports no `unresolved-action-reference` for `saveFile`; a unit test for the recipe change itself.
- **EXPORT-004 — XM mode is a clean no-op, not a wrong file.** Invoking export while `Tracker.inFTMode()` is true produces no download and logs why. Acceptance: a unit test asserting no writer runs and a log entry is produced.
- **EXPORT-005 — No regressions.** Full unit suite passes; `node build.mjs app`/`dist` succeed; `saveFile` leaves the unresolved-action-reference list in `app/LOOSE-ENDS.md`.

## Non-functional requirements

- Headless verification only (no browser-automation dependency in this environment, the same recorded reason every spec since 019 has given) - the actual browser download trigger (`URL.createObjectURL`/`<a download>`) is exercised nowhere near a test; `exportModule`'s own pure byte-production (`protracker.js#write`) is what is actually verified, matching how `domain/playback/index.js#loadModule`'s own DOM-only tail (nothing, in that case) has never needed a browser test either.
- One recorded compiler-adjacent change (`compiler/recipes.js`'s verb list) - see Decisions.

## Scope boundaries

In scope: `domain/moduleExport/{binaryWriter,protracker,index}.js`, a `README.md`, the `compiler/recipes.js` verb addition, the `capabilities.js` mapping, and tests for all of the above.

Out of scope, recorded rather than silently dropped:

- **XM export** - a real, separate, roughly-twice-the-size port (delta-encoded sample data, full instrument envelope/vibrato blocks); a later spec.
- **Sample export** (WAV 8/16-bit, RAW, XI instrument) - depends on an instrument-slot/sample-editor UI concept this port does not have authored yet; a later spec. `riffWave.js#encodeRIFFsample`'s own hardcoded 8kHz declared sample rate (real, load-bearing, already read in full) is recorded for whichever spec takes this up.
- **Playlist export** (PLS/M3U/JSON) - depends on a playlist model/domain this port does not have at all yet (spec 036 deferred loading a playlist for the same reason); a later spec.
- **MP3 export** - the vendored-encoder open decision (already resolved in spec 010's own requirements) remains unimplemented; a later spec, and not `editor.js`'s own dead, CDN-fetching `window.renderToMp3` path either way.
- **A save/export screen** (format/target pickers) - `script/src/ui/diskOp_Save.js`'s own UI; a later spec, once more than one export format exists to choose between.
- **Dropbox/local-file save targets** - unchanged from specs 034/036's own scope boundaries; this spec's one reachable target is the browser's own download.
