# 048 — Nibbles screen prerequisites

Date: 2026-09-14. Kind: feature. Status: specified. Continues package **P10** (features and the plugin path) of the [port roadmap](../010-port-roadmap/requirements.md), following spec 047 (the Nibbles engine and grid). The same two-step split specs 023/024, 025/026 and 041/042 already used: a mechanism lands first, the screen it unlocks lands next (spec 049).

## Purpose

Spec 047 built `nibblesGrid` - registered, but authored nowhere. Before it can be, this spec closes a real gap found while researching where it should mount: Nibbles does not fit into `top-view.value`, the mechanism the sample editor's own three panels already share.

## What v1 actually does, and what this narrows out (read from source, not assumed)

Opening Nibbles (`app.js`'s own `COMMAND.nibbles` handler, 159-184) does two things in sequence: `EventBus.trigger(EVENT.showView, "main")` (a defensive reset, closing any disk-operation/options view that might be open), then `Plugin.load("Nibbles", ...)` → `Nibbles.init(...)` → `host.EventBus.trigger(EVENT.pluginRenderHook, {target: "main", ...})`. `appMainPanel.js`'s own handler for that hook (252-270) is the real takeover: it calls `this._hideMain()` (470-483), which hides the instrument list, the song list, **both pattern panels** (the pattern grid itself), the title/BPM/repeat controls - essentially all of `AppMainPanel`'s own content - and shows a new custom-rendered panel in their place. `GameControls`'s own "Exit" button (`nibbles.js:720-722`) reverses this with `EventBus.trigger(EVENT.command, COMMAND.showMain)`.

This is a **materially bigger takeover than `top-view.value`'s own swap**. `top-view.value` (spec 025/026) gates only the control-panel sub-region (`fileOperationsPanel`/`optionsPanel`/`sampleEditPanel`, alongside `editPad`/`songPatternList`/`songProperties`, which are *not* gated by it at all - they are always-visible siblings). Nibbles needs to additionally hide those three always-visible siblings too, while the menu bar/control bar/info bar stay put (v1's own `Nibbles.init` never touches those, and `GameControls`'s own layout only ever positions itself against `Layout.col*` regions, never the menu bar). `top-view.value`'s own single-field `visibleWhen` mechanism (spec 025) cannot express "hide six existing, independently-gated regions and show one new one" without a second, independent condition on nodes that already carry one - the exact same one-field-per-node limitation spec 046 found and fixed for the sample-editor panel's own third sub-view.

## Decisions and assumptions

- **A new field, `main-view.value` (`""`/`"nibbles"`), gates the whole main content area** - not a second condition bolted onto `top-view.value`'s existing nodes. `fileOperationsPanel`, `optionsPanel`, `sampleEditPanel`, `editPad`, `songPatternList` and `songProperties` (currently six direct siblings of `main`) are wrapped, unchanged, inside one new `normalMainView` panel carrying the new field's own `visibleWhen`; a new sibling `nibblesPanel` carries the opposite. This is the same "wrap existing content in a new gating panel" shape spec 045 already used for `sampleEditNormalView` - nesting instead of combining two conditions on the same node, since `visibleWhen` (spec 025) reads exactly one field per node.
- **The menu bar, control bar and info bar are untouched.** v1's own takeover never hides them either (`_hideMain()`'s own list, read in full, names none of them); `main-view.value` only wraps the six regions named above.
- **This spec authors a placeholder `nibblesPanel`, not the real screen.** Matching spec 025/026's own precedent exactly (a declared breakpoint mechanism landed with a placeholder-only control panel; the real content came a spec later): this spec's own acceptance is the swap mechanism working, proven with a minimal placeholder, not the game's own score/config/buttons.
- **Two existing loose ends are resolved here, and no others.** The View menu's own `nibbles` action (already authored, currently unresolved) is renamed `openNibbles` to resolve via the existing "open" verb (spec 045), and `showMain` (also already authored, currently unresolved) is wired to close Nibbles back to the normal view - both directly relevant to this mechanism. `showOptions`/`showFileOperations`/`showSampleEditor` (the View menu's other three unresolved siblings) are a separate, pre-existing gap this spec does not touch, the same boundary spec 022 already drew around the menu bar's own remaining unresolved items.
- **The feature registry is not wired here.** Registering Nibbles as a lazy `domain/features/index.js` tenant is the real screen spec's own concern (it is the spec that gives the feature something worth deferring); this one only builds the view-switch mechanism the eventual screen needs to appear in. Recorded rather than assumed: `nibblesGrid`'s own controller and draw kind already import `domain/nibbles/index.js` at module scope (spec 047, matching every prior specialized leaf's own precedent - `waveformView`/`loopCreatorView` do the same for `domain/sampleEditor`), so Nibbles' own engine code is already part of the main bundle regardless of the feature registry; true code-splitting of a draw kind's own domain import is a real, unaddressed limitation shared by every specialized leaf in this port, not something either this spec or the next one fixes.

## User stories and acceptance

- **NSP-001 — `main-view.value` swaps the whole main content area, not just the control-panel sub-region.** With the field `""`, every one of the six wrapped regions is present and behaves as an ordinary nested panel (each already had its own `visibleWhen`/layout rules, untouched by the wrapper - see NSP-004's own note on the one real, expected side effect of nesting one level deeper). With it `"nibbles"`, `normalMainView`'s whole subtree (all six wrapped regions) is absent from layout, draw and hit-testing, and `nibblesPanel` is present instead. Acceptance: a `computeGenericLayout()` integration test (mirroring spec 019's own convention) against the real, live `app.yaml`.
- **NSP-002 — The "Nibbles" menu action opens the view.** Renamed `openNibbles`, resolving via the existing `verb-action` "open" verb (no new compiler vocabulary) to command `nibbles.open`, which sets `main-view.value` to `"nibbles"`. Acceptance: a compiler-recipe check (empirical, per spec 036/042/045/046's own precedent) plus a capability unit test.
- **NSP-003 — `showMain` closes it.** Resolves to command `main.show` (verb-action's existing "show" is not yet a recognized verb - see design.md for which existing verb actually matches, confirmed empirically before authoring), which sets `main-view.value` back to `""`. Acceptance: a compiler-recipe check plus a capability unit test.
- **NSP-004 — No regressions.** Full unit suite passes; `node compiler/generate.js` shows no new warnings on the six wrapped regions; `node build.mjs app` succeeds with the two newly-resolved commands mapped in `capabilities.js` and no longer listed as unresolved-action-reference loose ends. One real, expected, non-regression side effect: nesting the six regions one level deeper than a direct child of `main` costs exactly one more panel's own padding on each side (`runtime/genericLayout.js`'s own `PADDING`, applied consistently at every nesting depth - not a bug, and not specific to this spec, since spec 045's own `sampleEditNormalView` wrapper already did the same to its own contents without being flagged as a regression). No control's own authored `fixed` size changes; only a `fill` dimension's own resolved pixel count shrinks by that one padding level.

## Non-functional requirements

- Headless verification only (no browser-automation dependency in this environment, the same recorded reason every spec since 019 has given) - the layout-rect comparison is the empirical proof this spec relies on, the same role spec 019's own "no Playwright" gap already established this convention for.
- No new component type, no new draw kind - `normalMainView`/`nibblesPanel` are plain `panel` nodes.

## Scope boundaries

In scope: `project/specs/application/current/app.yaml` (wrapping the six regions, adding the placeholder `nibblesPanel`, renaming `nibbles` to `openNibbles`), two new `domain/nibbles/index.js`-adjacent capability functions (see design.md for which module owns them), `compiler/recipes.js` only if an empirical check finds a real gap (not assumed), two new `capabilities.js` mappings, and tests for all of the above.

Out of scope, recorded rather than silently dropped:

- **The real Nibbles screen** (score/lives display, the difficulty/wrap/grid config controls, Start/Exit/HighScore buttons, the info overlay, the high-score table's own visual list) - spec 049's own.
- **The feature registry / lazy loading** - see Decisions and assumptions; a real, already-existing, port-wide limitation this spec does not fix.
- **`showOptions`/`showFileOperations`/`showSampleEditor`** - a separate, pre-existing gap, not touched here.
- **The "SKIP"/"TRITON" cheat codes** - already deferred by spec 047.
