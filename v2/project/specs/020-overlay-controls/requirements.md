# 020 — dropdown, submenu, modalDialog

Date: 2026-09-11. Kind: feature. Status: specified. Implements the fourth implementing cluster of package **P5** of spec [010](../010-port-roadmap/requirements.md), the port roadmap, following spec [017](../017-leaf-types/requirements.md) (leaves), spec [018](../018-value-controls/requirements.md) (value controls) and spec [019](../019-listbox/requirements.md) (listbox).

## Purpose

Spec 016 grouped `dropdown`, `submenu` and `modalDialog` as "the overlay-dependent trio, building on the overlay/modal mechanism specs 013 and 015 already shipped and verified." All three need a control that is not laid out in its authored position: a dropdown's popup list, a submenu's flyout, and a dialog's centred box all have to appear above everything else, take input exclusively while shown, and go away again. Spec 013 built the layout half of that (`layer: "overlay"`, `modal: true`, always centred, always present) and spec 015 built the input half (Tab trapped inside a modal, Escape/Enter cascaded to it) - both verified only against a hand-built throwaway type that was *always* in the tree, because nothing yet needed one that comes and goes.

That is the one real gap this cluster closes: nothing in v2 can currently show or hide an overlay at runtime. A `modalDialog` authored in a tree today would be permanently open and would permanently swallow all input, which is not what any of the three types need. Making an overlay's presence a runtime fact - open or closed - is this spec's one piece of new mechanism; everything else (anchoring the layout, wiring the input) is built to need nothing further from spec 013/015's own mechanism.

## Scope decision

`menu` itself is not promoted by this spec. Spec 016 already said `submenu`'s promotion depends on `menu`'s, and that deciding to promote both together is a later spec's call, not this one's - that stands. `submenu` is implemented here as a self-contained flyout (open/close, hover-to-preselect, click-to-execute, disabled items), verified the same way spec 013/015 verified the modal mechanism itself: against a hand-built tree that opens it directly, since nothing else can trigger it yet. Wiring it under a real `menu` is `menu`'s own future promotion, not this spec's.

Nested submenus (an item inside a submenu opening a second, nested submenu) are v1 behaviour (`Submenu.activateSubmenu`) that this spec does not carry forward. The anchored-overlay mechanism below generalizes to it without changes, but there is no trigger to open one against yet outside a hand-built test tree, and building a second layer of flyout on spec-of-a-spec would be shaping the mechanism to a guess rather than a real need. Flagged, not built.

`tooltip` (component type), `tabPanel`, `collapsePanel` and `buttonGroup` are untouched; they are P5's composition cluster, next in the roadmap's dependency order, not this one's.

## User stories and acceptance

- **OVL-001 — An overlay can be shown and hidden at runtime:** As a renderer, any `layer: "overlay"` node can be open or closed; closed means it is absent from layout, paint and hit-testing exactly as if it were not in the tree at all, and open means exactly what spec 013 already verified. Acceptance: `computeGenericLayout`'s new `overlayOpen` option, when it returns false for a node, removes that node (and its subtree) from the `overlays` list and leaves no rect/clip for it or its descendants; the option's default keeps every existing caller - including spec 013/015's own hand-built-tree tests - working unchanged.
- **OVL-002 — An overlay can be anchored to another node instead of centred:** As an author of the mechanism (not of YAML - nothing authors this directly), a popup can be positioned against the rect of the control that opened it, on a declared edge, flipping to the opposite edge when it would overflow the viewport and clamping along the cross axis so it never runs off either side. Acceptance: `below`/`above`/`right`/`left` anchoring, each verified for the normal case and the flip.
- **OVL-003 — A dropdown opens a popup of its items and closes again:** As a user, clicking a closed dropdown opens a popup listing its `items`, anchored below it (or above, if below would overflow); clicking an item selects it (0-based index in the same bound `field` valueFieldOf already resolves) and closes the popup; clicking anywhere else while it is open, or pressing Escape, closes it without changing the selection. Acceptance: open/select/close and open/dismiss both leave the field in the expected state, and closing never leaves the popup double-counted in a later relayout.
- **OVL-004 — A submenu opens, previews on hover and executes on click:** As a user (of a hand-built tree, since `menu` does not open one yet), hovering an item preselects it, clicking a non-disabled item runs whatever command binding it carries and closes the submenu, and clicking a disabled item does nothing. Acceptance: hover/click/disabled all verified against the controller directly; a real command binding on an item fires through the existing generic `dispatch()` path with no submenu-specific case there.
- **OVL-005 — A modal dialog shows a message, optional OK/Cancel and an optional text field, and both Escape and Enter close it:** As a user, an open `modalDialog` draws its background dimmed, its message, and synthesized OK/Cancel buttons and a text field for whichever of `ok`/`cancel`/`input` it declares; clicking OK, clicking Cancel, pressing Enter or pressing Escape all close it, each reporting which one happened (and the text field's value, if it had one) through a `close` dispatch on the dialog node. Acceptance: all four dismissal paths close the dialog and report the right result; a dialog with none of `ok`/`cancel`/`input` still shows its message and still closes on Escape/Enter.
- **OVL-006 — No regressions:** Acceptance: the unit suite passes; every other interactive type's click/drag/wheel/keyboard routing, and spec 013/015's own hand-built-tree overlay/modal mechanism, are unchanged for a caller that does not use the new `overlayOpen` option or an anchor.

## Non-functional requirements

No component type is checked by name outside `runtime/componentTypes.js`, `runtime/skinModel.js` and `renderers/canvas/drawKinds.js` (spec 009's own rule, enforced by `componentTypes.test.js`'s scanning test). Every generic addition in this spec - opening/closing an overlay, closing one after an activation inside it, anchoring its rect - is gated on a registry fact (`.modal`, `.layer`) or a behavior name (`"dropdown"`, `"list"`, `"submenu"`), never on `node.type === "..."`.

Synthesized structure - a dropdown's popup, a dialog's OK/Cancel/input - is built once, in a pure function with no DOM or canvas access, from the same node shape `runtime/components.js` already produces, so it is unit-testable exactly like every other `runtime/` module and needs nothing from the compiler.

## Scope boundaries

In scope: the `overlayOpen` layout option and anchored-overlay positioning (`runtime/genericLayout.js`); overlay synthesis for a dropdown's popup and a dialog's OK/Cancel/input (new `runtime/overlaySynthesis.js`); a submenu controller (new `runtime/submenuController.js`); `renderers/canvas/mountGeneric.js`'s open/close API and the generic auto-close-after-activation rule; draw kinds for all four (`dropdown`, `dropdownPopup`, `submenu`, `modalDialog`); promoting `dropdown`, `submenu` and `modalDialog` to `implemented: true` with a `dropdownPopup` entry added for the synthetic type; `compiler/emit.js`'s state-field seeding for a dropdown's own field.

Out of scope: promoting `menu`; nested submenus; any authored use in `app.yaml` (nothing currently authors any of the three); a compiler-side vocabulary for opening a `modalDialog` from an action (an application still opens one by calling the renderer's `openOverlay` directly, exactly as nothing yet authors `reorderable` on a listbox); real keyboard operation of an open dropdown/submenu (arrow-key preselection, Enter-to-choose) beyond what Tab/Escape already give every interactive node - `listController`/the new submenu controller do not handle `keydown` at all, matching listbox's own already-recorded gap. Browser verification: not performed, for the same reason spec 019 recorded none - this environment still has no Playwright/Chromium install (checked again for this spec); verification here is the unit suite plus direct `computeGenericLayout()`/controller-level integration tests.
