# 035 — Disk-operation screen prerequisites: the fileBrowser component

Date: 2026-09-13. Kind: feature. Status: specified. Continues package **P9** (persistence, providers, file operations) of the [port roadmap](../010-port-roadmap/requirements.md), following spec 034 (remote providers). Prerequisite for the disk-operation screen, the same two-step split specs 023/024 (menu bar) and 025/026 (control panel) already used: a mechanism lands here, the screen it unlocks lands in the next spec.

## Purpose

Reading `script/src/ui/diskOperations.js` in full (again, for this spec - spec 034 already read it once to scope the provider capability) surfaced the one real, load-bearing gap: v1's `ListBox` (`script/src/ui/components/listbox.js`) is driven imperatively (`setItems(items)`, called from JS whenever the data changes) and diskOperations.js flattens a live, lazily-expanded tree into that flat array itself (`addListatLevel`, `diskOperations.js:278-295`) every time something expands, collapses, or a remote page finishes loading. v2's own `listbox` type (spec 019) has no equivalent: its items are authored YAML children, a fixed set fixed at compile time - the opposite of what a remote catalog browser needs, where the row count is unbounded, unknown until fetched, and changes at runtime.

This is the same shape of gap package P7 hit for the pattern grid (spec 030): a node count that cannot be authored, needing a specialized-component leaf instead of a generic container. This spec is that leaf for disk operations - `fileBrowser` - built the same way patternGrid was: one leaf node, its own controller and draw kind, verified against a hand-built tree with no screen authored yet.

## What v1 actually does (read from source, not assumed)

- **`ListBox` renders a flat array of rows**, each `{label, data, level, index, icon, info}` (`diskOperations.js:287`), with indentation by `level` and an icon chosen per-row (an item's own `icon`, or a view-wide default, or `"disk"` for an unexpanded branch). It does not understand hierarchy at all; `diskOperations.js`'s own `addListatLevel`/`toggleDirectory` (`diskOperations.js:278-295,680-710`) own the recursion, calling `listbox.setItems()` again after every expand/collapse/fetch.
- **Selection and scroll are independent state** inside `ListBox` (`_selectedIndex`, `_visibleIndex`), exactly the two concerns spec 019's own `listbox` already keeps apart (`field` for selection, a derived `scroll.<id>` field for offset) - this spec's `fileBrowser` keeps that same separation, since nothing about v1's own behavior asks for anything different.
- **A row's icon is drawn from a small fixed vocabulary** (`"module"`, `"sample"`, `"disk"`, `"playlist"`, or an item's own declared icon/`iconsmall`) - resolved once per row at flatten time, never per-frame; this spec's draw kind resolves an icon the same way `image`'s own draw kind already does (`imageAsset(assets, null, explicitName)`, already supporting a name that is not a node's own authored property), so no new skin mechanism is needed, only a per-row explicit name instead of a per-node one.
- **`ListBox` supports drag-to-reorder**, unused by disk operations and already recorded as deferred by spec 019's own scope decision - not touched here either.

## Decisions and assumptions

- **A specialized leaf, not an extension of `listbox`.** `listbox`'s contract (`container: { childrenIn: "items" }`) means every row is a real child node with its own id, style and layout rect - fine for a handful of authored rows, wrong for an unbounded, runtime-changing catalog listing (hundreds of entries once a genre is expanded, an unknown count before the first fetch resolves). Reusing that contract would mean synthesizing and destroying child nodes on every expand/collapse/page load - a kind of dynamic-node-count layout mechanism v2 has never needed and this spec does not want to invent when patternGrid's own precedent (a leaf, procedurally drawn, node count fixed regardless of song size) already solves exactly this shape of problem.
- **Rows come from one bound, derived state field** (`rows.<id>`, this spec's own equivalent of `scrollFieldOf`), holding a plain array of `{title, icon?, info?, level, hasChildren?}` - already-flattened, exactly as `addListatLevel` already flattens v1's own tree before handing it to `ListBox`. Populating that field (fetching a genre, expanding a node, publishing a leveled array) is a *capability's* job - the next spec's, once this mechanism exists - not this one's. Verified here against a directly-seeded fake state field.
- **Selection reuses the existing `field`/`change`-dispatch convention unchanged.** A clean click on row *N* writes `node.field = N` and dispatches whatever `change` action is authored, carrying `{value: N}` - the exact mechanism every other value-like control (`radioGroup`, `slider`, `listbox` itself) already uses. Nothing here decides whether row *N* is a branch (expand) or a leaf (load) - that is the bound command's job, reading the row the capability itself still holds a reference to. This keeps `fileBrowser` itself completely agnostic to what its rows mean, exactly as `listbox`'s own controller is agnostic to what its authored items are.
- **Scroll reuses the existing `scroll.<id>` field convention** (spec 019's `scrollFieldOf`, imported unchanged from `runtime/listController.js`), but the *extent* it clamps against is computed from `rows.length * ROW_HEIGHT`, not from `genericLayout.js`'s child-stacking (there are no children to stack). This is why `fileBrowser` does not declare `clips: true` and is not routed through `scrollInfoOf()`'s existing layout-based extent lookup - the same choice patternGrid already made, and for the same reason: a specialized leaf manages its own content extent because layout cannot know it.
- **A new controller, not a reused one.** `listController.js`'s own `handle()` is generic about *how* `itemIndex`/`extent` arrive (it does not care whether they come from child rects or row-height math), but three call sites in `renderers/canvas/mountGeneric.js` (`contextFor`'s "list" branch, `itemIndexAt`, and `scrollInfoOf`'s layout-based extent) are not - reworking all three to also serve a childless node would risk the same entanglement patternGrid's own design deliberately avoided by not reusing `listController`/`scrollInfoOf` either. `runtime/fileBrowserController.js` is a new, small controller with the same external shape (`{transitions, activated, blocked, handled, changed, value, scrollTo}`) so `mountGeneric.js`'s existing generic write-back (`applyValue`/`applyScroll` in `feed()`) needs only the one already-established two-behavior-name check (`"list"` or `"fileBrowser"`) extended, not a new write-back path.
- **A shared, pure geometry module** (`renderers/canvas/fileBrowserGeometry.js`, mirroring `patternGridGeometry.js`'s existing role for patternGrid/gridController), so the controller's hit-testing and the draw kind's row placement can never disagree about where a row is.

## User stories and acceptance

- **FB-001 — Declared as a specialized leaf.** `fileBrowser` is registered in `runtime/componentTypes.js`: `container: null`, no `clips`, behavior `"fileBrowser"`, draw kind `"fileBrowser"`, one property (`field`, the selected row's index). Acceptance: a test mirroring `patternGrid.test.js`'s own declaration check.
- **FB-002 — Row hit-testing agrees with drawing.** Given a rect, a scroll offset and a row count, `fileBrowserGeometry.js#rowIndexAt` returns the same index the draw kind would place at that pixel, `null` past the last row or before the first, and index math survives a scroll offset that is not a multiple of the row height. Acceptance: pure unit tests, numbers only, no canvas.
- **FB-003 — Click-to-select dispatches through the existing generic mechanism.** A clean press-release over row *N* (no drag) yields `{value: N}` from the controller, which `mountGeneric.js`'s existing `applyValue()` already turns into `node.field = N` plus a `change` dispatch carrying `{value: N, from: <previous>}` - no new dispatch code, only the controller and the geometry it uses are new. Acceptance: a controller-level test asserting the returned `value`, plus one that a drag never selects (matching `listController.js`'s own "a drag never selects" rule, ported deliberately, not by copying code).
- **FB-004 — Wheel and drag scroll clamp to the rows' own content height**, independent of the selected index (scrolling can never disturb selection, matching spec 019's own guarantee for `listbox`). Acceptance: controller tests for wheel-step, drag-to-scroll (thumb vs. background, matching `listController.js`'s own ratio/direction rules) and end-of-content clamping, all against a synthetic row count/rect, no genericLayout involved.
- **FB-005 — The draw kind renders only the visible rows, never throws, and degrades gracefully with no rows, no icon, or no assets.** Acceptance: a `patternGrid.test.js`-style fake-canvas test - `measure()` returns a floor size, `draw()` does not throw for zero rows, a row past the visible window is never drawn (asserted via a synthetic row count large enough that the fake-canvas call log would show if it over-drew), a row with no `icon` skips the image draw without throwing, and an out-of-range `selectedIndex` (e.g. after the rows array shrinks) highlights nothing rather than throwing.
- **FB-006 — No regressions.** `listbox`'s own tests, `listController.js`, `scrollInfoOf`'s behavior for `"scroll"`/`"list"` nodes, and every other draw kind are unaffected - the two touched call sites in `mountGeneric.js` (`applyScroll`'s field-selection, and one new `contextFor`/`visualStateOf` branch each) are additive, gated on the `"fileBrowser"` behavior name, never on a type name (spec 009's own rule, already enforced by `componentTypes.test.js`'s scanning test). Full unit suite passes.

## Non-functional requirements

- No YAML/compiler change, no screen authored - a runtime/renderer mechanism only, verified the same way specs 013/015/020/030 verified their own mechanisms: mounting a hand-built tree (or, where a full mount is unnecessary, calling the controller/draw kind/geometry functions directly) through the public API, never a real disk-operation screen.
- Headless verification only (no browser-automation dependency in this environment, the same recorded reason every spec since 019 has given); `renderers/canvas/mountGeneric.js` itself keeps its own long-standing gap (no test coverage at all for the mount/interaction wiring - specs 014/015/019/020/025/030/031/032 all recorded the same thing), unchanged by this spec: the additive branches there are covered indirectly, by the controller/draw-kind unit tests plus a careful hand read-through, not a new integration test.

## Scope boundaries

In scope: `runtime/fileBrowserController.js`, `renderers/canvas/fileBrowserGeometry.js`, a new `fileBrowser` draw kind in `renderers/canvas/drawKinds.js`, the `componentTypes.js`/`behaviors.js` registrations, and the small, additive `mountGeneric.js` changes (`contextFor`, `visualStateOf`, `applyScroll`'s field-selection). Tests for all of the above.

Out of scope, recorded rather than silently dropped:

- **The disk-operation screen itself** (`fileOperationsPanel.yaml`, the load/save/type/target `radioGroup`s `diskOp_Actions.js`/`diskOp_Type.js`/`diskOp_Targets.js` already show are trivial to author, and the `fileBrowser` instance they'd all feed) - the next spec, once this mechanism exists.
- **A capability that populates the `rows.<id>` field** - local static snapshots (`data/modules.json` etc.), `domain/providers/{modArchive,modulesPl,hippo}.js#browse()` (already implemented, spec 034), and the expand/collapse/lazy-load bookkeeping `diskOperations.js#toggleDirectory` (`diskOperations.js:680-710`) already shows the exact shape of - all the next spec's.
- **Loading a selected row** (`Tracker.load(item.url)`, `domain/playback/index.js#loadModule`'s own existing job) - reachable only once a screen and a capability exist to call it.
- **Drag-to-reorder** - v1's own `ListBox` supports it, disk operations never uses it, and spec 019 already deferred the same feature for the authored `listbox` type.
- **Dropbox, save/export, the format write path** - unchanged from specs 033/034's own scope boundaries.
