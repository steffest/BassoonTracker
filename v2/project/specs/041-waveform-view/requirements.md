# 041 — The waveform view

Date: 2026-09-13. Kind: feature. Status: specified. Continues package **P10** (features and the plugin path) of the [port roadmap](../010-port-roadmap/requirements.md), following spec 040 (sample processing operations). The port's third specialized-component leaf, after `patternGrid` (spec 030) and `fileBrowser` (spec 035).

## Purpose

Spec 040's own research pass already found `waveform.js` (1540 lines) "genuinely a new specialized-component candidate... arguably richer than either [patternGrid or fileBrowser]" - unbounded per-sample content, real per-pixel gesture handling, its own zoom/scroll window. That same pass also found the full file is a tangle of several independent concerns (loop-marker dragging, a range-volume fade gesture, freehand sample redrawing, individual-sample-point dragging, playback preview with an animated cursor) layered on top of the one thing spec 040's own DSP operations actually need: **a way to see the sample and select a range on it.** This spec is that one thing - drawing, zoom/scroll, and click-and-drag range selection - reading the exact `waveform.js` sections that implement it (`render`'s core loop, `zoom`/`getZoomState`/`setZoomState`, and the range-only paths of `onDragStart`/`onDrag`/`onTouchUp`), not the whole file.

## What v1 actually does (read from source, not assumed)

- **Drawing** (`waveform.js:840-915`) is a plain one-sample-per-pixel-column polyline: for each pixel `i` in `[0, width)`, `index = floor(i * zoomLength/width)`, plotted at `mid + sampleData[zoomStart + index] * -maxHeight`. No min/max envelope downsampling - a real, faithfully-reproduced aliasing limitation at high zoom-out (a loud transient between two sampled columns is simply never drawn), not a bug this spec fixes. Three horizontal guide lines (center, ±half-height) are drawn first. Cached into an offscreen canvas, redrawn only when `needsRendering` - not reproduced verbatim here since v2's own draw-kind contract already redraws only on a dirty state (spec 032's own coalescing), making a second, hand-rolled cache unnecessary.
- **The zoom/scroll window** is `{zoomStart, zoomLength}` in sample-index units (`getZoomState`/`setZoomState`, `:86-119`); `zoom === 1` (no zoom) resets the window to the whole sample every render. A pinch-style `Scrollbar` (drag the middle to scroll, drag an edge to zoom, `:132-146`) drives it in v1 - a real, second scrollbar behavior beyond what v2's own `scrollbar.js`/`listController.js` support today (thumb-drag only). Not ported here - see Decisions.
- **Range selection** (the parts of `onDragStart`/`onDrag`/`onTouchUp` not gated behind a loop/range-volume/draw-mode check, `:168-270,378-420,422-431`): a plain click-drag with nothing else active starts a new selection at the clicked sample index and extends it to the drag's current position, snapping to an 8-way slice boundary only when slices are visible (`snapToSliceBoundary`, `:60-64` - slices themselves are out of scope, so this spec never snaps); releasing normalizes a backwards drag (`rangeStart > rangeEnd` swaps them) and is the only point v1 commits the selection to its own global `UI.setSelection`. Separately, once a selection exists, its own two edge handles (`getRangeMarkerPos`, hit-tested within 5px, `:209-225`) can be grabbed and dragged to resize the existing selection instead of starting a new one, each edge clamped to leave at least 2 samples of range and never past the sample's own end.
- **Everything else in the file is out of scope, deliberately, not by omission**: loop-marker dragging (a loop-creator concern, its own later spec), the three range-volume handles (`MARKERTYPE.rangeVolume{Left,Center,Right}`, an in-place fade-ramp gesture `sampleProcessing.js`'s own `adjustVolume("fadein"/"fadeout")` already covers non-interactively), draw-mode freehand redrawing and individual-sample-point dragging (`isDrawing`/`dragSampleIndex`, only active at high zoom, a real but separate editing mode), playback preview with an animated playhead (`play`/`playSection`/`isPlaying`, needs a real design decision about how a specialized component reaches `domain/playback` - not made here), and the 8-way slice overlay (`toggleSlices`, a pure display aid with no interaction of its own).

## Decisions and assumptions

- **A specialized leaf reading `domain/song`/`domain/sampleEditor` directly**, the same shape `patternGrid` already established (not `fileBrowser`'s - that one is data-source-agnostic by design; a waveform view is tied to exactly one thing, "the current instrument's sample," the same way patternGrid is tied to exactly one thing, "the current pattern"). No bound `field`, no new mountGeneric.js write-back path - the controller and draw kind both call `domain/song#getCurrentInstrument()` and `domain/sampleEditor#getSampleSelection()`/`setSampleSelection()` directly, mirroring `gridController.js`'s own already-established "reads/writes its own domain directly, returns no `value`/`scrollTo`" contract.
- **The zoom/scroll window lives in the controller's own local state** (`zoomStart`/`zoomLength`), not a derived `scroll.<id>` field - the same choice `gridController.js` already made for patternGrid's own horizontal pan window (`startTrack`): this is ephemeral view navigation, not data, and nothing outside this one component needs to read or persist it.
- **No pinch-zoom scrollbar.** Panning is a plain wheel gesture (matching every other scrollable component's own wheel convention in this codebase); zooming is a modifier-held wheel gesture (`ctrlKey`, the exact mechanism `gridController.js` already reads `pointerModifiers.ctrl` for, reused rather than invented) rather than v1's own drag-the-scrollbar-edge gesture, which needs a real scrollbar-behavior extension this spec does not attempt.
- **Selection updates live during a drag, not only on release.** v1 itself already draws the in-progress selection live and only commits to its own *global* selection concept on release; since `domain/sampleEditor`'s own selection *is* what this component's draw kind reads for highlighting (there is no separate "global selection" concept to defer to), writing to it on every drag step and again, normalized, on release is simpler than maintaining a second, parallel "live" selection just to defer the one write - and matches what a user visually expects (the highlighted range tracks the drag in real time).
- **No slice snapping.** `snapToSliceBoundary` only ever activates when the slices overlay (`toggleSlices`, out of scope) is visible; without it, v1's own function already reduces to a plain `Math.round`, so there is nothing to port beyond ordinary rounding.

## User stories and acceptance

- **WAVE-001 — Declared as a specialized leaf.** `waveformView` is registered: `container: null`, no `clips`, its own behavior and draw kind, no bound property. Acceptance: a `patternGrid.test.js`-style declaration test.
- **WAVE-002 — Hit-testing agrees with drawing.** A shared, pure geometry module converts a pixel position to a sample index and back, using the same `{zoomStart, zoomLength}` window the draw kind renders with, so a click always lands where it visually appears to. Acceptance: pure unit tests, numbers only.
- **WAVE-003 — A plain drag creates a new selection.** Clicking empty space (not near an existing selection's own edge) and dragging sets `domain/sampleEditor`'s selection to span the drag, normalizing a backwards drag on release. Acceptance: a controller test against a hand-built instrument/selection state.
- **WAVE-004 — Dragging an existing selection's edge resizes it**, clamped to at least a couple of samples and never past the sample's own end, without disturbing the other edge. Acceptance: a controller test.
- **WAVE-005 — Wheel pans; a held modifier zooms.** Plain wheel moves the view window within `[0, sampleLength - zoomLength]`; `ctrlKey`-held wheel changes `zoomLength` (clamped to a sane minimum and the sample's own full length), centered on the current view. Acceptance: controller tests for both, including clamping at either end.
- **WAVE-006 — The draw kind renders only the current zoom window, never throws, and degrades gracefully** with no instrument, an empty sample, or a selection outside the current view. Acceptance: a `patternGrid.test.js`-style fake-canvas test.
- **WAVE-007 — No regressions.** Full unit suite passes; `node build.mjs app`/`dist` unaffected (no YAML/compiler/component-count-visible change - `waveformView` is declared and implemented but authored nowhere yet, exactly as `fileBrowser` once was between spec 035 and spec 036).

## Non-functional requirements

- Headless verification only (no browser-automation dependency in this environment, the same recorded reason every spec since 019 has given), the same precedent `patternGrid`/`fileBrowser` already set: verified against hand-built instrument/state fixtures and a fake canvas context, no screen authored.
- No new component-authoring vocabulary, no capability mapping - a mechanism spec only.

## Scope boundaries

In scope: `runtime/waveformController.js`, `renderers/canvas/waveformGeometry.js`, a new `waveformView` draw kind, the `componentTypes.js`/`behaviors.js` registrations, the small additive `mountGeneric.js` touch (one `contextFor` branch, mirroring `patternGrid`'s own minimal one), and tests for all of the above.

Out of scope, recorded rather than silently dropped:

- **Loop-marker dragging, the range-volume fade gesture, draw-mode freehand editing, individual-sample-point dragging** - each a real, separate v1 feature; later specs (the first two arguably belong with `loopCreator.js`'s own port, the latter two are genuinely optional given `sampleProcessing.js`'s own operations already cover the common cases non-interactively).
- **Playback preview / an animated playhead** - needs a real design decision about how a specialized component reaches `domain/playback` for a one-off preview play, not made here.
- **The 8-way slice overlay and its snapping** - a pure display aid with no interaction of its own; a later, small addition if ever needed.
- **The pinch-zoom scrollbar gesture** - a real scrollbar-behavior extension `scrollbar.js`/`listController.js` do not have; this spec's own wheel+modifier zoom covers the same need without it.
- **The rest of the sample-editor screen** (menu, sliders, spinboxes, envelope panels, transport buttons) and **where it all mounts** - unchanged from spec 040's own scope boundaries.
