# 028 — Song document: pattern editing and undo

Date: 2026-09-11. Kind: feature. Status: specified. Opens package **P6** (document model, undo, selection) of the [port roadmap](../010-port-roadmap/requirements.md), following P5's closure (spec 027).

## Purpose

Spec 012 (P2, playback) ported v1's sequencer behind `domain/playback/`, but only the read path: `Tracker.getSong()` is the *only* way to reach the song, exactly as in v1, and nothing mutates it. `domain/playback/README.md` names this itself: *"The song document lives inside the engine, reachable only through it. Package P6 of the roadmap gives it an explicit model and an editing layer."*

This spec gives pattern-level editing an explicit API and a working undo, read from `script/src/editor.js` and `script/src/ui/stateManager.js` in full (neither file was part of P2's playback-only subset, so none of this exists in v2 yet). Selection (a block/range and a cursor distinct from it) and clipboard are a separate concern — design.md's P6 sketch treats "an explicit protocol" for the eight selection verbs and a de-privatized clipboard as their own piece of work, and they depend on the mutation primitives this spec builds, so they are the next spec, not this one.

## What v1 actually does (read from source, not assumed)

- **Undo is a cell-diff history, not a snapshot stack.** `stateManager.js`'s `history.undo`/`history.redo` hold action objects `{type, id, data:[{position:{track,row}, from, to}]}`; a single note edit is one `data` entry, a track/pattern clear is one entry per non-empty cell. `maxHistory = 100`, a hard cap (`shift()` on overflow); redo is cleared on every new edit. Sequential `VALUE`-type edits on the same control id are coalesced into one entry rather than pushed separately.
- **Only pattern-scoped edits go through it.** `putNote`, `putNoteParam`, `clearTrack`, `clearPattern`, `pasteTrack`, `pastePattern` all call `StateManager.registerEdit`. Song-structural operations — `insertNote`/`removeNote` (row shift), `addToPatternTable`/`removeFromPatternTable` (song sequence), `clearSong`, `setPatternLength`, `setTrackCount` — call **no** undo method at all in v1; this is a real, uninstrumented gap in v1, not a design choice, confirmed by reading every call site.
- **Copy/paste is two independent, closure-private buffers.** `editor.js`'s own `pasteBuffer` (whole track/pattern, survives a pattern switch) is separate from `patternView.js`'s rectangular block buffer (`_rangeCopy`, spec 029's concern) — different code, same net idea. Both carry the full note (`instrument, period, effect, param, volumeEffect, index`), copied via `Note.duplicate()`/`populate()`.
- **Cursor position is not selection.** `Editor` keeps `currentTrack`/`currentTrackPosition`/`currentCursorPosition` in closure state (not a store, not undoable, not persisted); `Tracker` keeps `currentPattern`/`currentPatternPos`/`currentSongPosition` the same way. All editing operations act on "the current" position; there is no parameter-passing of an explicit target in most call sites. This spec keeps that shape (an explicit `getCurrent*`/`setCurrent*` API) rather than requiring every caller to pass coordinates.

## Decisions and assumptions

- **Where it lives.** `domain/song/`, a sibling to `domain/playback/` under the same `domain/` capability convention (one folder, one door). Because pattern editing must mutate the *exact* object playback schedules from, `domain/song/index.js` is a second, narrow, documented exception to `domain/playback/README.md`'s "only `index.js` may be imported from outside this folder" rule: it imports the shared `Tracker` (and `Note`) singleton directly from `domain/playback/engine/`. Both READMEs record this explicitly, so it reads as a decision, not a violation found later. Nothing else gets that exception; everything outside `domain/song/` reaches editing only through `domain/song/index.js`.
- **Scope is pattern editing, not song-structure editing.** PORT-003 (spec 010) says undo/selection/clipboard "behave as v1 does" for *pattern editing* specifically. Reading v1's source shows song-structural operations (pattern-table sequence, pattern length, track count, whole-song clear) are a different shape of edit — they resize the document rather than diff its cells — and were never part of v1's undo either. This spec covers pattern editing (note, track, pattern, and row-shift edits, all within one pattern) uniformly under one cell-diff undo mechanism; song-structure editing is deliberately deferred to a later spec, with its own undo representation, not shoehorned into this one to avoid a second mechanism now.
- **v1's own undo gap is closed for row-shift, not reproduced.** `insertNote`/`removeNote` fit the exact same cell-diff shape every other pattern edit here uses (a `RANGE` action over one track's rows) at no extra cost, so they are made undoable — a small, deliberate improvement, not a re-litigation of the "song-structure" boundary above (a row shift is still a pattern edit, just one v1 happened to leave uninstrumented).
- **No event bus revival.** v1 notifies listeners via `EventBus.trigger(EVENT.patternChange, id)`. Nothing in v2 subscribes to a document change yet (the pattern grid is P7). Each mutation here returns which pattern it touched instead, the same synchronous-result convention specs 018/027 already use, so a future caller can act on it without a speculative pub/sub layer built for zero current subscribers.
- **No store fields.** Per spec 010's own decision, restated here because this is the spec that could have violated it: song/pattern data, cursor position and undo history are not added to `runtime/store.js` / `app/state.js`. They are reachable only through `domain/song/index.js`'s own functions.
- **Undo history is real but unwired to any control yet.** The `VALUE` edit-action kind (a value-bound control's own undo, coalesced by control id) is ported faithfully since it costs nothing extra and is part of "v1's seven edit-action kinds", but nothing calls it in this spec — no document-bound value control exists yet. `DATA`/`SAMPLE` (the sample editor's own undo) are declared as history-replay no-ops with a recorded reason (P10's own territory), the same "declared, not implemented" convention the component catalogue used throughout P5.

## User stories and acceptance

- **DOC-001 — An explicit document API, not a getter into the engine:** As a future caller (the pattern grid, P7), `domain/song/index.js` exposes cursor/position getters and setters, and pattern-editing mutations, without reaching into `domain/playback/engine/`. Acceptance: nothing outside `domain/song/` and `domain/playback/` imports `domain/playback/engine/*`, confirmed by a grep-based test (mirroring the project's existing registry-boundary tests).
- **DOC-002 — Put a note, clear a track, clear a pattern, shift a row — all undoable:** As a caller, `putNote`, `putNoteParam`, `clearTrack`, `clearPattern`, `insertNote`, `removeNote` mutate the current pattern at the current cursor, and each is undoable/redoable back to the exact prior cell contents. Acceptance: every one of v1's own edit operations is exercised directly against real fixture modules (`tests/fixtures/*.mod`/`*.xm`, the same three P2 already uses), asserting both the mutation and its undo/redo.
- **DOC-003 — Copy and paste a track or a pattern:** `copyTrack`/`copyPattern` read out plain note data (no clipboard ownership — that is spec 029's job); `pasteTrack`/`pastePattern` write caller-supplied data back, undoably, matching v1's "paste survives a pattern switch" behaviour trivially (the caller decides where the data goes; nothing here privileges the pattern it was read from). Acceptance: copy from one pattern, paste into a different one, undo restores the pasted-into pattern's prior contents in one step.
- **DOC-004 — A hundred-step undo with the same coalescing:** `registerEdit`/`undo`/`redo`/`canUndo`/`canRedo`/`getUndoLabel`/`getRedoLabel` behave exactly as `stateManager.js` does: a 100-entry cap, redo cleared on a new edit, sequential same-id `VALUE` edits merged. Acceptance: a unit test drives the history to 101 pushes and confirms the oldest is dropped; a second confirms coalescing; both ported directly from the numbers in `stateManager.js`, not reinvented.
- **DOC-005 — No regressions:** Acceptance: the full unit suite still passes; `node build.mjs app`/`dist` succeed unchanged (this spec authors no YAML and touches no compiler/renderer path).

## Non-functional requirements

`domain/song/` follows `domain/playback/`'s own conventions: one `index.js` boundary, a `README.md` recording provenance and the one documented cross-boundary import, pure sub-modules (`editHistory.js`, `noteData.js`) that are independently unit-testable without a loaded song.

## Scope boundaries

In scope: `domain/song/index.js` (cursor/position API, pattern-editing mutations, undo/redo delegation); `domain/song/editHistory.js` (pure undo/redo stack, ported from `stateManager.js`); `domain/song/noteData.js` (pure `duplicateNote`/`populateNote`, ported from v1's `Note.duplicate()`/`populate()`, since the ported v2 engine's own `models/note.js` never carried those two methods and the playback boundary's "byte-identical, three divergences" invariant is not this spec's to extend); a `domain/song/README.md`; an amendment to `domain/playback/README.md`'s boundary paragraph; a grep-based boundary test.

Out of scope, recorded rather than silently dropped: selection (cursor-distinct block range) and a de-privatized clipboard (spec 029); song-structural editing — pattern-table sequence, pattern length, track count, whole-song clear (a later spec, once its own undo representation is designed; not part of PORT-003's "pattern editing" wording); wiring the generated application's mocked `pattern.clear`/`track.clear`/`track.copy`/`track.paste`/etc. commands to this new API (there is no real pattern-grid selection yet to supply "which pattern/track" — that is P7's job, the same way P2's playback stayed unwired to UI until P3/P4); a command-enablement gate rebuilt against document state (design.md names this as owed work P6 unblocks, but it is not this spec's acceptance criterion). Browser verification: not performed, for the same reason specs 012, 019–027 recorded none — this is headless domain logic, verified the same way P2's engine was.
