# 030 — The pattern grid

Date: 2026-09-11. Kind: feature. Status: specified. Implements package **P7** of spec [010](../010-port-roadmap/requirements.md), the port roadmap, following P3 (spec [013](../013-layout-foundations/requirements.md)), P4 (specs [014](../014-pointer-interaction/requirements.md)/[015](../015-keyboard-interaction/requirements.md)) and P6 (specs [028](../028-song-document/requirements.md)/[029](../029-selection-clipboard/requirements.md)).

## Purpose

`script/src/ui/app/components/patternView.js` (789 lines) is the screen the whole port is judged against: the note grid a tracker musician stares at for hours. It is also the one screen the catalogue's generic node tree structurally cannot express — a pattern holds 6-20,000 note cells, and a node per cell would make the outline scale with song size, something PORT-002's own "no song data in the outline" rule and P7's "why here" already rule out.

This spec introduces v2's first **specialized component**: a declared type that owns its own drawing and its own data access — reading `domain/song` and `domain/playback` directly rather than through a store-bound field — instead of being assembled from generic child nodes. P7's own framing calls this "the architectural bet": if it does not hold here, the renderer/outline split needs revisiting before the remaining specialized surfaces (P11) are attempted.

## Alignment with product vision

[product.md](../product.md) names the pattern grid explicitly as the next step after the document model ("then the document model and the pattern grid, then delivery") and states the value being tested is changing app structure without hand-laying-out every screen or rewriting domain behavior — while still treating "canvas rendering, tracker performance and musical compatibility" as essential, not optional. A specialized component that is declared once, drawn from an authored skin, and backed by the same `domain/song` capability P6 already built is exactly that claim, applied to the one screen most likely to break it.

## Research basis

Read in full for this spec: `script/src/ui/app/components/patternView.js` (rendering, scroll, cursor, selection, per-glyph caching), `script/src/ui/input.js:304-544,720-868` and `script/src/enum.js:419-505` (keyboard note entry and the 27-entry key table — the roadmap's design sketch says "thirty-one" but v1's own `KEYBOARDKEYS`/`KEYBOARDTABLE.main` tables hold 27 entries; the design sketch's count does not match the source and is corrected here), `domain/song/index.js` and `domain/song/selection.js` (spec 028/029's cursor, undo and selection primitives this spec builds on unchanged), and `runtime/componentTypes.js`, `runtime/behaviors.js`, `renderers/canvas/drawKinds.js`, `renderers/canvas/mountGeneric.js` (the registry, behavior and draw-kind mechanisms a new type must fit).

v1's pattern grid does not scroll like a list: the row at the song's current pattern position is always drawn at the vertical center of the grid, and moving "up" or "down" moves that position (and, while playing, the playhead) rather than a generic scroll offset. Horizontal scroll pans a window of tracks when they do not all fit. A click sets which track (and resets the edit column within it) is being edited, not which row — the row is always the current position. A rectangular block selection (rows × contiguous tracks), independent of the edit cursor, is dragged with a modifier held; without it, drag pans the view. This is the actual behavior this spec ports, not a generic scrollable/selectable grid invented from scratch.

## Scope decision

Two things named in P7's own design sketch are deliberately deferred to a follow-up spec, the same way P4 and P6 were each split across specs when their two halves shared little but a boundary:

- **Keyboard note entry** — typing a note in via the 27-key table, hex entry into the instrument/volume/effect/param columns, octave selection (F1-F7) and insert/remove-row shortcuts (`script/src/ui/input.js:304-544,720-868`). This is a real, separate mechanism (a key-to-note table plus per-column hex parsing) layered on top of the grid's cursor, not needed to prove the specialized-component contract itself. It is recorded as deferred, not silently dropped, in tasks.md.
- **Per-track chrome** — mute/solo controls (`TrackControl`), the per-track FX panel and VU meters (`Visualiser`). These sit beside the grid in `patternPanel.js` but are not part of `patternView.js` itself; P7's own goal is the grid, and the roadmap already places VU meters and scopes under P11.

Everything else P7's design sketch and acceptance list — the specialized-component contract, the viewport, the cursor, mouse-driven block selection and its clipboard commands, per-glyph caching, and the node-count/survival/frame-work acceptance criteria — is in scope here.

## Requirements

- **GRID-001 — The grid is one specialized node, not one per cell:** As the port's architectural bet, `patternGrid` is a declared, leaf component type (no `container`) with its own draw kind and its own behavior, backed by a model accessor into `domain/song`/`domain/playback` rather than a store-bound field. Acceptance: authoring one `type: patternGrid` node produces exactly one node in the compiled outline regardless of the loaded song's pattern length or track count; no note or pattern data is ever copied into a state-store field or serialized into the outline.
- **GRID-002 — Only visible cells are drawn, and glyphs are cached:** The draw kind renders line numbers and, per visible row × visible track, the note name, instrument, and effect/param (plus volume in FastTracker mode), using an offscreen-canvas cache keyed by font and text content, ported from v1's `_noteCache`/`_noteParamCache`/`_lineNumberCache`. Acceptance: the number of draw/hit-test operations per frame is bounded by the viewport's visible rows and tracks, not by the pattern's length or the song's track count; a cell whose glyph was already cached this session is drawn from the cache, not re-rasterized.
- **GRID-003 — The current row stays centered; scrolling moves the song position:** The row at `domain/song`'s current pattern position is always drawn at the grid's vertical center. The mouse wheel and a vertical background drag move that position (clamped to the pattern's length) rather than a generic scroll offset, and do nothing while the song is playing. Acceptance: wheeling over the grid when not playing moves the highlighted center row by one per notch; the note data shown for any row always matches `domain/song`'s pattern data at that row's position, including the always-centered current row.
- **GRID-004 — Tracks scroll horizontally when they overflow:** When the track count exceeds how many fit in the grid's width, a horizontal scrollbar and a horizontal background drag pan the visible window of tracks; when they all fit, no horizontal scrolling is offered. Acceptance: dragging the horizontal scrollbar moves the visible track window; a track outside the window is neither drawn nor hit-tested.
- **GRID-005 — Clicking a track sets the edit cursor's track, not its row:** A click resolves an x position to a track (accounting for the horizontal scroll window) and sets `domain/song`'s current track via its existing cursor API; the row a click lands on has no effect, since the edited row is always the current pattern position. Acceptance: clicking anywhere in a track's column while not dragging changes `domain/song.getCurrentTrack()` to that track and does not change `getCurrentPatternPos()`.
- **GRID-006 — The cursor is drawn at the right column and track:** A highlighted rectangle is drawn over the current track's current column (note, instrument, volume, effect or param) at the center row, sized to that column's character width exactly as v1's `cursorWidth1`/`cursorWidth3` distinguish the wide note column from the others. Acceptance: the highlight rectangle's horizontal position and width track `domain/song`'s current track and column as the cursor moves.
- **GRID-007 — A modifier-drag selects a rectangular block:** Holding the selection modifier while dragging (or clicking) begins or extends a rectangular row × track selection through `domain/song`'s existing `beginSelection`/`extendSelection` API; without the modifier, drag pans the view (GRID-003/004) instead. Releasing over a non-empty selection offers Clear/Cut/Copy/Paste, each dispatching to `domain/song`'s existing `selectionClear`/`selectionCut`/`selectionCopy`/`selectionPaste`. Acceptance: a modifier-drag draws a growing highlighted rectangle bounded by the drag's start and current cell; each of the four commands mutates (or reads) exactly the selected rectangle and is undoable through P6's existing history, with no new mutation logic added by this spec.
- **GRID-008 — Cursor and selection survive scroll, resize and a skin reload:** Because the cursor and selection live in `domain/song`, not in state private to the draw kind or its mount, no special handling is needed for either to persist. Acceptance: resizing the grid's panel or reloading the skin leaves `domain/song`'s current track/column/pattern-position and selection range unchanged, and the next render reflects them exactly as before the resize or reload.
- **GRID-009 — Frame work is measured and recorded:** The cost of one full grid redraw (a representative song: a full 32-track, 64-row pattern) is measured and the number recorded in tasks.md, establishing the baseline P8's frame-budget work measures against. Acceptance: tasks.md records a measured redraw time and the conditions it was measured under; this spec does not need to optimize past whatever that number is.
- **GRID-010 — No regressions:** Acceptance: the unit suite passes; every existing component type's layout, drawing, pointer and keyboard routing is unchanged, since `patternGrid` introduces a new type and a new behavior name rather than altering an existing one; P6's undo, selection and clipboard functions are called, never duplicated or re-implemented.

## Non-functional requirements

- **Architecture.** `patternGrid` is the first component type whose behavior reads live domain state directly instead of through the generic store-bound `field` mechanism every other type uses; this is a deliberate, narrow second door onto `domain/song`, matching the precedent P6's own README already documents for `domain/playback`, not a general bypass other types should copy. The mechanism itself (how a draw kind and a controller obtain that access) is a design decision, not fixed by this document.
- **Performance.** Draw cost must not scale with pattern length or track count, only with the viewport's visible extent; per-glyph caching is required, not optional, since v1 found it necessary at the same data volumes this spec targets.
- **Reliability.** All mutation (note edits already exist from P6; this spec adds none) and undo continues to go through `domain/song`'s existing history; a rendering or selection bug in this spec must not be able to corrupt pattern data or bypass undo.
- **Usability.** Column layout, highlight colors and the centered-current-row scrolling model match v1's, so a musician already familiar with the tracker is not relearning the editing surface; exact pixel/artwork fidelity is not required, per spec 010's open decision 1 (a smaller authored skin).
- **Security.** Not applicable beyond the existing pointer/keyboard input handling spec 014/015 already established; no new input surface (network, file) is introduced.

## Scope boundaries

In scope: the `patternGrid` component type and its contract; its draw kind (line numbers, note/instrument/volume/effect/param columns, per-glyph caching, the centered current row); its behavior controller (wheel/drag scroll on both axes, click-to-set-track, modifier-drag block selection); wiring the selection's Clear/Cut/Copy/Paste to `domain/song`'s existing functions; the node-count, survival and frame-work acceptance above.

Out of scope, recorded as deferred rather than dropped: keyboard note entry (the key-to-note table, hex column entry, octave selection, insert/remove-row shortcuts) as a follow-up spec once this one is implemented; per-track mute/solo controls, the per-track FX panel and VU meters/scopes (P11); authoring `patternGrid` into `app.yaml` beyond whatever minimal fixture this spec's own verification needs.
