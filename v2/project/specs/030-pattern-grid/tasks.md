## Found while doing it

- **v1's own `Tab`/`Shift+Tab` jump-a-track cannot be ported as `Tab`.** `mountGeneric.js`'s `handleKeyDown` claims `Tab` unconditionally for moving focus between controls (spec 015), before a keydown ever reaches a node's own controller - discovered by reading that function before writing `gridController.js`'s keydown cases, not by a failing test. Dropped from this spec's keydown vocabulary; left for the deferred note-entry follow-up spec to bind differently if it turns out to matter.
- **`isRecording` has no port.** v1's `patternView.js` treats "recording" as a second trigger (alongside the selection modifier) for drag-to-select; the ported engine (`player/src`) never carried a getter for its own private `isRecording` var (a UI/editor concern spec 012 had no reason to port). The selection-vs-pan gesture here decides on the modifier key alone - a real, recorded narrowing of GRID-007, not silently dropped.
- **Threading `metaKey`/`ctrlKey` through `runtime/pointerRouter.js` was considered and rejected.** That module's emitted gesture shapes are exercised by spec 014/015/019's own tests; adding fields to `down`/`move`/`up`'s fixed output for one controller's benefit was real risk (a stray `undefined`-valued key can already fail `assert.deepStrictEqual`-style comparisons) for no gain a cheaper alternative didn't already give. `mountGeneric.js` already sees the raw native event one call earlier, so a small piece of ambient state (`pointerModifiers`) reads it directly with zero change to the router.
- **The literal "one node" framing in GRID-001 needed a small correction once the selection menu was designed.** Synthesizing a `submenu` + four items for the context menu means the true count is 6, not 1, per `patternGrid` node - still fully independent of song size (the actual property GRID-001 cares about), recorded in design.md rather than treated as a contradiction.
- **Everything else matched the plan going into it**: `domain/song`'s existing cursor/selection API needed no changes beyond the handful of thin forwards and `formatNoteName`; no changes were needed to `runtime/genericLayout.js`, `runtime/pointerRouter.js`'s shape, or any other component type's routing; the controller's own unit tests against a real loaded fixture passed on the first run with no sign-convention bugs, which is some evidence the drag-delta math (ported from `patternView.js:502-558`) was reasoned through correctly before being written rather than debugged into shape afterward.

## Known limits

Keyboard note entry (the key-to-note table, hex column entry, octave selection, insert/remove-row shortcuts, `Tab`-jump-a-track under a different binding) and keyboard-driven selection growth are deliberately not implemented here - see requirements.md's scope decision; a follow-up spec's job. Per-track mute/solo, the FX panel and VU meters are not this spec's (P11's). No browser verification occurred in this environment (see "Verification plan") - the same open item spec 019 left, still not re-checked. Nothing in `app.yaml` authors a `patternGrid` yet - authoring the actual pattern-panel screen, and wiring the horizontal scrollbar to a visible thumb widget rather than the plain indicator bar drawn here, are both left to whichever spec authors that screen.
