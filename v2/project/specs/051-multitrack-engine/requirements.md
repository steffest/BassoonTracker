# 051 — The multitrack arrangement view's engine

Date: 2026-09-15. Kind: feature. Status: specified. Opens package **P11** (the remaining specialized surfaces) of the [port roadmap](../010-port-roadmap/requirements.md), following P10's close (spec 050). P11 covers the multitrack arrangement view, the piano, the envelope editor, the scopes and the VU meters - about 4,000 v1 lines together. This spec starts with the multitrack arrangement view, the first-named and largest (`multitrack.js` 803 lines, `dawtrack.js` 449 lines, `trackControl.js` 115 lines - all three read in full for this spec), matching this roadmap's own "mechanism, then interactive leaf, then screen" pattern (loop creator: specs 043/044/045; Nibbles: specs 047/048/049).

## Purpose

`Multitrack` (`script/src/ui/app/components/multitrack.js`) is v1's alternate, DAW-style view of the currently-loaded pattern: one horizontal lane per track, note-and-instrument blocks instead of a text grid, a live oscilloscope per track, per-track solo/mute/record controls, and drag-to-move-note editing. `DAWtrack` (`dawtrack.js`) is each lane's own drawing/state object (block/effect caching, waveform thumbnails, the live scope, the per-track control strip); `TrackControl` (`trackControl.js`) is the *smaller* solo/mute/FX header v1 also puts above the classic text-grid pattern view (`patternPanel.js`) - the same mute/solo mechanism, a second, simpler consumer of it.

This spec ports the headless half only: the pure per-track note/effect segmentation math, the move-note edit, and the real track mute/solo audio-volume mechanism (which affects actual playback, not just a lane's own drawing) - all fully testable with no canvas, no drag gesture, no live `AnalyserNode`. The interactive leaf (`multitrackView`, the port's sixth specialized component: scroll/zoom, drag-to-move-note, the live oscilloscope, waveform thumbnails, the per-track control strip) is a later spec's own, at least as large as the loop-creator overlay (spec 044) was. The screen (View-menu wiring, the classic grid's own smaller mute/solo header) follows after that.

## What v1 actually does, and what this narrows out (read from source, not assumed)

**Per-track block segmentation** (`multitrack.js#_buildPerTrackBlocks`, 639-729). Walks a pattern's rows once per track, opening a new "block" at each note-on and closing the previous one there; a block's `endStep` is capped at `startStep + maxLengthSteps` when the sample itself is shorter than the remaining pattern (`_getSampleLengthInSteps`, 756-802) - but only when the sample has no enabled loop (a looping sample plays indefinitely, so its block always runs to the next note or the pattern's end). Volume comes from the row's own volume-column effect (`0C`/FT volume-column `16-80`) or the instrument's own default; instrument-index "sticky" tracking (a note with no explicit instrument keeps the last one played) and `SETTINGS.emulateProtracker1OffsetBug`'s own sample-offset (`9xx`) carry-forward both reappear here exactly as the playback engine itself already implements them (`domain/playback/engine/tracker.js`) - this spec re-derives the same two rules for display purposes, not sharing code with the engine's own scheduling loop (which computes them for entirely different reasons, at a different granularity).

**Per-track effect markers** (`_buildPerTrackEffects`, 731-747): every cell with a nonzero effect or param, flattened to `{step, effect, param}` per track - pure, no engine math at all.

**Move note** (`_moveNote`, 587-623): drags a note block from one (track, step) to another, clearing the source cell and populating the destination, as one undoable edit (`StateManager.createRangeUndo` + two `StateManager.addNote` calls - the same shape `domain/song/index.js` already gives every other pattern mutation).

**Track mute/solo** is a real audio effect, not a drawing-only toggle. Three separate v1 files each maintain a locally-mirrored copy of the same two rules ("soloing a track mutes every other track; un-soloing restores them") and broadcast `EVENT.trackStateChange` for the others to pick up: `multitrack.js` (147-159, driving each lane's own dimming), `trackControl.js` (the classic grid's own smaller header, 62-74), and `audio.js` (144-201, `updateTrackVolumes()` - the one copy that actually matters, since it sets each track's own `FilterChain.volumeValue()`, live). `v2`'s ported engine (`domain/playback/engine/audio.js`, spec 012) never received this listener at all - nothing triggered it at the time, and it is genuinely new P11 territory, not a dropped P2 feature. This spec ports the *one* real rule (the mute/solo interaction and its effect on `FilterChain` volume) once, as a single domain owner, rather than v1's own three duplicated copies of it.

A **known v1 quirk, preserved rather than "fixed"**: clicking Mute on a track that is itself currently soloed clears that track's own solo flag locally, but (because `triggerTrackStateChange()` is called with no `wasSolo` argument on the mute path) never fires the "restore everyone else" cascade the way turning Solo off does. Confirmed by reading `dawtrack.js:130-144` and `trackControl.js:37-41,62-67` side by side - not a bug report anywhere, and changing it would be new, unrequested behavior, not a port of v1's own. Recorded here since it looks, at a glance, like an inconsistency worth "fixing."

## Decisions and assumptions

- **One new domain folder, `domain/arrangement/`** - not folded into `domain/song` (this is view-derived data about a pattern, not a pattern-editing mutation, matching `domain/song/README.md`'s own "not here" list) and not folded into `domain/playback` (the segmentation math has nothing to do with the playback engine; only the mute/solo volume effect does). Reaches `domain/song/index.js`'s and `domain/playback/index.js`'s public surfaces only, never `domain/playback/engine/` directly - the same documented shape `domain/sampleEditor/{loopCreator,resample}.js` already use.
- **`moveNote` itself lives in `domain/song/index.js`**, not `domain/arrangement` - it is exactly the shape of pattern-cell mutation that module's own `putNote`/`removeNote`/etc. already own (two cell diffs, one undo action), and needs the same private diff helpers those functions already close over. `domain/arrangement#moveNote` is a one-line forward, kept so the arrangement view's own future controller has one door for everything it needs, the same as `domain/sampleEditor`'s own functions sit beside forwards into `domain/song` for undo registration.
- **Track mute/solo state is centralized in `domain/arrangement`, not triplicated.** v1's three independent, locally-mirrored copies (Purpose section) collapse into one: `domain/arrangement` is the single owner of each track's mute/solo flag, and calls a new `domain/playback/index.js#setTrackVolumes(muteFlags, soloFlags)` (a parameterized port of `engine/audio.js`'s own `updateTrackVolumes()`, added to the engine as one small additive function - not a fourth "byte-identical" divergence, the same footing spec 038's `getBPM`/`getAmigaSpeed` already established) to apply the real effect. No `EVENT.trackStateChange` broadcast is needed in v2: nothing else has to independently react, because nothing else independently mirrors the state anymore.
- **The known mute/solo-while-soloed quirk (Purpose section) is preserved, not fixed** - `setTrackMute` never cascades to other tracks, exactly matching v1's own `wasSolo`-omitted call path.
- **Four small, additive `domain/playback/index.js` forwards**, all one-line wrappers over existing engine math the same way `getSampleRateForPeriod` (spec 046) already is: `getFineTuneForNote`, `getFineTuneForPeriod`, `usesLinearFrequency` (a getter over the engine's own `Tracker.useLinearFrequency` flag), `getTickTiming` (`{ticksPerStep, tickTime}` from `Tracker.getProperties()`), and `emulatesProtracker1OffsetBug` (a getter over the engine's own `SETTINGS.emulateProtracker1OffsetBug`, itself derived from the loaded format - see `engine/tracker.js:2003`).
- **One small, additive `domain/song/index.js` forward**: `getInstrumentAt(index)`, mirroring `getCurrentInstrument`'s existing shape for an arbitrary index rather than only the current one (block segmentation needs an arbitrary row's own instrument, not only the currently-selected one).

## User stories and acceptance

- **ARR-001 — Per-track blocks match v1's own segmentation exactly.** Given a real loaded fixture, `getPerTrackBlocks(pattern)` produces the same start/end/instrument/volume/name per block as hand-traced from the source rules, including: sticky instrument carry-forward, volume-column and `0C` effect overrides (both tracker modes), sample-offset (`9xx`) carry-forward under `emulateProtracker1OffsetBug`, and a block capped by its own sample's playable length only when the sample has no enabled loop. Acceptance: unit tests against `wizballalt.mod` (ProTracker) and a real `.xm` fixture (FastTracker), covering every branch above at least once.
- **ARR-002 — Per-track effects are flattened correctly.** `getPerTrackEffects(pattern)` lists every nonzero effect/param cell per track, in row order. Acceptance: unit test against a real fixture.
- **ARR-003 — Move note is one undoable edit.** Moving a note from an occupied cell to an empty one clears the source and populates the destination as a single undo/redo step; moving from a cell with no playable note (no period/index) is a no-op. Acceptance: unit tests for move+undo+redo and for the no-op guard.
- **ARR-004 — Solo mutes every other track; un-soloing restores them.** Soloing track N sets every other track's mute flag and clears their solo flags; turning that solo back off restores every other track's mute flag to false. Acceptance: unit tests reproducing v1's own interaction table, including the two-tracks-solo-in-sequence case.
- **ARR-005 — Mute/solo actually changes audio volume.** `setTrackVolumes`'s own math (ported from `updateTrackVolumes()`) is exercised directly against a real `FilterChain`-shaped fake, confirming the exact 70/0 volume values for every combination of (this track muted/soloed, any-track-soloed). Acceptance: unit tests for all four combinations from `updateTrackVolumes()`'s own two branches.
- **ARR-006 — The known quirk is preserved.** Muting a currently-soloed track clears only that track's own solo flag; every other track's mute state, forced on by the earlier solo, stays forced on. Acceptance: one unit test reproducing this exactly.
- **ARR-007 — No regressions.** Full unit suite passes; `node compiler/generate.js`/`node build.mjs app` unaffected (no YAML/`capabilities.js` change - this spec is headless, matching spec 039/040/043/047's own precedent for an engine-first spec).

## Non-functional requirements

- Headless verification only (no browser-automation dependency in this environment, the same recorded reason every spec since 019 has given).
- No new authoring mechanism, no YAML, no `capabilities.js` mapping - nothing here is reachable from any UI yet; the interactive leaf and the screen are later specs'.

## Scope boundaries

In scope: `domain/arrangement/` (new: `index.js`, `README.md`), `domain/song/index.js`'s two small additions (`getInstrumentAt`, `moveNote`), `domain/playback/index.js`'s five small additions (`getFineTuneForNote`, `getFineTuneForPeriod`, `usesLinearFrequency`, `getTickTiming`, `emulatesProtracker1OffsetBug`, `setTrackVolumes`), `domain/playback/engine/audio.js`'s one additive function (`me.setTrackVolumes`), and tests for all of the above.

Out of scope, recorded rather than silently dropped:

- **`multitrackView`, the interactive specialized-component leaf** - scroll/zoom, drag-to-move-note (calling `ARR-003`'s `moveNote` from a real gesture), the live oscilloscope (a per-track `AnalyserNode`, architecturally new - no prior specialized leaf in this port is driven by live audio analysis), waveform thumbnails, and the per-track solo/mute/record control strip's own drawing and hit-testing. A real, substantial later spec, at least as large as spec 044 (the loop-creator overlay) was.
- **The classic grid's own smaller mute/solo header** (`trackControl.js`, above the text-grid pattern view) - a second, simpler consumer of the same `domain/arrangement` mute/solo functions this spec builds, authored once that UI exists to host it.
- **The screen**: the View-menu's own multitrack/main/sample view-mode switch (`EVENT.showView`, `patternPanel.js:275-314`), record-arm wiring (`FX panel toggle`), and any layout for either control strip.
- **Sharing segmentation code with the playback engine's own scheduling loop** - the engine already computes sticky-instrument and offset-carry-forward for its own reasons, at its own granularity (per scheduled note, not per displayed block); re-deriving the same two rules here for display is simpler and safer than threading a new shared abstraction through both, and matches this spec's own "reach the engine only through domain/playback's public surface" rule.
