# 042 — The sample-editor screen

Date: 2026-09-14. Kind: feature. Status: specified. Continues package **P10** (features and the plugin path) of the [port roadmap](../010-port-roadmap/requirements.md), following spec 039 (the feature registry), spec 040 (sample processing operations) and spec 041 (the waveform view). Gives P10's first named tenant an actual screen: spec 040's four DSP operations and spec 041's waveform view were both headless until now.

## Purpose

Specs 039-041 each built one mechanism and left it unreachable from any UI on purpose, matching the roadmap's own "mechanism before tenant/screen" pattern (P7's pattern grid before its screen, P9's `fileBrowser` before the disk-operation screen). This spec authors the screen: it replaces `components/sampleEditPanel.yaml`'s spec-026 placeholder text with real content, wiring the waveform view and the four sample-processing operations to actual controls for the first time, plus the instrument-selection/metadata fields those operations and that view both implicitly depend on (which instrument is "current" was never itself a v2 concept before this spec).

## What v1 actually does, and what this narrows out (read from source, not assumed)

`script/plugins/sampleeditor/sampleView.js` (1070 lines, re-read in full for this spec) is one screen with far more surface than P10's own remaining mechanisms cover: an instrument name field and 8/16-bit buttons; the waveform view plus a loop creator, a hiss-reduction panel and a resample panel (each its own popup sub-feature); a menu (Sample/View/Edit, mixing disk load/save, maximize, slice toggling, resample, and the four operations spec 040 already ported); two envelope panels (volume/panning point editing); a side panel of sliders/spinboxes for volume, finetune, panning, loop start/length, fadeout, relative note, and vibrato speed/depth/sweep/wave-type, switchable between "Loop" and "Vibrato" sub-tabs; a bottom row of Load/Play/Range/Loop/Stop/More transport-preview buttons; and four collapsible button groups (Display/Select/Edit/Volume zoom/select/edit/volume-adjust shortcuts). Authoring all of that now would either silently reproduce features nothing else in this port supports yet (sample load/save has no capability; the loop creator/hiss-reduction/resample panels are each substantial, separate popups; playback preview needs note-triggering wiring spec 041 already excluded), or invent placeholder behavior for them, which is worse than not authoring them yet.

This spec authors exactly the slice that is real and already backed by an existing capability:

- **The waveform view** (spec 041), mounted for the first time.
- **The four sample-processing operations** (spec 040: `adjustVolume("max"/"fadein"/"fadeout")`, `trim`, `reverse`, `invert`), as six buttons - the two extra buttons (Fade In/Fade Out) are the same zero-argument shape as Normalize/Trim/Reverse/Invert, so including them costs nothing new.
- **Instrument selection** (`spinBoxInstrument`, sampleView.js:256-258) and **its name field** (`instrumentName`, 67-78) - neither existed anywhere in v2 before this spec; nothing else could have used the current instrument's own identity or name.
- **Volume** (`volumeSlider`, 261-263) and **loop enabled/start/length** (`loopEnabledCheckbox`/`repeatSpinbox`/`repeatLengthSpinbox`, 273-302,525-534) - the only sample-metadata fields meaningful to *every* loaded format (MOD and XM alike), unlike finetune/panning/fadeout/relative-note/vibrato below.

## Decisions and assumptions

- **Instrument-property edits are not undoable.** v1's own `trackUndo`/`undoInstrument` mechanism (sliderBox.js:81-96) registers an `EDITACTION.VALUE` action whose `target` is the live UI control object itself, replayed by calling `target.setValue(...)` directly (stateManager.js:187-195, editHistory.js's own still-carried-verbatim `VALUE` case). Nothing in v2 has ever registered one of these - a mounted control's controller is ephemeral, re-created on remount, not a persistent object an undo entry could hold a reference to. Porting this properly needs its own replay shape (most likely: the *field name* plus a domain setter, not a live object), which is a separate, later concern - not invented here for six new controls alone.
- **FT-only fields stay out**: finetune, panning, fadeout, relative note, and the three vibrato sliders plus the four wave-type buttons are all fields v1 disables outright in ProTracker mode (`sampleView.js`'s own `EVENT.trackerModeChanged` handler, 1013-1020) and, for finetune specifically, also re-bounds dynamically (`fineTuneSlider.setMin/setMax`, 1005-1006). v2 has `disabledWhen` as a runtime mechanism (spec 015) but no YAML vocabulary to author it yet (spec 015's own design.md still records this gap), and no mechanism at all for a control's authored `min`/`max` to vary by tracker mode. Authoring these fields now would mean either a MOD-mode control that visibly does something meaningless, or guessing at a new compiler mechanism ahead of a real need - both worse than recording the gap. See Scope boundaries.
- **Loop start/length use one static authored ceiling (65535, matching v1's own), with the real bound enforced in the capability handler against the sample's actual current length** - this is not a v2 shortcut, it is exactly what v1's own `repeatSpinbox`/`repeatLengthSpinbox.onChange` already do (sampleView.js:274-301): the authored `max` is a rough ceiling, the real clamp happens on change.
- **The loop-enabled checkbox is the first authored rule needing `CONDITION_FIELD_ALIASES` for anything beyond transport state.** A rule's own `deriveMockFieldName` (dot-joining a multi-word subject) and `toggle-generic`'s own derived field (hyphen-joining, with a `.active` suffix) can only ever agree by coincidence for a multi-word subject; `compiler/recipes.js`'s alias list exists for exactly this seam and gains one entry (see design.md).
- **The instrument spinBox switching instruments also resets the sample selection**, mirroring `waveform.js#setInstrument` (593-620: v1 resets its own zoom and range together on every instrument switch) - without this, a selection made on one instrument would silently apply to whatever instrument the user switches to next, index-for-index, which is never what a user means. `runtime/waveformController.js` (spec 041) gains the matching zoom-reset half of the same behavior, since nothing before this spec ever exercised an instrument switch against it.
- **No proactive "publish on song load" hook.** The screen's own fields display blank/zero values until the instrument-index control is first touched (dragged, typed into, or driven by a click elsewhere that calls `setInstrumentIndex`) - `domain/playback` (which is the only module that knows when a song loads) does not import `domain/sampleEditor` to push an initial value, since that would invert this port's own established module layering (a lower-layer module reaching into a higher one). Recorded as a known limit, not fixed here - see Scope boundaries.

## User stories and acceptance

- **SES-001 — The panel shows real content.** Switching the control bar to "Sample Edit" shows the waveform view, the instrument selector/name, volume, loop controls, and the six operation buttons - not spec 026's placeholder text. Acceptance: `project/specs/application/app-outline.json` (via `node compiler/generate.js`) shows a real `waveformView` node and the described controls under `main.sampleEditPanel`, with zero new warnings.
- **SES-002 — The instrument selector switches the current instrument, clamped, and resets the sample selection.** Dragging/typing past `getMaxInstruments()` clamps rather than desyncing the display; switching instruments always resets the sample-editor's own selection (spec 040) to "the whole sample." Acceptance: a unit test against a real loaded fixture.
- **SES-003 — Volume and loop fields read and write the current instrument's own sample.** Each control's own capability clamps to a sane range (volume: `[0,64]`; loop start/length: clamped to the sample's real current length, exactly as v1's own handlers do) and publishes the resulting value back, so a rejected/clamped request never leaves the display showing a stale or invalid number. Acceptance: unit tests for each field, including the over-the-ceiling clamp case.
- **SES-004 — The loop-enabled control reflects the real loop state.** Its own `rule:` resolves to the exact same field name `toggleLoopEnabled`'s own command writes, verified empirically against the compiled outline (spec 036's own "confirm by reading the outline back, not by calculation" precedent). Acceptance: a compiler-recipe unit test plus the app-outline read-back.
- **SES-005 — The six operation buttons run the existing spec-040 operations and republish on change.** Each is a zero-argument, fire-and-forget command; running one that changed the sample (e.g. Reverse) re-publishes every instrument field afterward (Trim can change the sample's own length, which can shift the loop's own bounds - spec 040's `trim()` already adjusts them). Acceptance: unit tests against a real loaded fixture, one per button.
- **SES-006 — No regressions.** Full unit suite passes; `node build.mjs app` succeeds with the loose-ends count unaffected (every new command is mapped in `capabilities.js`, none left as a generated mock); `node build.mjs dist` still blocked only by the pre-existing `esbuild` mismatch every spec since 019 has recorded.

## Non-functional requirements

- Headless verification only (no browser-automation dependency in this environment, the same recorded reason every spec since 019 has given).
- No new authoring mechanism invented for this spec alone: the two compiler additions (`verb-action`'s six new verbs, one `CONDITION_FIELD_ALIASES` entry) are vocabulary added to existing, already-designed extension points, not new recipe *kinds*.

## Scope boundaries

In scope: `project/specs/application/current/components/sampleEditPanel.yaml` (replacing spec 026's placeholder), `domain/sampleEditor/index.js`'s new capability surface, `domain/song/index.js`'s two new re-exports (`getMaxInstruments`, `setCurrentInstrumentIndex`), `runtime/waveformController.js`'s one additive zoom-reset hook, `compiler/recipes.js`'s vocabulary additions, the twelve new `capabilities.js` mappings, and tests for all of the above.

Out of scope, recorded rather than silently dropped:

- **Finetune, panning, fadeout, relative note, vibrato (speed/depth/sweep/wave-type)** - each is an FT-only field v1 disables/re-bounds dynamically by tracker mode; v2 has no YAML vocabulary for `disabledWhen` yet (spec 015's own recorded gap) and no mechanism for a control's `min`/`max` to vary by mode. A real, deliberate boundary, not an oversight.
- **Volume/panning envelope editing** (`EnvelopePanel`) - a substantial, separate interactive component (point add/remove/drag, sustain/loop markers), not a field binding.
- **The loop creator, hiss-reduction panel, resample panel** - each its own separable feature (already recorded as such in spec 040's own scope boundary).
- **Draw mode** (freehand sample editing) - excluded already by spec 041's own requirements.
- **8/16-bit sample conversion** - recorded already in spec 040 as not undoable in v1 either; not fixed here.
- **Playback preview** (Play/Range/Loop/Stop, the spacebar toggle) - excluded already by spec 041's own requirements ("no playback preview").
- **Sample load/save** - no capability exists for either; spec 036 only ever built module load.
- **Maximize, slice toggling** - maximize is a layout-only feature with no functional value without its own resizing logic; slices excluded already by spec 041.
- **The ±5%/±10% volume-percentage buttons** - each needs a parameter baked into which button was clicked, a shape `verb-action`'s fixed zero-argument command cannot express; a real mechanism gap, not merely skipped.
- **The Select button group** (All/None/loop-bound/Cut/Copy/Paste) - "None" has no distinct representation from "the whole sample" in the current `{start, length}` selection model (`length: 0` already means "the whole sample" - spec 040's own convention), a domain-model ambiguity that belongs to `domain/sampleEditor` itself, not this screen.
- **Instrument-property undo** - see Decisions and assumptions above; a real, later concern.
- **A proactive "publish on song load" hook** - see Decisions and assumptions above; the screen's fields start blank/zero until first touched.
