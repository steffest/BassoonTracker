# 029 — Selection and clipboard

Date: 2026-09-11. Kind: feature. Status: specified. Closes package **P6** (document model, undo, selection) of the [port roadmap](../010-port-roadmap/requirements.md), building on spec 028's document API and undo layer.

## Purpose

Spec 028 gave pattern editing an explicit, undoable API but deliberately left out selection and clipboard, since design.md names them as their own piece of work: *"Selection becomes an explicit protocol with the eight verbs v1 routes through one global callback, plus a clipboard that is not private to the editor module."* This spec is that piece: a rectangular block selection distinct from the edit cursor, and a clipboard any caller can address directly.

## What v1 actually does (read from source, not assumed)

- **Selection is a rectangular block, owned by one long-lived UI component instance.** `script/src/ui/app/components/patternView.js`'s own `_range = {start:[row,track], end:[row,track]}`, normalized to top-left/bottom-right by `_normalizeRange`. It spans arbitrary rows across arbitrary contiguous tracks - not one cell, not one track. It survives scrolling and resizing only because nothing ever recreates the `PatternView` instance that owns it; it is cleared by an explicit action (Escape, a new drag, or the `RESET` verb), never by rendering.
- **Eight declared verbs, six actually implemented.** `SELECTION = {RESET, CLEAR, CUT, COPY, PASTE, POSITION, DELETE, REPLACE}` (`script/src/enum.js:181-190`). `patternView.js`'s `processSelection()` implements `RESET/CLEAR/CUT/COPY/PASTE/POSITION`; `DELETE`/`REPLACE` are declared and never given a case - the same "declared, not implemented" gap this project already has a convention for (component types, `stateManager.js`'s `DATA`/`SAMPLE` kinds in spec 028).
- **Routing is one global callback pointer**, not a protocol: `UI.setSelection(callback)` stores a single function; `UI.clearSelection/copySelection/cutSelection/pasteSelection` just call `selection(SELECTION.XXX)`. Only one selection "owner" can exist at a time, whichever component last registered. `copySelection`/`cutSelection` null out the pointer afterward but keep `prevSelection`, so `POSITION` exists purely to let a later paste-with-no-active-selection recover the last selection object and target the *current cursor* instead of the original range. Spec 010's design sketch names this specific shape - "the eight verbs v1 routes through one global callback" - as the thing to replace with "an explicit protocol," not reproduce.
- **Two independent, closure-private clipboards for the same net idea.** `editor.js`'s own `pasteBuffer` (whole track/pattern, already given an explicit primitive in spec 028's `copyTrack`/`copyPattern`/`pasteTrack`/`pastePattern`) and `patternView.js`'s `_rangeCopy` (the rectangular block above) are two separate in-memory buffers with overlapping purpose, not a deliberate design - reading both call sites shows no case where having two actually does something one couldn't. Design.md's "a clipboard that is not private to the editor module" is read here as licence to fix that duplication, not preserve it: one clipboard, addressable from `domain/song/index.js` directly.
- **No cross-track transpose.** Grepped the whole v1 tree for `transpose`; paste writes raw note/effect fields verbatim regardless of which track a block lands on. Not a feature to port.

## Decisions and assumptions

- **One selection object, not a registry of callbacks.** v2 has exactly one document open at a time (spec 028's `domain/song/` is already a singleton capability), so there is nothing for a "whichever component last called `setSelection`" indirection to arbitrate between. The eight verbs become five ordinary functions (`selectionCopy`, `selectionCut`, `selectionClear`, `selectionPaste`, `resetSelection`) plus range-building (`beginSelection`, `extendSelection`, `selectAll`) and range/clipboard queries (`getSelectionRange`, `hasSelection`, `getClipboard`, `hasClipboard`) - all directly callable, no indirection to replace later.
- **`POSITION` has nothing left to recover.** It existed to let a paste after a null-out find its way back to *a* selection object across the single global callback. With one addressable selection object there is no null-out to recover from: paste always targets the current selection's top-left if one exists, otherwise the current cursor - which is what `POSITION`'s fallback was already trying to approximate. No function is named `selectionPosition`; the behaviour it existed for is simply how `selectionPaste` always works.
- **One clipboard, not two.** The rectangular-block clipboard from `patternView.js` is the one this spec builds (`getClipboard`/`setClipboard`, holding a 2D array of plain note data plus its width/height). Spec 028's `copyTrack`/`pasteTrack`/`copyPattern`/`pastePattern` remain explicit, no-ambient-state primitives (an explicit source and target, no clipboard involved) - a caller wanting "copy the whole track to the clipboard for a later paste" selects the track's full range first (`selectAll`, then `selectionCopy`), the same protocol as any other block. This removes v1's duplication instead of reproducing it.
- **`DELETE`/`REPLACE` stay declared, not implemented**, exactly as v1 left them - not a gap this spec is scoped to close, since nothing in v1 ever calls them either.

## User stories and acceptance

- **SEL-001 — Build and query a rectangular selection:** `beginSelection(row, track)` starts a one-cell range at an arbitrary cell; `extendSelection(row, track)` grows it to cover any rectangular span of rows × contiguous tracks; `selectAll()` selects the current track's full row range; `getSelectionRange()` returns the normalized `{top, left, bottom, right}` or `null`; `resetSelection()` deselects. Acceptance: unit-tested with both orderings (dragging up-left vs down-right) normalizing to the same rectangle.
- **SEL-002 — Copy, cut, clear and paste a block:** `selectionCopy()` reads the selected cells into the clipboard without mutating the document; `selectionClear()` clears them, undoably, as one action; `selectionCut()` does both as one undoable action; `selectionPaste()` writes the clipboard back at the current selection (or the cursor, with none active), undoably, clipping to the pattern's row count and the song's current track count exactly as v1 does. Acceptance: copy a block, switch pattern, paste - the clipboard survives the switch (matching v1); undo restores the pasted-into pattern's prior contents in one step; a clear/cut is undoable in one step.
- **SEL-003 — The clipboard is addressable, not private:** `getClipboard()`/`hasClipboard()` are ordinary exports on `domain/song/index.js`, not a closure variable reachable only through a UI component; `clearClipboard()` empties it explicitly (v1 has no equivalent - nothing ever clears `pasteBuffer`/`_rangeCopy` - but an addressable clipboard should be able to say "nothing copied" too, a small, honest addition rather than a ported one). Acceptance: a test reads the clipboard's contents directly after a copy, without going through a paste.
- **SEL-004 — No regressions:** Acceptance: the full unit suite still passes; `node build.mjs app`/`dist` succeed unchanged (this spec authors no YAML).

## Scope boundaries

In scope: `domain/song/selection.js` (pure range-normalization + clipboard storage); `domain/song/index.js` additions (`beginSelection`, `extendSelection`, `selectAll`, `resetSelection`, `getSelectionRange`, `hasSelection`, `selectionCopy`, `selectionCut`, `selectionClear`, `selectionPaste`, `getClipboard`, `hasClipboard`), all built on spec 028's existing undo/mutation primitives with no changes to that spec's own surface.

Out of scope, recorded rather than dropped: `DELETE`/`REPLACE` (declared, not implemented, matching v1); wiring any of this to a real pattern-grid UI (P7, which does not exist yet - there is nothing to click or drag on); the generated application's mocked block-selection commands (none are currently authored - `editPad.yaml`'s clear/copy/paste buttons are track/pattern-scoped, already covered by spec 028's primitives, not this spec's block selection); keyboard shortcuts for cut/copy/paste (`app.yaml`'s `cut`/`copy`/`paste` unresolved-action-reference loose ends stay unresolved - they need a real pattern grid to know what "the current selection" even means on screen, which is P7's job). Browser verification: not performed, for the same reason specs 012, 019-028 recorded none.
