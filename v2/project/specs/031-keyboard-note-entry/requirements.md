# 031 — Keyboard note entry for the pattern grid

Date: 2026-09-11. Kind: feature. Status: specified. The follow-up spec [030](../030-pattern-grid/requirements.md) deferred: package **P7** of spec [010](../010-port-roadmap/requirements.md), the port roadmap, is not closed until this lands.

## Purpose

Spec 030 gave the pattern grid a real cursor, mouse-driven block selection and a rendering/scroll model, but deliberately left the keyboard unable to write a single note: v1's musicians type notes directly into the grid from the QWERTY keyboard (a 27-key piano layout), enter hex values into the instrument/effect/param columns, pick an octave with F1-F7, and insert/remove rows without ever touching the mouse. Without this, "it edits" (roadmap milestone F) is not actually true yet - the grid can be looked at and clicked on, but not played into.

## Alignment with product vision

[product.md](../product.md) names "the document model and the pattern grid" as the step the port's whole value proposition (musical and editing parity) rests on. A grid that cannot be typed into is not yet the tracker musicians are familiar with - the acceptance bar spec 010's PORT-003 set ("pattern editing... behave as v1 does") is not met by pointer-only editing alone.

## Research basis

Read in full for spec 030 and re-used here: `script/src/ui/input.js` (`handleKeyDown`, lines 304-544; `handleNoteOn`, lines 734-830; `getCurrentOctave`/`setCurrentOctave`, lines 717-730) and `script/src/enum.js` (`KEYBOARDKEYS`/`OCTAVENOTES`/`KEYBOARDTABLE.main`, lines 419-505 - 27 entries, not the roadmap's originally-stated "thirty-one", a correction spec 030's requirements.md already recorded). `domain/song/index.js` (spec 028/029's `putNote`/`putNoteParam`/`insertNote`/`removeNote` and selection API) and `runtime/gridController.js` (spec 030's existing keydown navigation) are the primitives this spec builds on, unchanged in shape.

Three real gaps found by reading the current v2 source, not assumed going in:

- **"Recording" has no v2 concept.** v1 gates all of this on `Tracker.isRecording()`, a boolean the ported engine (`player/src`) never carried a getter for (spec 030 already found this once, for the mouse gesture). `app/actions/recordToggle.js` and the `record.active` state field already exist - a control-bar Record button already toggles them - but `capabilities.js` still maps nothing to it (`// "record.toggle": still a generated mock; recording is not ported yet.`). This spec is what finally reads that comment as instructions.
- **"Current octave" has no v2 concept.** v1's `currentOctave` (default 2) lives in `script/src/ui/input.js`, clamped to 1-3 in ProTracker mode or 0-7 in FastTracker mode. Nothing in v1's UI outside the piano widget (`pianoView.js`, a P11 surface) displays it, so it needs no store field or visible control here - internal state only, the same shape `domain/song`'s own `currentTrack`/`currentTrackPosition` already are.
- **`mountGeneric.js`'s `keyInput()` only carries `event.key`.** v1's key-to-note table is keyed by `event.code` (the physical key, e.g. `"KeyZ"`), which is what makes the QWERTY-shaped ZXCV/QWERTY layout work identically regardless of Shift or a non-Latin input method active. Matching that (rather than reinventing a `key`-based table that would break under Shift or drift on non-QWERTY layouts) needs `code` threaded through the same event, alongside `event.repeat` for the OS key-repeat guard v1's own `keyDown[index]` map exists to approximate - both are small, additive fields nothing else reads.
- **Spec 030's own `ArrowUp`/`ArrowDown`/`PageUp`/`PageDown` do not match v1's real keyboard behavior.** Spec 030 ported its baseline keydown navigation from `patternView.js`'s *mouse-wheel* handler (`onMouseWheel`, which guards against ever crossing a pattern boundary, so it reads as a clamp), not from `input.js`'s own keyboard case statements - `script/src/ui/input.js` was read in full for the first time for *this* spec. The real keyboard behavior is different on both counts: `ArrowUp`/`ArrowDown` call `Tracker.moveCurrentPatternPos(±1)` (`input.js:416,422`), which *wraps* at the pattern's ends (`script/src/tracker.js:230-236`), not clamps; `PageUp`/`PageDown` (`input.js:390-403`) jump to the nearest quarter-pattern boundary (`Math.floor(patternLength/4)` as the step, rounding to the nearest multiple, moving one more step if already on one) and *do* clamp at either end. This spec corrects both, since it is already re-reading and rewriting this exact keydown surface - see NOTE-010.

## Requirements

- **NOTE-001 — Recording is a real, toggleable concept:** As a user, pressing the control bar's Record button (or dispatching `record.toggle`) flips a real state in `domain/song`, mirrored to the existing `record.active` field exactly as `domain/playback`'s own transport state already mirrors to `playback.status`. Acceptance: `capabilities.js` maps `record.toggle` to a real module (no longer a generated mock); toggling it twice returns to the original state; nothing about pattern editing is possible while it is off (NOTE-003 through NOTE-006 below all no-op).
- **NOTE-002 — An octave is selectable with F1-F7:** As a user, F1-F7 set the octave notes resolve into, clamped to the current format's valid range (1-3 in ProTracker/MOD, 0-7 in FastTracker/XM); a key outside the current range is a no-op, matching v1. Acceptance: `domain/song.getCurrentOctave()` starts at 2; F1 sets it to 1; in ProTracker mode, F5-F7 (values 5-7) have no effect; in FastTracker mode they do.
- **NOTE-003 — A mapped key writes a note while recording, cursor on the note column:** As a user, with the grid focused, recording on, and the cursor's column at the note position (column 0), pressing one of the 27 mapped keys (ZXCVBNM,./SDGHJ row for the current octave, QWERTYUIO/2356 79 row for one octave up) writes that note - instrument from the currently selected instrument, period/index from the key and octave - at the current track and pattern position, then advances the pattern position by one row. Acceptance: the note written matches v1's own `KEYBOARDTABLE.main`/`OCTAVENOTES` resolution for every mapped key; an unmapped key does nothing; holding a key down (OS key-repeat) writes the note once, not once per repeat event.
- **NOTE-004 — Typed hex (or FastTracker mnemonic) characters edit the instrument/volume/effect/param columns:** As a user, with the cursor on any column but the note column, typing a hex digit (`0-9A-Fa-f`) edits that column's nibble via the existing `putNoteParam`, then advances one row; in FastTracker mode, the volume column's *first* nibble additionally accepts the single-letter volume-effect mnemonics v1 does (`-`,`+`,`d`/`D`,`u`/`U`,`s`/`S`,`v`/`V`,`p`/`P`,`<`,`>`,`M`, and `0`-`4`), and the effect column accepts base-36 (`0-9A-Za-z`) rather than plain hex, matching FastTracker's own extended effect letters. Acceptance: typing a digit into the instrument or param columns matches v1's nibble math exactly (already implemented and tested in `putNoteParam`); an unrecognized character in a given column is ignored, not written as garbage.
- **NOTE-005 — Backspace, Ctrl/Cmd+Backspace, Delete and Ctrl/Cmd+Enter edit rows and columns:** As a user: plain Backspace clears the current column (the note, or the column's value) and then steps the pattern position *forward* one row, matching v1's own (non-obvious) direction; Delete does the same, without Backspace's FastTracker-volume-column special case; Ctrl/Cmd+Backspace removes the current row (shifts the rest of the track up) and steps *backward* one row; Ctrl/Cmd+Enter inserts a row (shifts the rest of the track down) and steps forward one row. Acceptance: each of the four reuses `domain/song`'s existing `putNote`/`putNoteParam`/`removeNote`/`insertNote` with no new mutation logic; each remains undoable through the same history those functions already register with.
- **NOTE-006 — A track jumps by a full column-set without using Tab:** As a user, since `Tab` is already claimed globally for moving focus between controls (found while implementing spec 030), Ctrl+ArrowLeft/Ctrl+ArrowRight move the cursor a full track's worth of columns backward/forward, replacing v1's `Tab`/`Shift+Tab`. Acceptance: from any column of track *n*, Ctrl+ArrowRight lands on the same column of track *n+1* (wrapping at the song's track bounds, exactly as plain column movement already wraps at pattern bounds).
- **NOTE-007 — Holding the selection modifier while navigating grows a selection, exactly as a mouse drag does:** As a user, holding Ctrl or Cmd while pressing any navigation key (arrows, the Ctrl+Arrow track jump, PageUp/PageDown, Home/End) begins a selection (if none exists) at the cell the cursor was on before the move, or extends the existing one to the cell it lands on after the move - the same rectangle spec 030's mouse-drag selection already produces, through the same `beginSelection`/`extendSelection` calls. Acceptance: Ctrl+ArrowDown twice from an unselected cursor selects a 3-row-tall, one-track-wide rectangle; releasing Ctrl and pressing a plain arrow afterward leaves that selection untouched, matching the mouse gesture's own behavior.
- **NOTE-008 — Escape clears the grid's own selection:** As a user, pressing Escape while the grid is focused clears any active selection, in addition to whatever `mountGeneric.js`'s existing generic Escape handling (blur, closing an open modal) already does. Acceptance: with a selection active, Escape clears it and reports the key as handled by the grid's own controller.
- **NOTE-009 — Nothing fires unless recording is on and the cursor's context makes it meaningful:** As a user, none of NOTE-003 through NOTE-006 mutate anything while `record.active` is off - the key is left unhandled (falls through to whatever else the application does with it), not silently swallowed. Navigation (arrows, Page/Home/End, the track jump) and selection-growth (NOTE-007) work regardless of recording, matching spec 030 and v1 alike. Acceptance: with recording off, every mapped note/hex/Backspace/Delete/Enter key at the grid reports `handled: false`; with recording on, they report `handled: true` and mutate as specified above.
- **NOTE-010 — `ArrowUp`/`ArrowDown` wrap; `PageUp`/`PageDown` jump by a quarter pattern, not a fixed count:** As a correction to spec 030 (which ported these from `patternView.js`'s mouse-wheel guard, not `input.js`'s own keyboard cases): `ArrowUp`/`ArrowDown` move the pattern position by one row, wrapping from the last row to the first (and vice versa) rather than stopping; `PageUp`/`PageDown` jump to the nearest multiple of `floor(patternLength/4)` (stepping one further if already exactly on one), clamped at the pattern's ends rather than wrapping. Acceptance: `ArrowUp` from row 0 moves to the last row; `PageDown` from row 0 in a 64-row pattern moves to row 16, and again to row 32, and from row 63 stays at 63.

## Non-functional requirements

- **Architecture.** No new consumer of `domain/song` beyond `runtime/gridController.js` (already spec 030's); "recording" and "current octave" are added to that same module as two more pieces of internal state, exactly the shape `currentTrack`/`currentTrackPosition` already are - not a new capability boundary. `mountGeneric.js`'s `keyInput()` gains two additive fields (`code`, `repeat`) read by nothing else.
- **Fidelity.** The 27-key table, the per-column hex/mnemonic parsing, and the Backspace/Delete-direction quirks are ported exactly as v1 has them, including the parts that read as inconsistent (Backspace stepping *forward*) - matching musicians' existing muscle memory is the point, not a corrected version of it.
- **Reliability.** Every mutation goes through `domain/song`'s existing, already-undo-tested functions; this spec adds no new edit-action kind and no new replay logic.
- **Usability.** The note-key table is keyed by physical key (`event.code`), not the shifted/localized character, so it behaves identically under Shift and on the QWERTY layout v1's own convention assumes - matching v1's behavior rather than v2 accidentally depending on keyboard layout or shift state.
- **Security.** Not applicable; no new input surface beyond the existing keyboard handling spec 015/030 already established.

## Scope boundaries

In scope: `domain/song`'s recording and octave state; wiring `record.toggle` to it in `capabilities.js`; `runtime/gridController.js`'s keydown cases for note entry, hex/mnemonic column entry, Backspace/Delete/Ctrl+Backspace/Ctrl+Enter, the Ctrl+Arrow track jump, keyboard-driven selection growth, and Escape-clears-selection; the two additive `keyInput()` fields.

Out of scope, recorded rather than dropped: live audio preview/audition when a mapped key is pressed while *not* recording - v1's `handleNoteOn` always previews a sound regardless of recording state, but that reaches the audio engine directly and has nothing to do with the grid or its focus; it belongs with P11's "the piano" surface, which does not exist yet. The global Edit-menu shortcuts (`undo`/`redo`/`cut`/`copy`/`paste`, already `unresolved-action-reference` loose ends in `app.yaml`) - real, but a menu-wiring concern, not keyboard note entry, and not gated on the grid having focus the way everything above is. v1's auto-nudge of the current octave by ±2 when the loaded format's mode changes (`input.js:962-968`) - a nicety with no v2 trigger point yet (nothing in this spec's scope changes the loaded format at runtime), not implemented.
