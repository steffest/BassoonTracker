# 043 — The loop creator

Date: 2026-09-14. Kind: feature. Status: specified. Continues package **P10** (features and the plugin path) of the [port roadmap](../010-port-roadmap/requirements.md), following spec 040 (sample processing operations), spec 041 (the waveform view) and spec 042 (the sample-editor screen). The first of the three sub-features spec 040 recorded as separable (`loopCreator.js`, `resamplePanel.js`, `hissReductionPanel.js`).

## Purpose

`script/plugins/sampleeditor/loopCreator.js` (848 lines, read in full for this spec) is a self-contained crossfade loop-creation editor: given a sample's chosen loop start/end, it blends a little audio across the seam (three independently-sized regions, each with its own blend-volume control) so the loop plays back without an audible click or pop. This spec ports the mechanism - the state model and the DSP that computes and applies the blended preview - as a headless, fully-testable capability, matching the established "mechanism before its interactive screen" pattern (`patternGrid` before its screen, `fileBrowser` before the disk-operation screen, spec 040's own four operations and spec 041's waveform view before spec 042's own screen). The interactive drag-based waveform overlay this needs (its own eight independent drag targets: two loop markers, three blend-size handles, three blend-volume lines, plus three more "original volume" lines) is real, substantial, and deliberately a later spec's own - see Scope boundaries.

## What v1 actually does, and what this narrows out (read from source, not assumed)

Three independently-sized regions, each in samples, each computed from the chosen loop bounds: **tail** (audio just after the loop end, faded and blended into the loop's own start - "cyan"), **head** (audio just before the loop start, faded and blended into the loop's own end - "orange"), and **loop-end** (the loop's own trailing audio, faded and blended into the audio just before the loop start - "purple"). Each region has two independent blend-volume controls (0-1): how loud the *blended-in* audio is (`blendTail`/`blendHead`/`blendLoopEnd`) and how loud the *original* audio stays within that same region (`origBlendTail`/`origBlendHead`/`origBlendLoopEnd`) - the fade shape of each mirrors the other so they crossfade rather than simply mix. `computeLayers()` builds the three blended layers from a snapshot of the original, unmodified sample data (`originalData`, captured once at open time); `applyPreview()` rebuilds `instrument.sample.data` from that same snapshot every time, writing each layer's own blended values over it - idempotent by construction, never compounding across repeated calls. Three presets (`Fade in Head`, `Fade out Tail`, `Cross Fade`) set all nine values at once from the current max region sizes; opening for an instrument with no usable existing loop applies `Cross Fade` automatically as a sane default, matching v1's own `needsDefaultLoop` branch (`loopCreator.js:764,802-808`).

`me.open`/`me.save`/`me.cancel`/`me.setLoopStart`/`me.setLoopLength`/`me.setZoom` are the entire public surface a host (`sampleView.js`) drives; everything else (drag handling, drawing, the menu-bar controls) is internal to the panel itself. Notably, `me.setLoopStart`/`me.setLoopLength` (called by the sample-editor screen's own loop spinboxes while the overlay is open, `sampleView.js:275,290`) do **not** apply `snapToZero` - only a mouse *drag* on a loop marker does; a genuinely real asymmetry, not an oversight to smooth over. A dead function was also found: `snapMarkersToZero()` (`loopCreator.js:590-601`) is fully implemented but never called from anywhere in v1 - not wired to the "Snap to zero" checkbox (which only flips the flag `onDrag` reads) or to any button. Not ported - see Scope boundaries.

A genuine, confirmed bug was found in v1's own undo path, not merely a difference of taste: `saveLoop()` sets `editAction.loopStart`/`.loopLength` (to the loop bounds *before* the loop-creation session, for undo to restore), but the replay handler for a `REPLACE`-kind sample action (`waveform.js`'s own `EVENT.commandProcessSample` listener, 1469-1524) only ever reads those two fields for its `CUT`/`PASTE` branches - never `REPLACE`, the one kind `saveLoop()` itself uses. Undoing "Create Loop" in v1 reverts the sample *data* but leaves `instrument.sample.loop.start`/`.length` at whatever the loop-creation session left them, silently out of sync with the reverted audio underneath. Fixed here, not reproduced - see Decisions and assumptions.

## Decisions and assumptions

- **One new internal module, `domain/sampleEditor/loopCreator.js`**, not folded into `domain/sampleEditor/index.js` itself - the state this subsystem owns (loop bounds, three region sizes and their maxes, six blend values, a snapshot of the original data, snap-to-zero) is large and genuinely distinct from the plain `{start, length}` selection `index.js` already holds; splitting it out mirrors `domain/moduleExport/{protracker,fasttracker}.js`'s own precedent of an internal, directly-testable sibling module within the same domain folder, imported only by tests and (once a later spec wires a real screen) by that screen's own controller - never re-exported through `index.js` as its own name would be redundant.
- **The absolute setters this spec exposes (`setLoopStart`/`setLoopLength`/`setTailSize`/`setHeadSize`/`setLoopEndSize`/`setBlendTail`/`setBlendHead`/`setBlendLoopEnd`/`setOrigBlendTail`/`setOrigBlendHead`/`setOrigBlendLoopEnd`) are the domain-level equivalent of v1's own delta-driven drag handlers**, the same split already established between `runtime/waveformController.js` (computes a drag delta, calls `sampleEditor.setSampleSelection(start, length)` with an absolute value) and the domain module underneath it. A later spec's own drag controller computes deltas against pointer movement and calls these; this spec supplies the destination, not the gesture.
- **`setLoopStart`/`setLoopLength` deliberately do not apply snap-to-zero**, faithfully matching v1's own asymmetry (Purpose section above) - `snapToZero` is stored as plain state for a later drag controller to read, not applied by either of these two setters.
- **`snapMarkersToZero()` is not ported.** It is dead code in v1 (confirmed by grep - defined, never called), and porting an unreachable function forward gains nothing; recorded rather than silently dropped.
- **The undo/redo loop-bounds bug is fixed, not reproduced.** `domain/song/index.js#applySampleDiff` (spec 040) gains one small, optional, backward-compatible extension: a registered SAMPLE action may carry `loop: {from: {start, length}, to: {start, length}}`, restored alongside the data when present. Every existing caller (the four spec-040 operations) omits it and is unaffected; this spec's own `saveLoopCreator()` is the first to supply it, and undoing "Create Loop" now correctly restores both the data and the loop bounds together.
- **No reactive instrument-change handling.** v1's own `EVENT.instrumentChange` listener (`loopCreator.js:741-753`) restores the previous instrument's data and either reopens for the new instrument or closes, entirely automatically. Nothing in v2 reaches this module from any UI yet (matching spec 039/040's own "headless only" precedent), so there is no event to react to; wiring this belongs to the later screen spec that actually opens this panel from a real gesture.

## User stories and acceptance

- **LOOP-001 — Opening seeds sane defaults.** Opening for an instrument with no usable loop (`disabled`, or `length < 2`) creates one at roughly 60%-85% of the sample (snapped to the nearest zero crossing at each end) and applies the Cross Fade preset automatically; opening for an instrument with an existing usable loop keeps it and computes layers from the region sizes already in state. Acceptance: unit tests against a real loaded fixture, one per branch.
- **LOOP-002 — The three blended layers are computed correctly and applied idempotently.** `computeLayers()`/`applyPreview()` produce byte-identical output to hand-traced expected values for a small, synthetic sample; calling either twice in a row (with no state change between) produces the same result both times, never compounding. Acceptance: unit tests with small hand-computed fixtures.
- **LOOP-003 — Every setter clamps to its own current maximum, recomputed from the current loop bounds.** Moving a loop marker re-derives every region's own maximum (`recomputeMaxes`) and clamps any region already past the new maximum down to fit, exactly as v1's own `recomputeMaxes` does. Acceptance: unit tests for each setter, including a marker move that shrinks an existing region's own max below its current size.
- **LOOP-004 — Presets set all nine values from the current max region sizes.** Each of the three presets matches v1's own table exactly. Acceptance: a unit test per preset.
- **LOOP-005 — Save registers one undo entry restoring both data and loop bounds together; cancel restores immediately.** Undo/redo of a saved loop-creation session round-trips both the sample data and `instrument.sample.loop.start`/`.length` exactly - the fix described above. Cancel restores the original data and loop bounds synchronously, with nothing registered on the undo stack. Acceptance: unit tests for save+undo+redo and for cancel, against a real loaded fixture.
- **LOOP-006 — No regressions.** Full unit suite passes; `node build.mjs app`/`dist` unaffected (no YAML/compiler/capabilities.js change - this spec is headless, matching spec 039/040's own precedent).

## Non-functional requirements

- Headless verification only (no browser-automation dependency in this environment, the same recorded reason every spec since 019 has given).
- No new authoring mechanism, no YAML, no `capabilities.js` mapping - nothing here is reachable from any UI yet.

## Scope boundaries

In scope: `domain/sampleEditor/loopCreator.js` (new), `domain/song/index.js`'s one small optional extension to `applySampleDiff`, and tests for both.

Out of scope, recorded rather than silently dropped:

- **The interactive drag-based waveform overlay** - eight independent drag targets (two loop markers, three blend-size handles, three blend-volume lines, three "original volume" lines), its own hit-testing, its own drawing (loop-region tint, marker triangles, colored blend layers, a legend) - a fourth specialized-component leaf, at least as complex as the waveform view (spec 041) was, and a real, substantial later spec of its own.
- **The menu-bar controls** (title label, Apply/Cancel buttons, "Snap to zero" checkbox, the presets dropdown) and the panel's own open/close wiring into the sample-editor screen (spec 042) - ordinary component-tree territory once the interactive overlay above exists to host them; authoring the menu bar without the overlay it controls would be premature.
- **`snapMarkersToZero()`** - confirmed dead code in v1, not ported.
- **Live zoom sync with the waveform view** (`me.setZoom`) - purely a drawing concern of the deferred overlay; nothing in this spec's own state needs a zoom window.
- **Reactive instrument-change handling** (v1's own `EVENT.instrumentChange` listener) - nothing reaches this module from any UI yet for it to react to.
